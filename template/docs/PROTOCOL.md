# Протокол

## Протокол сессии

**Старт:** автозагрузка хаба (`CLAUDE.md` → `AGENTS.md` → «Чтение на старте») → `ROADMAP.md` § Вехи (у незакрытых вех — строки задач со ссылками на таск-файлы) → таск-файл задачи (`docs/tasks/<задача>.md`). Итерация автоцикла получает имя задачи аргументом и открывает таск-файл сразу, минуя роадмап. Больше на старте ничего не читается.

**Работа:** за сессию — не больше одного шага из очереди «Постановки» таск-файла; критерии шага записаны там же. Шаг бывает больше сессии (дебаг, сторонняя дока, сломанные тесты): такая сессия рвётся по сигналу context-guard, «Контекст» несёт точку продолжения, следующая сессия ведёт тот же шаг дальше. Чекбокс шага ставится только по критерию завершения, не по числу сессий.

**Завершение** — единый список, и штатный конец, и конец по сигналу context-guard:

1. результат — в артефакт задачи (код, спека, архитектура, ресерч);
2. `DECISIONS.md` — запись сверху на каждое решение пользователя: ответ на блокер (секция «Блокер» при статусе «в работе»), выбор из вариантов агента, отказ от предложения агента. Запись — одна строка `- **<ISO-дата>** <вопрос> — задача: <задача или «беседа»>; предложение агента: <…>; ответ: «<слова пользователя>»`, у ответа на блокер в конце — `; «Постановка» правилась` или `; «Постановка» не правилась` (по `git diff HEAD` таск-файла, отметки чекбоксов не в счёт): одной строкой запись целиком переживает слияние веток и находится grep-ом. Мат в цитатах пользователя заменяется литературным словом в квадратных скобках — «текста [очень много]», а мат без литературного смысла — двумя точками: «да .. делай». Ответ оркестратора на блокер (§ Таск-файлы) — запись того же вида, ответ — `ответ: оркестратор — «<его текст>»`: в реестре видно, что решал оркестратор, а не пользователь. Его ответ на просьбу о проверке — прогон тестов, осмотр, запрос к базе — идёт в запись одной фразой итога: «прошли», «упали 3 теста», «работает, 2 недочёта»; нужное дальше из подробностей — недопроверенное, замечания, находки вне задачи — уходит в хвосты «Контекста»;
3. таск-файл: шапка актуальна, чекбокс шага по критерию завершения, «Контекст» перезаписан целиком;
4. коммит в текущую ветку — всё сделанное сессией, включая правки доков; личные данные в коммите и его сообщении — по § Личные данные и скрытые настройки; сообщение — одна строка с именем задачи и шага: по имени запись журнала о задаче соберёт её коммиты; WIP допустим; своя прошлая работа отменяется новым коммитом, своё сообщение ему — `git revert --no-commit` и `git commit -m`; перезапись истории ветки — `git reset`, `git rebase`, `git commit --amend`, в том числе коммита, сделанного в этом же ответе, — после явного «да» пользователя;
5. `JOURNAL.md` — когда работа закончена: задача получила статус «готово» или закончена работа вне задачи; коммиты закрытых шагов собирает запись о задаче. Запись сверху одной строкой: у задачи — `` - **<ISO-дата>** задача `<задача>`, `<типы коммитов>` (`<хэш>`, …) — что сделано. Зачем: … ``, у работы вне задачи — `` - **<ISO-дата>** `<типы коммитов>` (`<хэш>`, …) — что сделано. Зачем: … ``; текст после хэшей — до 1250 знаков, счёт `LC_ALL=C.UTF-8 wc -m`, языком, понятным менеджеру, без имён файлов, классов и технического жаргона; часть «Зачем: …» — только при явной причине: её назвал пользователь — цель задачи, ответ в `DECISIONS.md` — или она записана по ходу работы — ресерч, сообщение коммита; такой нет — запись кончается на «что сделано»; все записи одной задачи находит grep по `` задача `<задача>` ``. В скобках — хэши всех коммитов работы: у задачи — её коммиты (`git log --oneline --grep '<задача>'`) после коммита последней записи журнала по ней; коммит, где имя задачи — часть имени другой задачи или слово в другом смысле, — не её; у работы вне задачи — коммиты этой работы. Задача, дополненная шагами после «готово», на новом «готово» получает новую запись — с коммитами после прошлой и о сделанном по новым шагам. Запись — отдельным коммитом после перечисленных, сообщение — пометка «журнал», у записи о задаче — и имя задачи: собственного хэша коммит в себе не несёт.

Работа вне задачи — разовая правка, закрытие вехи — завершается шагами 1, 2, 4, 5.

Журнал и реестр сливаются между ветками без конфликта правилом `merge=union` из `.gitattributes`, а кнопка запроса на слияние на сайте его не применяет — проверено на GitHub. Перед кнопкой в свою ветку вливается основная командами git на компьютере — `git fetch origin`, `git merge origin/<основная ветка>`, `git push`; сайт показал конфликт в журнале или реестре — те же команды.

Сигнал context-guard в итерации автоцикла означает «завершение сейчас»: тот же список, после него сессия заканчивается. Режим сигнала задаёт движок переменной окружения `CONTEXT_GUARD_MODE=protocol` при запуске итерации — хук присылает инструкцию выполнить протокол молча. Интерактивным сессиям проекта хук предлагает варианты по правилам проекта: в репозитории лежит `.claude/context-guard.conf` со строкой `CONTEXT_GUARD_MODE=rules`.

## Сообщения пользователю

Всё, что сессия пишет пользователю, — вопрос, варианты выбора, секция «Блокер», итог сессии — читает человек, который может не знать или не помнить подробностей проекта и его реализации:

- к читателю — на «ты», обычными словами: что увидит пользователь продукта и что нужно от человека; имена файлов, функций и шагов остаются в коде и «Контексте», обозначения проекта и слова из текста задачи — «пересмотр плана», «отпавшие вопросы» — раскрываются словами: каждое звено объяснения называет то, что человек видит или может открыть, — вопросы 2 и 3 блокера, заметку в файле задачи;
- коротко: вопрос — одной фразой, пояснение — пара строк, когда вопросу нужен контекст. Ответ на вопрос пользователя в любой беседе, со скиллом и без, — о спрошенном, одной-двумя фразами: на «какой вопрос я тебе задал?» — сам вопрос; планы и разбор, о которых он не спрашивал, прячут ответ. Поручение — сразу делом: на «пиши по шагам» — первый шаг;
- вопрос в беседе — один на сообщение, с контекстом: о чём он и что изменит ответ; следующий вопрос — следующим сообщением, после ответа на этот. Окно выбора `AskUserQuestion` — тоже один вопрос. Пункт под номером, на который отвечают по номеру, — находка, правка задачи — тоже вопрос. Секция «Блокер» собирает все вопросы шага (§ Таск-файлы), а в беседе их показывают по одному: в общем сообщении читатель путается и теряет часть, а уточнения уводят его выше окна терминала;
- просьба сделать что-то руками — отдельным пунктом, нумерованными шагами; шаг — одно или несколько действий ради одного результата. Первая строка шага — `<N>. <место> — <дело>`: место — где шаг начинается: компьютер, сервер, браузер, чат Claude, одним и тем же словом у всех шагов этого места; действие шага в другом месте называет это место; дело — несколько слов. У первого шага и шага, сменившего место, вторая строка — `Вход: <как туда попасть>`: команда (`ssh <сервер>`, `cd <папка>`), адрес страницы или окно — «терминал в папке проекта». Дальше — готовые команды и что прислать: вывод или строка, по которой виден итог. Шаг — до пяти строк, не считая команд, без веток «если пошло не так»: сбой разбирается по присланному. По местам и входам шагов оркестратор рисует схему мест на странице задачи. Просьба, после которой остаются тестовые папки, сети Docker или истории сессий, кончается шагом уборки с готовыми командами;
- шаги руками в беседе — по одному на сообщение: перед первым — строка, сколько шагов и где; у шага — зачем он, одной фразой; следующий — после ответа пользователя, что шаг сделан, или присланного итога. В секции «Блокер» шаги просьбы стоят все, по номерам: её читают из файла и уведомления;
- строка готовой команды — до 60 знаков: терминал переносит длинную строку по ширине окна, и скопированная команда вставляется кусками, которые рвут её смысл; длинная команда — несколькими короткими или строками с `\` в конце;
- выясненное по ходу работы — для следующей сессии, его место — «Контекст».

## Личные данные и скрытые настройки

Личные данные — сведения о человеке и его окружении, которые проекту для работы не нужны: имена людей, названия личных проектов и компаний, адреса, телефоны, почта, пути и папки компьютера, имена компьютеров и адреса домашней сети, номера договоров и счетов, коды клиентов. Правило действует и на значение, которое уже есть в коде проекта.

- В git — в файлах и сообщениях коммитов — личные данные идут обезличенным вариантом: «пилотный проект», «<компания>», путь в домашней папке — через `~`. Обезличивание идёт молча, движок продолжает цикл.
- Исходное значение — строкой на замену в `my_local/personal.md` проекта: что написано в git, что было на самом деле, в каком файле. Папка `my_local/` — вне git строкой `my_local/` в `.gitignore`; строки нет — сессия дописывает её до записи файла.
- Согласие на исходное значение в git — вопросом пользователю, когда без него документ теряет смысл; в итерации движка — вопросом блокера (§ Таск-файлы). Таск-файл и `DECISIONS.md` лежат в git, поэтому вопрос называет значение обезличенным вариантом и строкой `my_local/personal.md`. Согласие на вид данных навсегда («название компании можно») — строка в `RULES.md` § Конвенции работы: следующие сессии пишут такие данные без вопроса.

Скрытая настройка — файл, который меняет поведение git, Claude Code или оболочки и не виден среди файлов проекта: всё в папке `.git/` — настройки, хуки, список исключений `.git/info/exclude`; настройки под `.gitignore`, например `.claude/settings.local.json`; личные настройки в домашней папке компьютера и контейнера — `~/.gitconfig`, `~/.config/`, `~/.claude/`, файлы запуска оболочки (`~/.zshrc`, `~/.bashrc`), планировщики задач.

- Правка скрытой настройки — после явного «да» пользователя на вопрос сессии об этой правке. Вопрос называет файл и его место, зачем правка, что после неё изменится без следа в файлах проекта, и видимую замену, когда она есть: `.gitignore` вместо `.git/info/exclude`. Вопросом ответ сессии кончается, правка — после «да». Просьба о результате — «только на моей машине», «в файлы проекта не пиши» — согласием на правку не считается: «да» относится к правке, которую вопрос уже назвал. В итерации движка вопрос — блокером. В контейнере, где `.git/info` подключена только на чтение, запись в неё отклоняется: правку там сессия после «да» отдаёт пользователю командой для терминала хоста. Право на запись в скрытую настройку проверяется без записи, `test -w <путь>`: пробный файл в скрытой папке — тоже правка.
- Тихая правка скрытой настройки — антипаттерн: система ведёт себя иначе, чем видно по файлам проекта, и пользователь не находит причину. Пример — строка в `.git/info/exclude`, дописанная без спроса: git перестаёт показывать файл, а в `.gitignore` и истории проекта следа нет.

## Таск-файлы

Задача — файл `docs/tasks/<задача>.md`: постановка, перезаписываемый контекст, машиночитаемая шапка. Формат шапки фиксирован — движок автоцикла читает её `grep`-ом, статус всегда первой строкой:

```
статус: в работе | блокер | готово
```

Шаблон:

```markdown
статус: в работе

# <задача>

## Постановка
Просьба пользователя, <дата>: «<его слова>»

Решения по теме: «<ответ>» (<дата>)

Дописала сессия: <что и откуда>

<цель; очередь шагов чекбоксами `- [ ]`, по одному на шаг; способ проверки завершения шага; критерий блокера. Пишется при создании задачи, живёт до её конца; чекбокс ставится по критерию завершения шага.>

## Контекст
<перезаписывается каждой сессией целиком: следующий шаг и файл, с которого начать; хвосты; состояние среды — эмулятор, контейнеры>
```

Очередь делится на этапы абзацем `Этап <N> — <название>.` перед первым шагом этапа: правила, общие для шагов этапа, — тем же абзацем или следующим, а шаг несёт только своё. По этой строке страница задачи оркестратора ставит этап над его шагами. Этапы ресерча и проверки постановки ставит сессия, заводящая задачу (§ Ресерч и проверка постановки), этап ревью дописывает `/box-review`, этап QA — `/box-qa`.

Секция `## Блокер` дописывается в конец таск-файла вместе со статусом «блокер» и пишется по § Сообщения пользователю: вопрос, предложение сессии, просьба сделать руками, когда она есть, и последней строкой — как ответить, с именем задачи. Вопросы шага собираются в один блокер: сессия сначала делает в шаге всё, что от ответов не зависит, затем пишет секцию со всеми вопросами шага, у каждого — своё предложение; так шаг останавливает автоцикл один раз, а в беседе их показывают по одному (§ Сообщения пользователю). У предложения: `Как ответить: допиши в конец файла docs/tasks/<задача>.md строку, которая начинается с «ответ:», — «ответ: ок» или «ответ:» и свой вариант. Потом запусти в Claude /box-next <задача> или в терминале agent-loop.sh <задача>.` У вопроса и просьбы сделать руками: `Как ответить: допиши в конец файла docs/tasks/<задача>.md строку, которая начинается с «ответ:», и после двоеточия — сам ответ. Потом запусти в Claude /box-next <задача> или в терминале agent-loop.sh <задача>.` Движок отправляет секцию в уведомлении. Строка секции, начинающаяся с «ответ:» в любом регистре, — ответ на блокер: с ней блокер снят, поэтому сессия шага так строк не начинает. Ответ пишет пользователь или оркестратор — интерактивная сессия на хосте, которая ведёт задачу движком и сама отвечает на вопросы, снимаемые без решения пользователя; строка оркестратора начинается с «ответ: оркестратор —». При статусе «в работе» сессия на первом же завершении переносит блокер с ответом в `DECISIONS.md` и стирает секцию.

Просьба сделать руками, итог которой виден в файлах — копии прогона, журнале движка, истории бесед, — просит у пользователя только шаги и «сделано»: ответ — «ответ: сделано» и строки, которые напечатали шаги, например путь копии. Что проверить, секция пишет пунктами, у пункта — файл, где виден его итог. Пункты сверяет оркестратор агентом проверок, без оркестратора — следующая сессия по копии: итог берётся из файлов, и пользователь не сверяет пункты сам. Сессия в контейнере читает только папку проекта: историю беседы с компьютера и тестовый проект шаг уборки переносит в папку `my_local/` проекта — она вне git, а в историях бесед пути компьютера (§ Личные данные и скрытые настройки); копию в папке под git движок после итерации принимает за правки без коммита и останавливает цикл. Вопрос пользователю об итоге — только о том, что видно одними глазами и в файлы не попадает, — отдельным вопросом блокера.

Цель и способ проверки (тест, команда, ожидаемый вывод) меняет только пользователь — сам или согласием на правку из секции «Блокер»: её слово в слово вписывает сессия, которая переносит блокер в `DECISIONS.md`. Цель, разошедшаяся с докой или возможностями инструмента, и способ проверки, разошедшийся с реальностью, — блокер: сессия пишет в секцию «Блокер», что разошлось и что предлагает, и ставит статус «блокер».

Предложение сессии — в секции «Блокер», в хвостах «Контекста», в ресерче и макете, в беседе — сверяется с `DECISIONS.md` grep-ом по словам темы. Решение пользователя по теме идёт в предложение дословно, цитатой с датой, всеми своими частями. Предложение, которое расходится с ним хоть в части, начинается пометкой «против решения от <дата>: «<цитата>»» и называет, что меняет: так «ок» пользователя утверждает только то, что он видел.

Адрес интернета, нужный шагу и закрытый ограничением сети контейнера, — тоже блокер. Закрытый адрес отвечает ошибкой соединения сразу, за доли секунды: `Couldn't connect to server`, `Network is unreachable`, `fetch failed`. В секции «Блокер» — адрес, зачем он шагу, и просьба сделать руками: строка `CLAUDE_BOX_ALLOW` в `environment:` сервиса `claude` в `claude-box.yml` готовой к вставке — прежние адреса строки и новый через пробел; `claude-box.yml` правит человек.

Сбой среды — Docker, сеть, инструменты, — не связанный с шагом, — тоже блокер. Сессия его не обходит — не удаляет ресурсы руками, не вырезает предупреждения из вывода, не меняет способ запуска: обход прячет причину, и она возвращается на следующем запуске. Сессия ищет причину проверкой — вывод команд, документация, история git — и пишет в секции «Блокер», что сломалось, почему и что предлагает починить. Сбой, на котором итерация упала, не дойдя до блокера, — например, контейнер Claude не стартовал, — оркестратор разбирает так же: причина и починка — в его вопросе пользователю о падении итерации.

Итерация движка идёт без человека: её последнее сообщение никто не читает, а статус «в работе» движок запускает на тот же шаг новой сессией. Поэтому в итерации вопрос пользователю, просьба сделать руками и команда, которую отклонила проверка разрешений Claude Code, — блокер; отклонённая команда идёт в секцию просьбой сделать руками, готовой строкой. Что сессия — итерация, ей сообщает строка движка в системном промпте.

«Контекст» перезаписывается, история живёт в журнале. Блокер снимает пользователь или оркестратор: пишет ответ строкой «ответ:» в секции «Блокер» — согласие или свой вариант; пользователь при необходимости ещё правит «Постановку» или «Контекст». Согласие — короткое «ок», «да», «согласен» или «делай»: сессия делает, как предложила. Свой вариант и согласие с замечаниями («норм, но …») — тоже решение: сессия делает по нему, и вопрос закрыт вместе с проверкой, которую он вёл. Правка по словам пользователя на повторное «так годится?» не выносится: такой вопрос гонит шаг по кругу без нового решения. Новый блокер после ответа — вопрос, который ответ оставил открытым: отказ целиком, замечание с несколькими исполнениями и разными последствиями, вопрос пользователя вместо ответа. Статус «в работе» по строке ответа ставит движок перед итерацией, при ручном запуске — `/box-next` на старте сессии. Правки пользователь оставляет в рабочем дереве: их забирает коммит сессии, а шаг 2 завершения видит их в `git diff HEAD`.

Ответ, который снял допущение остальных вопросов блокера, предложенного итога шага или плана «Контекста» на время после ответа, — повод пересмотреть план: сессия писала их до ответа, и опрос по ним ведёт задачу к цели, которой у пользователя уже нет. Пример — пилотный проект: ответ опроверг допущение о стране пользователя, а беседа задавала вопросы, стоявшие на нём. Беседа, которая показывает вопросы блокера по одному, следующего не задаёт: одной-двумя фразами называет, что ответ изменил и какие вопросы и части плана отпали, и одним вопросом предлагает пересмотр. Согласие — строка «ответ:» с номерами отпавших вопросов в начале, она закрывает их; «нет» — опрос идёт дальше. Новый план собирает сессия, которая переносит блокер в `DECISIONS.md`: план «Контекста» на время после ответа она выполняет, только когда ответ не задел его допущений, а новые вопросы пишет новым блокером.

Очередь шагов живёт только здесь, и шаги в неё добавляет только пользователь — сам или своим согласием на очередь, предложенную сессией в секции «Блокер»: такую очередь вписывает сессия, которая переносит блокер в `DECISIONS.md`, — слово в слово, а личные данные — обезличенным вариантом по § Личные данные и скрытые настройки. Размер шага — текст, который сессия прочитает ради него: файлы кода и документов шага вместе до 150 тыс. символов, счёт — `LC_ALL=C.UTF-8 wc -m <файлы>` (в локали C `wc -m` считает байты, и кириллица выходит вдвое); больше — шаг делится. Это около половины бюджета итерации до порога context-guard, остальное — обдумывание, правка и завершение. Сессия, увидевшая нужду в новом шаге, пишет предложение в хвосты «Контекста»; при перезаписи «Контекста» неразобранные предложения переносятся. Задачу заводит скилл `/box-task` или сессия по просьбе пользователя: таск-файл по шаблону выше и строка со ссылкой на него под своей вехой в `ROADMAP.md`. Черновик постановки начинается со слов пользователя — его просьба и его решения по теме из `DECISIONS.md`, дословно, с датой. Дописанное сессией — цель, шаги, рамки ресерча, которых в его словах нет, — отдельным списком «дописала сессия»: пункт — что и откуда. Проверка, которую пользователь берёт на себя, — «потом сам проверю», взгляд глазами, прогон вне контейнера, — шаг очереди: в цикле движка этот шаг кончается блокером, и «готово» задача получает после проверки пользователя; итог прогона, видный в файлах, сверяется по ним, а пользователь только делает шаги — абзац «Просьба сделать руками, итог которой виден в файлах» выше. Сообщений пользователю о новой задаче два, по § Сообщения пользователю: второе — после ответа на первое. Первое — о задаче. Его первая строка — один вопрос: выбор, которого из слов пользователя не вывести, а без такого выбора — заводить ли задачу, — и в той же строке за вопросом его решения по теме цитатой с датой; варианты — сразу под этой строкой. После вариантов — пункты «дописала сессия» обычными словами, фразой каждый, без вопроса; последняя строка — что будет после ответа: возражение против пункта уберёт пункт, следующим сообщением придёт вопрос о ресерче и проверке. Второе — предложения ресерча и проверки постановки и вопрос о них (§ Ресерч и проверка постановки); последняя строка — что будет после ответа: задача заведётся. Заготовку задачи — черновик целиком — пользователь видит только по просьбе. Ответ на первый вопрос — согласие на сказанное в первом сообщении, возражение против пункта убирает пункт; вопрос, который ответ на первое сообщение оставил открытым, — отдельным сообщением так же, до второго; запись — после ответа на последний. Состояние задачи живёт только в таск-файле; правила этого раздела в роадмап не дублируются.

## Ресерч и проверка постановки

Заводя задачу, сессия предлагает два этапа до основной работы: ресерч — как обычно делают дело этой задачи, где оно ломается и что из этого к месту здесь — и проверку постановки — сходятся ли задача и задумка со словами пользователя, его решениями и проектом. Предложения — во втором сообщении о новой задаче, после ответа на первое (§ Таск-файлы), каждое отдельным пунктом с фразой, что оно даст этой задаче. Под ними — вопрос с вариантами «оба», «только ресерч», «только проверка», «без них»; первым — тот, что сессия советует этой задаче. Этапы встают только по ответу на этот вопрос.

Выбранные — первыми этапами очереди, ресерч перед проверкой, по шаблону ниже слово в слово; за ними — абзац `Этап <N> — основная работа.` перед прежними шагами. Номера этапов — по порядку.

Ресерч и проверка предлагают правку задачи, только когда без неё задача хуже дойдёт до цели: что-то сломается, выйдет сложнее или дольше нужного. Практика ради самой практики, стиль и вкус правкой не становятся: тот, кого просят искать недочёты, находит их всегда, а правка каждого добавляет лишнее.

Правки задачи приходят пользователю один раз — блокером последнего из этих этапов: без проверки — блокером ресерча, с проверкой — её блокером, вместе с правками ресерча, которые она прошла. Правка — пунктом с номером: что изменится в задаче — одной фразой; кусок «Постановки» «сейчас» и «после»; зачем — находка проверки или практика ресерча с источником, у правки ресерча — итог её проверки. Правки одного места — одним пунктом. Тексты ресерча и проверки в блокер не идут: блокер называет их файлы. Ответ — «ответ: ок» на все правки или по номерам: «ответ: 1 ок, 2 нет, 3 — <свой вариант>». Принятые правки — шаги, цель и способ проверки тоже — вписывает слово в слово сессия, которая переносит блокер в `DECISIONS.md`. Правок нет — блокера нет: чекбокс шага, работа дальше.

Шаблон этапов: `<N>` — номер этапа, `<дата>` — день шага.

```text
Этап <N> — ресерч.

Шаг этапа называет одной фразой, что за дело делает задача, — например, «выгрузка таблицы в CSV», — и ищет, как такое дело обычно делают и где оно ломается: готовые решения и библиотеки, типовые ошибки, советы документации — поиск в интернете, документация инструментов проекта, прошлые ресерчи `docs/researches/` и решения пользователя в `docs/DECISIONS.md` grep-ом по словам темы — и по каждой находке решает, к месту ли она в этой задаче, по `docs/PROTOCOL.md` § Ресерч и проверка постановки. У каждого утверждения — источник: адрес страницы или файл; вывод по выдаче поиска без чтения страницы так и помечен; закрытая ограничением сети контейнера страница, от которой зависит вывод, — блокер по `docs/PROTOCOL.md` § Таск-файлы. Итог — `docs/researches/<дата>-<задача>.md`: практики и решение по каждой, в конце — правки задачи, у каждой «сейчас → после» и зачем, или вывод «по ресерчу нынешний план оптимален» с причиной. Дальше в очереди проверка постановки — чекбокс, правки возьмёт она; иначе правки — блокером по тому же разделу, без правок — чекбокс.

- [ ] Ресерч: как такое дело делают, где оно ломается и что из этого к месту здесь

Этап <N> — проверка постановки.

Шаг этапа сверяет задачу до начала работы: цель и шаги — со словами пользователя в «Постановке» и его решениями по теме в `docs/DECISIONS.md`; решение ведёт к цели; шаги вместе закрывают цель, каждый ей нужен, порядок выполним; проверка шага даёт однозначный итог; задуманное не спорит с `RULES.md`, `ARCHITECTURE.md` и файлами областей, чей код задача меняет, — `docs/architecture/<область>.md` и `docs/rules/<область>.md`; был ресерч — каждая его правка по тем же пунктам. Находка — по `docs/PROTOCOL.md` § Ресерч и проверка постановки. Итог — `docs/researches/<дата>-<задача>-check.md`: находки — где, что сломается, правка «сейчас → после»; правки ресерча — прошла ли каждая и почему. Находки и прошедшие правки ресерча — правками задачи блокером по тому же разделу; правок нет — чекбокс.

- [ ] Проверка постановки: цель, шаги, архитектура и правила проекта
```

## Статус «готово»

Все чекбоксы очереди закрыты: сессия ставит «готово», движок останавливает цикл и шлёт уведомление с именем задачи. Итог сессии на «готово» — сессии шага и оркестратора — одно последнее сообщение сессии. Оно несёт предложения сессий о новых шагах из хвостов «Контекста» самим текстом: на предложение — что сделать и что изменится для пользователя продукта, одна-две фразы. Ссылка на файл и прошлое сообщение их не заменяют: прошлое сообщение к концу сессии уходит выше окна терминала. Сделанное пользователь проверяет руками по записи журнала о задаче — в ней хэши всех её коммитов — и хвостам «Контекста» — там предложения сессий о новых шагах — или ревью: `/box-review <задача>` дописывает в очередь шаги ревью и возвращает задачу в цикл, находки шаг ревью приносит блокером с предложенными шагами правок; после ревью — QA, прогон в браузере глазами пользователя: `/box-qa <задача>` по согласию пользователя пишет сценарии в `docs/qa/<задача>.md` и дописывает в очередь шаги прогона, их цикл ведёт на хосте — `agent-loop.sh --host <задача>`, провалы шаг QA приносит блокером; после проверки ставит чекбокс строке задачи в `ROADMAP.md`. Из этого пути итог называет одно следующее действие пользователя и что оно даст, одной фразой, — по последней строке «Этап <N> — …» очереди: ревью — QA `/box-qa <задача>`, а у проекта без приложения в браузере — чекбокс строке задачи в `ROADMAP.md`; QA — чекбокс строке задачи в `ROADMAP.md`; иначе — проверка сделанного: ревью `/box-review <задача>` или руками по записи журнала. Статус «в работе», поставленный пользователем (с новыми шагами в очереди), возвращает задачу в цикл. Таск-файл остаётся в `docs/tasks/` навсегда со статусом «готово»: на старте его никто не читает, поиск по нему — grep, как по `DONE.md`.

## Протокол закрытия вехи

Веха закрыта, когда у всех её задач в роадмапе стоит чекбокс проверки. Закрытие выполняет интерактивная сессия по команде пользователя («закрой веху X»): чекбокс в «Вехах» → карточка вехи в `DONE.md` → завершение шагами 1, 2, 4, 5: коммит, затем запись в `JOURNAL.md` с его хэшем. В роадмапе от закрытой вехи остаётся строка со ссылкой.

## Порядок на месте

Порядок поддерживается правилами записи в момент появления данных, без отдельной уборочной сессии:

- **у факта один дом.** Перед записью — поиск существующей записи о том же; найдена → обновляется она, второе место ссылается на первое.
- **раздел по областям.** Архитектура и правила, разделённые по областям кода, — папки `docs/architecture/` и `docs/rules/`: факт и конвенция кода одной области — в файл области, общее — в основной файл. Документ одним файлом, после записи сессии больше порога — ключ `split_chars` конфига agent-box, без файла или ключа 50 000 знаков, счёт `LC_ALL=C.UTF-8 wc -m <файл>`, — сессия пишет в хвосты «Контекста» предложение раздела: повторный `/box-init` заводит задачу сборки документации с шагами раздела. Конфиг — в контейнере `/etc/claude-box/config.yml`, на хосте `config.yml` в папке, куда ведёт команда `agent-loop.sh`: `readlink -f "$(command -v agent-loop.sh)"`.
