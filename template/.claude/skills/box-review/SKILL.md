Текущий каталог — корень проекта. Задача — `$ARGUMENTS`; пусто — первый вопрос пользователю: какая задача.

1. **Проверки.** Нет `docs/PROTOCOL.md` или `docs/tasks/` — назвать это и закончить без правок: проект подключается к agent-box командой `box-connect` в терминале компьютера в папке проекта, затем `/box-init`. Коммит в конце забирает всё рабочее дерево, поэтому на старте оно чистое: `git status --porcelain` непуст — перечислить правки и закончить без правок. Нет таск-файла `docs/tasks/<задача>.md` или статус в его первой строке не «готово» — назвать это и закончить без правок: ревью идёт по сделанной задаче.

2. **Коммиты задачи** — все, от первого: `git log --reverse --format='%h %s' --grep '<задача>'`; коммит, где имя задачи — часть имени другой задачи или слово в другом смысле, — не её.

3. **Деление.** Объём шага ревью — изменения его коммитов, «Постановка» таск-файла и файлы областей его коммитов вместе. Таск-файл, журнал и реестр шаг читает в нынешнем виде, поэтому их изменения в счёт не идут; ресерчи задачи в `docs/researches/` — путь к решению, а не её результат, и в ревью не идут. Из таск-файла шаг читает «Постановку» — цель и критерии шагов. `ARCHITECTURE.md` шаг читает нужными разделами, вне счёта. Файлы областей шага — при разделе по областям: области из § Области в `ARCHITECTURE.md`, чьи папки кода меняют коммиты шага, их файлы — `docs/architecture/<область>.md` и `docs/rules/<область>.md`, какие есть. Счёт группы коммитов — `{ git show --format= <хэши> -- . ':!docs/tasks/<задача>.md' ':!docs/JOURNAL.md' ':!docs/DECISIONS.md' ':!docs/researches'; sed -n '/^## Постановка/,/^## Контекст/p' docs/tasks/<задача>.md; cat /dev/null <файлы областей группы>; } | LC_ALL=C.UTF-8 wc -m` — у группы без файлов областей `cat` читает один `/dev/null`; норма — размер шага из `docs/PROTOCOL.md` § Таск-файлы без 3 тыс. знаков: столько займёт в таск-файле этап ревью. Все коммиты в норме — один шаг. Больше — коммиты делятся на группы подряд, каждая в норме; коммит больше нормы — шаг сам по себе.

4. **Запись.** Этап ревью — в конец очереди «Постановки», после её последнего чекбокса, по шаблону ниже. Номер этапа — следующий за последней строкой «Этап <N> — …» в «Постановке»; таких строк нет — перед первым чекбоксом очереди встаёт абзац `Этап 1 — основная работа.`, и ревью — этап 2. Номер ревью — следующий за последней строкой «Этап <N> — ревью <K>.», без таких строк — 1. Первая строка таск-файла — `статус: в работе`. «Контекст» перезаписывается: следующий шаг — первый шаг этапа ревью; неразобранные предложения прежнего «Контекста» переносятся.

5. **Завершение** — `docs/PROTOCOL.md` § Протокол сессии, «Завершение», шаги 1, 2, 4; таск-файл — коммитом с именем задачи в сообщении: его хэш войдёт в следующую запись журнала о задаче.

6. **Итог пользователю:** этап ревью — сколько в нём частей и по скольким коммитам; дальше — запуск в Claude `/box-next <задача>`, в терминале хоста из папки проекта `agent-loop.sh <задача>` или в Claude на компьютере, запущенном в папке проекта, `/box-orchestrate <задача>` — оркестратор ведёт цикл сам и вопросы ревью приносит в беседу. Шаг ревью с находками кончается вопросом: находки и предложенные шаги правок, ответ — «ок» или свой вариант строкой «ответ:»; оркестратор показывает находки в беседе по одной; шаги правок цикл ведёт как обычные. Без находок задача снова получает «готово».

Шаблон этапа ревью: абзац ревью — один на этап, шаг — строка части; частей одна — строка шага `- [ ] Ревью: коммиты <хэши>`; `<хэши>` — коммиты части через запятую:

```text
Этап <N> — ревью <K>.

Шаг этапа — часть ревью задачи по своим коммитам: изменения — `git show <хэши шага> -- . ':!docs/tasks/<задача>.md' ':!docs/JOURNAL.md' ':!docs/DECISIONS.md' ':!docs/researches'` — сверяются с целью задачи и критериями её шагов из «Постановки» таск-файла в нынешнем виде, ответами пользователя по задаче (`` grep -E 'задача: `?<задача>`?[;,]' docs/DECISIONS.md | grep -v 'ответ: оркестратор' ``), `RULES.md`, нужными разделами `ARCHITECTURE.md`, при разделе по областям — и с файлами областей, чей код меняют коммиты шага: `docs/architecture/<область>.md` и `docs/rules/<область>.md`, области — § Области в `ARCHITECTURE.md`, — и проверяются на ошибки — логика, краевые случаи, безопасность; другие коммиты и файлы проекта читаются по нужде; находка до записи сверяется с нынешним видом файла — исправленное позже другим коммитом задачи не находка; сомнительная находка перепроверяется чтением кода или запуском до записи; находка, отклонённая пользователем в `docs/DECISIONS.md`, повторно не предлагается. Простота — по результату: после правки код не сложнее, чем нужно задаче, — без обходов, лишних слоёв, опций на вырост и обработки случаев, которых в задаче нет. Случай из задачи, который код не обрабатывает, — находка. Сложность решения задачи, которую можно убрать, — тоже находка. Когда простой результат требует переделки базового кода — ошибки устройства с самого начала, — вариантов два: переделка — её объём в шагах и что станет проще; запасная правка на месте — что она оставляет сложным. Рекомендация — один из двух. Находки — в секцию «Блокер» со статусом «блокер»: у каждой номер, что сломается, где, как чинить; под ними предложенные шаги правок — номера находок, что делается, чем проверяется, какие файлы читает, размер шага по `docs/PROTOCOL.md` § Таск-файлы, мелкие находки — одним шагом; у находки с двумя вариантами — шаги каждого, ответ «ок» берёт рекомендованный. По согласию пользователя шаги правок слово в слово, личные данные — обезличенным вариантом, вписывает в «Постановку» сразу после шага ревью сессия, свой вариант — пользователь; чекбокс шага ревью ставит сессия, увидевшая шаги там. Находок нет — чекбокс ставится сразу.

- [ ] Часть 1 из <M>: коммиты <хэши>
- [ ] Часть 2 из <M>: коммиты <хэши>
```
