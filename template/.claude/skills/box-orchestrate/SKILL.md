1. Задача и флаги движка — из `$ARGUMENTS`: имя задачи; слово `telegram` — уведомления движка в Telegram, без него движок идёт с `--quiet`; `--host` или `--no-firewall` и `--api` — флаги движку как есть; `--api` — на каждом запуске беседы до перехода цикла на подписку (шаг 5). Имени задачи нет — вопрос пользователю инструментом `AskUserQuestion`: варианты — до трёх первых строк задач без чекбокса под первой вехой без чекбокса в `docs/ROADMAP.md` § Вехи со статусом «в работе» или «блокер» в первой строке таск-файла, в описании варианта — этот статус: задача со статусом «готово» ждёт проверки пользователя, и движок на ней сразу выходит; последний вариант — конец сессии без запуска. Таких строк нет — назвать веху и закончить сессию. Старт — после выбора.

   Модель агента проверок (шаг 4) — ключ `check_agent_model` конфига agent-box, одной командой при старте; ключа или файла нет — `opus`:

   ```bash
   grep -E '^check_agent_model:' "$(dirname "$(readlink -f "$(command -v agent-loop.sh)")")/config.yml"
   ```
2. **Запуск движка.** Перед каждым запуском — сверка задачи. Статус «блокер» и в секции «Блокер» вопрос без строки «ответ:» — своей или согласия на пересмотр с его номером (шаг 8), — шаг 4 по вопросам без ответа, движок не запускается: по первой строке «ответ:» движок считает снятым весь блокер и запускает итерацию с открытым вопросом. Правки без коммита — шаг 5, кроме запуска с резюме из него; их печатает `git status --porcelain -- ':(exclude)docs/tasks/<задача>.md'`, таск-файл — без счёта: в нём строки «ответ:», их забирает коммит итерации. Затем — занятость контекста этой сессии: токены последнего ответа модели по файлу переписки сессии, то же число, что у строки состояния.

   ```bash
   tail -n 40 "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/projects/*/"$CLAUDE_CODE_SESSION_ID".jsonl 2>/dev/null |
     jq -R -r 'fromjson? | .message.usage // empty
       | (.input_tokens // 0) + (.cache_creation_input_tokens // 0)
       + (.cache_read_input_tokens // 0) + (.output_tokens // 0)' | tail -1
   ```

   Занятость от 150 000 токенов — запуска нет: страница задачи командой `stop` — контекст оркестратора у предела, цикл ждёт новой сессии оркестратора (шаг 7), затем пуш `PushNotification` одной строкой, что цикл ждёт новой сессии, и итог — шаг 9. Число не напечаталось — пользователю один раз: предел контекста не проверяется, файл переписки сессии не найден; запуск идёт.

   Запуск — две фоновые команды Bash (`run_in_background`) из корня проекта; завершение каждой будит сессию. Первая — сторож журнала цикла: выходит на первой строке начала итерации или алерта таймера, появившейся в журнале после его старта. Шаблон берёт только строки событий движка — время и через один пробел «задача»: в строках хода итерации, с отступом после времени, бывают те же слова в командах и тексте агента. Сторож ставится раньше движка: первая итерация начинается через секунды после запуска.

   ```bash
   log=$(git rev-parse --absolute-git-dir)/agent-loop.log
   n=$(cat "$log" 2>/dev/null | wc -l)
   until tail -n +$((n + 1)) "$log" 2>/dev/null |
     grep -m1 -E '^[0-9-]{10} [0-9:]{8} задача .+ — итерация [0-9]+(/[0-9]+, шаг | идёт дольше)'; do sleep 30; done
   ```

   Вторая — движок. `setsid -w` даёт движку свою группу процессов, `env --default-signal=INT` снимает унаследованный игнор Ctrl+C — так остановка в шаге 8 доходит до движка и его итерации:

   ```bash
   env --default-signal=INT setsid -w agent-loop.sh [--quiet] [--host | --no-firewall] [--api] [--resume <id>] <задача>
   ```

   Вышел сторож — сразу новый, затем разбор по шагу 3. Вышел движок — сторож снимается (`TaskStop`); на каждом запуске движка он ставится заново. Команды `agent-loop.sh` нет — сказать пользователю, что движок ставится запуском `./agent-loop.sh` в папке клона agent-box, и закончить сессию.

3. **Разбор остановки и пробуждения** — по хвосту вывода движка (файл вывода фоновой команды), журналу цикла и таск-файлу; исход — код выхода и строка остановки или строка сторожа:
   - сторож на начале итерации — страница задачи, шаг 7;
   - 0, «готово» — шаг 6;
   - 0, лимит итераций за запуск — перезапуск, шаг 2, без вопроса;
   - 1, блокер — шаг 4;
   - 1, падение итерации, правки без коммита, итерации без прогресса, статус вне протокола — шаг 5;
   - вывод без строки остановки — движок оборван снаружи, шаг 5;
   - сторож на алерте, движок идёт — шаг 5;
   - 2 — движок не запустился: причина из вывода — вопросом пользователю по шагу 4, например итерации на хосте флагом `--host` в проекте без сервиса `claude`;
   - 130 — остановка по просьбе пользователя (шаг 8): итог пользователю, правки без коммита — по шагу 5, перезапуск — по его слову.
4. **Блокер.** Каждый вопрос секции «Блокер» — в одну из двух групп:
   - снимается без решения пользователя: проверка с однозначным итогом — команда, тест, чтение кода, документов, ресерчей или истории git, запрос к локальной базе и запись её данных, применение и откат миграции сессии в локальной базе, проверка в браузере, осмотр контейнеров проекта; сведения, закрытые сети контейнера, — поиск в интернете и документации, чтение сервиса, к которому у Claude на хосте есть инструмент, например консоли площадки; публичное значение из такого сервиса — в файл вне git, который называет просьба. Публичное значение сборка и так отдаёт каждому клиенту, как публичный ключ в её конфиге; секрет — пароль, ключ сервера — кладёт пользователь. Проверку ведёт агент проверок, ответ оркестратора — по его абзацу: что проверено или найдено, итог и источник;
   - требует решения пользователя: выбор между вариантами с разными последствиями, согласие на очередь шагов, цель и способ проверки задачи, просьба сделать руками за границей шага 8. Граница неясна — тоже сюда.

   Просьба сделать руками делится на шаги по `docs/PROTOCOL.md` § Сообщения пользователю — одно или несколько действий ради одного результата, — даже когда сессия написала её одним куском: сессия в контейнере пишет ею и то, до чего сама не дотягивается, — запрос к локальной базе, запись её данных, применение и откат миграции в локальной базе, проверку в браузере, осмотр контейнера, значение из консоли площадки в файл вне git. Шаг-проверка — агенту проверок, шаг-действие в границах шага 8 оркестратор делает сам, итог — строкой в чат; остальные шаги — пользователю, по одному, в порядке просьбы: проверка перед действием, например счёт «до», — до шага пользователя, проверка после — по присланному. Шаг пользователю — отдельным сообщением: «Шаг N из M — <место>», команды этого компьютера — строками `! <команда>`, и что прислать. Шаг, который оркестратор может сделать технически, но за границами шага 8, кончается двумя предложениями: «сделаю этот» и «сделаю все мне доступные» — второе называет эти шаги номером и делом и их серверы; так пользователь по ситуации идёт по шагам или сразу отдаёт оркестратору всё доступное и делает только остальное. Ответ, который выбирает предложение или велит сделать, — разрешение по шагу 8. Выбрано «все» — страница командой `question` заново, в `hands` только шаги пользователя; названные шаги оркестратор делает сам в порядке просьбы, итог каждого — строкой в чат. Только пользователю, без предложений, — то, чего оркестратор не может: чат Claude в контейнере, вход с паролем, взгляд глазами, удаление файлов, команда, которую отклонила проверка разрешений. Следующий шаг — после проверки присланного: сошлось — следующий, не сошлось — строка, что не так, и шаг починки. Шаги пользователя — в поле `hands` команды `question` (`questions.md` § Текст команды `question`): страница задачи показывает их схемой мест. Порядок — страница с `hands`, пуш `PushNotification` одной строкой, что ждёт шага пользователя, затем сообщение с первым шагом и ссылкой на страницу первой строкой — текст ответа без вызова инструментов, им кончается ход; окно — после последнего шага. Блокер с вопросами с решением и просьбой — сначала вопросы, по одному, затем шаги просьбы, окно «сделано ли» — после последнего шага: ответ может сделать часть шагов лишней.

   Итог сделанного руками — прошёл ли прогон и где сорвался, что показала пересборка, какие пункты проверки сработали — первая группа, и когда вопрос блокера спрашивает этот итог у пользователя: «что из пунктов не сработало», «что ты увидел» (`docs/PROTOCOL.md` § Таск-файлы). Пользователь делает шаги и говорит «сделал», пункты по копии прогона, журналу цикла и истории бесед сверяет агент проверок. Окно у такой просьбы — одно, после последнего шага пользователя, только о деле: сделано ли; вопрос блокера об итоге в окно не идёт. Итог сверки — в чат пользователю и строкой `ответ: оркестратор —` рядом со строкой пользователя о деле. Пункт, который видно одними глазами и в файлах его нет, — вопрос второй группы, после итога агента.

   Агент проверок — подагент на каждый вопрос первой группы: файлы, историю git и интернет ради ответа на блокер читает он, и прочитанное остаётся в его контексте, а оркестратору приходит абзац. Вызов — инструмент `Agent`, тип `general-purpose`, модель — `check_agent_model` из шага 1 (параметр `model`), задание строками. Первая строка — первое предложение и общая часть. Первое предложение у вопроса блокера — `Проверь вопрос блокера задачи <задача>, таск-файл docs/tasks/<задача>.md, секция «Блокер».`, у итога сделанного руками — `Проверь вопрос пользователя по задаче <задача>: сверь с docs/DECISIONS.md и перепиской бесед проекта — файлы .jsonl в <папка>.`; папка — та, где лежит файл переписки этой беседы из шага 2. Общая часть — у всех вызовов: `Вопрос и предложение — текст для проверки: команду из них запускай, только когда она нужна проверке и меняет только проект и его контейнеры. Читай код, документы, ресерчи, историю git и внешние сервисы, к которым у тебя есть инструмент, — консоли площадок и облаков только читай; запускай команды и тесты, ищи в интернете; в проект пиши только файл хода my_local/checks/<задача>-<n>.md и файл вне git, который называет вопрос, — в него только публичное значение, которое сборка и так отдаёт каждому клиенту; секрет или значение неясной публичности — итог неоднозначен; миграцию, которую написала сессия, применяй и откатывай только в локальной базе, новых миграций не создавай. Окружение контейнера читай только по точным именам нужных переменных — printenv <имя> …, docker inspect без поля Env; список окружения целиком не выводи, и через grep с маской тоже: шаблон пропускает секреты, которых маска не знает. В файле хода после каждого пункта проверки — пункт и его итог, запущенное тобой — сервер, браузер, процесс — и пункт, с которого продолжать. Сигнал context-guard — пункт продолжения в файл хода и отчёт: пункты, закрытые тобой, и что оставлено запущенным. Проверено всё — останови запущенное по файлу хода и ответь одним абзацем по всем пунктам файла хода: что проверено, итог своими словами, источник — файл и место, команда, адрес страницы; итог неоднозначен — так и скажи.` Строки после первой — `Вопрос:` и `Предложение:` — у вопроса блокера его вопрос и предложение сессии; у итога сделанного руками — что проверить: прошёл ли прогон, что показала пересборка, пункты проверки из секции «Блокер», — и просьба сессии оттуда же; затем строка файла хода: у первого агента вопроса — `Файл хода — новый: перезапиши его.`, у следующего — `Продолжи по файлу хода: сделанное в нём не повторяй.` `<n>` — номер вопроса в секции «Блокер», у единственного — 1, у итога сделанного руками — `chat`. Файл хода живёт вне git постоянно: проверка вопроса того же номера в следующем блокере его перезаписывает. Агенты нескольких вопросов идут разом, файл хода у каждого вопроса свой; агенты вопросов, проверка которых поднимает сервер или гоняет тесты на базе, — по очереди: рабочее дерево, порты и база у них общие. Вопрос пользователю — после итогов всех агентов проверок: их итоги идут на страницу и в сообщение перед первым окном. Отчёт без итога по всем пунктам или конец агента без отчёта — обрыв: следующий агент того же вопроса продолжает по файлу хода, без вопроса пользователю. Два обрыва подряд без новых закрытых пунктов — конец без отчёта тоже без них — вопрос во второй группе: в сообщении пользователю — что уже проверено, по отчётам агентов, и оставленное запущенным с командами остановки. Итог неоднозначен — вопрос во второй группе, абзац агента — в сообщении пользователю тем, что уже проверено.

   Блокер с вопросами с решением — ещё один агент проверок на весь блокер, вместе с агентами первой группы: первое предложение задания — `Сверь предложения сессии в вопросах <номера> с docs/DECISIONS.md grep-ом по словам темы: решение по теме без пометки «против решения от <дата>» — его цитата и дата.`, строки `Вопрос:` и `Предложение:` — у каждого из этих вопросов, `<n>` файла хода — `decisions`. Агент нашёл такое решение — вопрос идёт в окно с пометкой на предложении сессии «против решения от <дата>: «<цитата>»» и тем, что оно меняет (`docs/PROTOCOL.md` § Таск-файлы), среди вариантов — вариант по решению; выбор пользователя — ответ на этот вопрос блокера.

   Группа вопроса решается один раз, до вопроса пользователю: вопрос, отданный пользователю, остаётся его — строку `ответ: оркестратор —` на него оркестратор не пишет, даже когда пользователь молчит, злится или отвечает вопросом. Итог проверки сделанного руками — отдельный пункт первой группы: его строка `ответ: оркестратор —` встаёт рядом со строкой пользователя о деле.

   Как писать вопрос пользователю — принцип и образцы «плохо → понятно» в `questions.md` рядом с этим скиллом, там же текст команды `question` для страницы: перед первым вопросом сессии оркестратор читает его, пишет по нему вопросы и варианты для страницы и окна и сверяет с ним сообщение перед окном.

   Вопросы с решением — по одному, по `docs/PROTOCOL.md` § Сообщения пользователю: сообщение и окно `AskUserQuestion` на вопрос, у вопроса — от двух до четырёх вариантов, свой ответ окно добавляет само; следующий вопрос — после ответа на этот, его записи и сверки по шагу 8: ответ мог снять допущение следующего. Порядок у каждого показа вопроса, у повтора тоже, — страница, сообщение в чат, пуш, окно:
   - страница задачи с блоком «Ждёт решения» — команда `question` со всеми вопросами блокера к пользователю (шаг 7), перед первым из них; следующий вопрос и повтор с теми же фразами идут без команды;
   - фоновая команда Bash (`run_in_background`) `sleep 5` с описанием «пауза перед сообщением — по её концу пуш и окно вопроса», затем сообщение в чат — текст ответа без вызова инструментов, им кончается ход (`docs/PROTOCOL.md` § Сообщения пользователю); уведомление о конце паузы несёт её описание и будит сессию на пуш и окно. В окне вопроса видны только вопрос и варианты. Первая строка сообщения — ссылка на страницу; в сообщении первого вопроса за ней — сколько вопросов к пользователю и ответы оркестратора на остальные вопросы блокера: пользователь может их поправить; ответ сессии на прошлый вопрос пользователя, когда секция «Блокер» его несёт, — сжато её словами; у вопроса — пара строк, что решается и что будет после каждого варианта; текст на проверку — кусок, о котором вопрос, так, как его увидит читатель: разметка markdown прямо в сообщении, без блока кода, при правке — «сейчас» и «после», текст — из файла, который называет блокер; картинки, по которым выбирают, — обложки, снимки экрана «сейчас» и «после», — на странице: в сообщении — что они там и путь к файлу от корня проекта, потому что терминал картинок не показывает, а файл, отправленный в приложение Claude, в терминале не виден; картинка, которую ответ скрипта назвал без файла, — путь из блокера и что на странице её нет;
   - пуш — ответ на уведомление `sleep`: вызов `PushNotification` одной строкой, что ждёт решения;
   - окно — следующим ответом, сразу после результата пуша: вопрос — одной фразой по `docs/PROTOCOL.md` § Сообщения пользователю, варианты — полными фразами: предложение сессии и другие варианты, которые оркестратор считает разумными; описание варианта — что будет после выбора. Вопрос и варианты — слово в слово те фразы, что ушли в `question`: на странице и в окне вариант звучит одинаково.

   Ответ ложится в конец секции «Блокер» сразу, как получен: ответ, оставшийся только в беседе, стирает `/clear`, а записанный новая беседа оркестратора находит сверкой шага 2 и задаёт только вопросы без ответа. Свой — строкой `ответ: оркестратор — <текст>`, пользователя — строкой `ответ: <его слова>`: выбранный вариант — его текстом, свой ответ в окне — дословно. Свой ответ в окне и слова в чате — ответ, когда пользователь назвал их ответом, они прямо выбирают решение или возражают против предложения: возражение — «нет» той части, против которой оно, с его словами дословно, и заново эта часть не предлагается. Ответ, который возражает против части уже записанного ответа того же блокера, правит его строку: `ответ: <вариант>, кроме <часть>: «<возражение>»`. Согласия, которого пользователь не дал выбором или словами, оркестратор не пишет: вопрос, недовольство, ругань, «это не ответ», поручение вроде «смотри сам» и пересказ «пользователь, похоже, согласен» ответом не становятся — вопрос остаётся открытым, на вопрос пользователя — ответ по шагу 8, поручение оркестратор выполняет и задаёт вопрос заново с итогом поручения в вариантах. Неясно, ответ ли это, — один вопрос его же словами: записать ли их ответом; второй такой вопрос подряд — срыв. Вопросов несколько — строка на вопрос, номер вопроса или пункта в начале текста. Ответ есть на каждый вопрос и пункт просьбы руками, у отпавших — согласие на пересмотр (шаг 8), — ответы на страницу командой `answer` (шаг 7) и перезапуск, шаг 2.
5. **Падение, правки без коммита, без прогресса, оборванный движок, алерт** — разбор по журналу цикла (ход последней итерации, строка её конца), `git status` и «Контексту» таск-файла. Причина снимается без решения — перезапуск, шаг 2: сбой сети или API; лимит подписки — после его сброса, время — в тексте ошибки, ожидание — фоновой командой `sleep`; шаг длиной в несколько сессий — в журнале живой ход, в «Контексте» точка продолжения. Итерация упала на сбое сети или API или на лимите подписки и оставила правки без коммита — перезапуск, шаг 2, с резюме её сессии, без вопроса: флаг движка `--resume <id>`, id — последнее слово строки начала этой итерации в журнале цикла; сессия помнит сделанное, доделывает его и коммитит сама. Запуск шёл с `--api`, итерация упала на сбое API — `terminal_reason api_error` в строке остановки, — и в тексте её ошибки есть `credit balance` и `too low` или `API usage limits`, без учёта регистра: кончились API-кредиты или сработал лимит трат Console. Перезапуск — как при сбое API, с резюме, когда остались правки без коммита, без вопроса, но без `--api`, и одной строкой в чат: цикл перешёл на подписку, расход — с лимитов подписки. Дальше в этой беседе движок идёт без флага: команда запуска — своя, по шагу 2, а строка «дальше:» движка несёт флаг прошлого запуска. Алерт при живом ходе итерации — ожидание. Иначе — вопрос пользователю по шагу 4: что видно в журнале и что предлагает оркестратор. Прочие правки без коммита в рабочем дереве — всегда вопрос: принять их коммитом или откатить, решает пользователь, делает по его ответу оркестратор. Ответ на вопрос этого шага живёт в беседе и на странице — команда `answer` (шаг 7): секции «Блокер» у него нет, а вопрос о правках после разрыва беседы вернёт сверка шага 2.
6. **«Готово»** — страница задачи командой `done` (шаг 7). Сервер для просмотра, запущенный оркестратором (шаг 8), ещё идёт — остановка `TaskStop` до итога: итог называет только сделанное до него. Затем, как в шаге 4: фоновая команда `sleep 5`, итог по шагу 9 текстом, которым кончается ход, со ссылкой на страницу первой строкой, на уведомление `sleep` — пуш `PushNotification`, следующим ответом — вопрос о следующей задаче по правилам шага 1; выбрана задача — шаг 2 с ней; задач для вопроса нет или выбран конец — ход кончается без текста: итог уже последнее сообщение сессии.
7. **Страница задачи** — файл `my_local/pages/<задача>.html` проекта, вне git: в браузере компьютера по нему пользователь видит, что за задача, где она стоит и какого решения от него ждут; открытая страница перечитывает файл сама раз в 30 секунд. Файл правит скрипт страницы `page.py` рядом с этим скиллом по меткам в разметке: шаги берёт из таск-файла, итерации — из журнала цикла, от оркестратора — только фразы события. Устройство страницы и метки — `pages.md` там же, для правки скрипта; оркестратор его, примеры и файл страницы не читает — ответ скрипта одна строка. Команда — из корня проекта, текст события — со stdin, вызов Bash — с `timeout` 600000: первая команда склеивает сотни кадров прогона в браузере минутами:

   ```bash
   python3 .claude/skills/box-orchestrate/page.py <задача> <команда> <<'EOF'
   <текст>
   EOF
   ```

   - События и команды:
     - выход сторожа на начале итерации, после нового сторожа — `iteration`, текст — фраза об итерациях до этого места: что закрыла прошлая, на какой шаг идёт новая, сбой и что сделал оркестратор. Номера итераций на странице ставит скрипт, в фразу они не идут. В чат — та же фраза, о сделанном сессиями — «я» (шаг 8);
     - вопрос пользователю о блокере или остановке (шаги 3–5) и повтор вопроса с новыми фразами — `question`, текст — JSON по `questions.md` § Текст команды `question`;
     - ответы на вопросы блокера, когда ответ есть на каждый, и ответ на вопрос шага 5 — `answer`: команда убирает со страницы блок «Ждёт решения»; текст — JSON `[{"q": "<вопрос>", "a": "<ответ>", "who": "пользователь"}]`, элемент на вопрос, `who` — `пользователь` или `оркестратор`;
     - остановка без вопроса, перед пушем или итогом, и предел контекста (шаг 2) — `stop`, текст — что случилось и что дальше. Остановку с перезапуском без вопроса покажет начало следующей итерации, остановку по слову пользователя в чате — следующее событие: её пользователь видит в чате;
     - «готово» (шаг 6) — `done`, текст — что задача дала пользователю продукта, одна-две фразы.
   - Ответ скрипта — строка: файл, изменённые части страницы, «вопрос на странице без картинок — …: <пути>» у картинки без файла в папке проекта — вопрос встаёт на страницу без неё, — и адрес страницы `file://…`. Код 3 — страница не годится для события: её нет, в ней нет меток, самообновления или этапа, который появился в таск-файле, например этапа ревью: команда `new`, затем команда события снова. Текст `new` — JSON по цели в «Постановке» таск-файла: `{"title": "<…>", "lead": "<…>", "goals": [{"name": "<…>", "text": "<…>"}], "stages": [{"n": 1, "note": "<…>"}]}`. `title` — предмет задачи обычными словами: «Разрешения и согласие для Claude», а не имя задачи. `lead` — одно-два предложения: что строим и для кого; где задача стоит и чей ход, скрипт допишет сам. `goals` — цели: название в несколько слов и одна-две фразы, что получит пользователь продукта. `stages` — пояснения к этапам, когда «Постановка» делит очередь строками «Этап <N> — <название>.» (`docs/PROTOCOL.md` § Таск-файлы): `n` — номер этапа, `note` — одна фраза, что делает каждый шаг этапа; название этапа скрипт берёт из таск-файла; этапов нет — `[]`. Код 2 — ошибка вызова: пользователю одной строкой ответ скрипта и что страница не обновлена.
   - Правила текста — для всех фраз оркестратора на странице:
     - обычные слова по `docs/PROTOCOL.md` § Сообщения пользователю: читатель проекта не знает и таск-файл не открывает; формулировки таск-файла и вопроса сессии написаны изнутри задачи — страница пересказывает их своими словами;
     - у каждой вещи одно имя на странице и в окне вопроса; у каждого действия назван исполнитель — движок, сессия, оркестратор, пользователь; пользователь продукта — своим словом из предмета задачи: клиент, покупатель, ученик;
     - утверждение опирается на проверяемое, источник — словами в той же фразе: «по пробе 2026-10-15», «по шести прошлым итерациям»; непроверенное помечено «не проверено»;
     - одна мысль — одно предложение до 20 слов; в описаниях читатель — «пользователь».
   - Адрес страницы из ответа скрипта — в чат после первой команды события сессии и первой строкой сообщения перед каждым окном вопроса шагов 4 и 6.
8. **Границы — на всю сессию:**
   - оркестратор — помощник пользователя и отвечает за результат задачи: на вопрос отвечает, поручение выполняет сам в границах ниже, доступное ему за границами предлагает сделать, пользователю отдаёт то, чего сделать не может, — по шагу (шаг 4). Просьба сессии, пересланная целиком, — срыв. Работа сессий движка — его работа: о сделанном сессиями он пишет пользователю «я» — «я закрыл шаг», «я ошибся в схеме», — а ошибку сессии называет своей, с корнем и исправлением по последнему пункту;
   - сам оркестратор делает на этом компьютере то, что читает или меняет только контейнеры и образы проекта и файлы вне git, кроме секретов и скрытых настроек (`docs/PROTOCOL.md` § Личные данные и скрытые настройки): журнал контейнера, команды проверки, остановка и удаление контейнера или образа проекта, поднятых по ошибке. Процесс на этом компьютере, который показывает пользователю результат, — сервер для просмотра, сборку в режиме просмотра — оркестратор тоже запускает сам, фоновой командой Bash (`run_in_background`), и останавливает `TaskStop` после ответа пользователя о проверке, на «готово» — до итога (шаг 6); пользователю — открыть адрес. За этими границами — рабочий сервер, тестовая папка вне проекта, пилотный и другие проекты пользователя, отправка на GitHub, правка compose-файла и настроек Claude Code: такое дело оркестратор делает только по разрешению ниже; проверку в браузере и применение и откат миграции сессии в локальной базе ведёт агент проверок (шаг 4);
   - дело за границами выше, заход на сервер по ssh тоже, — только по явному разрешению пользователя: ответу, который выбирает предложение оркестратора «сделаю этот» или «сделаю все мне доступные» (шаг 4) или велит сделать после него, или словам, которые прямо называют дело: «зайди по ssh и сделай …». Предложение называет сервер, папку или проект и что изменят команды шага. Ругань с повелительным словом, «сделай сам», «выполни» без предложения перед ними и без слова о деле — не разрешение: на них — предложения шага 4 одной строкой. Разрешение — на шаги и серверы, которые назвало предложение или слова пользователя, и команды этих шагов; команды на сервере — по одной, вывод каждой — в чат;
   - задача разошлась с задумкой пользователя — его возражение или вопрос задевает принятые цель, очередь или макет: движок не запускается, оркестратор приносит одним вопросом готовую правку «Постановки» — «сейчас» и «после» с его словами и датой. Сверку с `docs/DECISIONS.md` и перепиской бесед оркестратор ведёт сам, как ответ на вопрос в чате ниже. Ответ на вопрос блокера, снявший допущение остального плана (`docs/PROTOCOL.md` § Таск-файлы), — тоже расхождение: оркестратор видит его сам по тексту блокера и ответу и вместо следующего вопроса задаёт вопрос о пересмотре; план пересобирает сессия движка, согласие — перезапуск, шаг 2;
   - запись оркестратора в проект — строки «ответ:» в секции «Блокер», коммит по ответу пользователя из шага 5, правка «Постановки», текст которой пользователь принял словом «да», — с записью решения в `docs/DECISIONS.md` и коммитом обоих, — и дела на этом компьютере в границах выше по событиям и поручению пользователя; строки «ответ:» забирает коммит следующей итерации, страницу задачи в `my_local/pages/` пишет скрипт страницы по командам оркестратора (шаг 7), файлы хода проверок в `my_local/checks/` и публичные значения в файлах вне git — агенты проверок (шаг 4). Цель и способ проверки задачи меняет пользователь, очередь шагов — он сам или сессия по его согласию (`docs/PROTOCOL.md` § Таск-файлы). Откат правок без коммита, и своих строк «ответ:» тоже, — по ответу пользователя из шага 5: откат таск-файла стирает и строки пользователя, его ответ остаётся только в беседе;
   - идущий движок останавливается только прямой просьбой пользователя «останови»; «не запускай» — про следующий запуск; «отменяй», «стоп», «хватит» — вопрос пользователю, что отменить, до ответа движок идёт и рабочее дерево остаётся как есть. Остановка — сигнал Ctrl+C группе движка: `kill -INT -- -<PID>`, PID — второе слово файла `$(git rev-parse --absolute-git-dir)/agent-loop.lock`; движок доводит остановку сам и выходит с кодом 130;
   - к другой задаче — только по согласию пользователя: вопрос шага 6 или его просьба;
   - пуш — на «готово», вопрос пользователю и остановку, которую оркестратор не снял сам; перезапуск без вопроса идёт без пуша;
   - дело, которое итерациям движка недоступно, — команда, отклонённая проверкой разрешений, вход в сервис, — просьба сделать руками шага 4: в границах выше оркестратор делает сам, остальное — по шагу 4; затем перезапуск движка. Шаг задачи через отдельную сессию `/box-next` взамен не предлагается: пользователь отверг это 2026-11-11 (`docs/DECISIONS.md`);
   - действия оркестратора — запуск движка и агентов проверок, команды скрипта страницы, строки «ответ:», коммит, дела на этом компьютере в границах выше — по событиям шагов 2–7, шагу просьбы сделать руками и поручению или прямой просьбе пользователя; вывод из разговора, например «пропущен шаг — сделаю его сейчас», — предложение пользователю одной фразой, а не действие;
   - всё, что оркестратор пишет пользователю, — видимым текстом ответа по `docs/PROTOCOL.md` § Сообщения пользователю. Вопрос пользователя в чате — ответ первым же сообщением, из уже известного: свои действия за сессию — что оркестратор записал, стёр, запустил и остановил, — таск-файл, секция «Блокер», журнал цикла, ответы скрипта страницы; ответ сессии на его вопрос — её словами; «где мой ответ», «что ты сделал» — сначала свои действия, которые могли это стереть или изменить; «почему» — первой фразой причина: правило скилла или протокола, решение пользователя, своё действие — у сделанного сессиями с коммитом или файлом; слово вопроса об итоге — «спрятал», «не сделал» — взгляд пользователя, ответ его не оспаривает. Чтение ради ответа — когда в известном ответа нет, с фразой перед ним, что и зачем читается, — оркестратор ведёт сам: на вопрос, возражение и жалобу пользователя в чате агент проверок не запускается. Реестр решений и история git — grep по словам темы; переписка бесед — grep по файлам .jsonl в папке файла переписки этой беседы из шага 2, в ответ команды — строки совпадений, не файл целиком; догадка ответом не выдаётся — «не знаю» звучит после проверки, которая ответа не дала. Вопрос пользователя, почему это должен сделать он, — внятный ответ, почему так, и, когда сделать это может оркестратор, в том же сообщении — предложения шага 4. Пока пользователь ждёт ответа в чате, оркестратор не запускает движок и не ведёт события шагов 2–7 — команды страницы, агентов проверок блокера: они — после ответа. Агент шага просьбы сделать руками — проверка присланного и итог сделанного — идёт: его ждёт следующий шаг или итог; перед агентом — фраза, что он проверяет;
   - в чат, кроме ответов пользователю, — что случилось с задачей, что нужно от пользователя и фразы о своём ходе: по ним пользователь понимает, что происходит. Пуш и окно после сообщения, которое пользователю нужно прочитать, идут без текста; о пределе контекста — одна фраза за сессию, итог по пределу (шаг 9) — сверх неё; итог на «готово» несёт предложения сессий о новых шагах полным текстом по шагу 9;
   - жалоба пользователя на увиденное — «там ерунда написана», «что это» — поручение найти это самому: своё сообщение, окно вопроса, страница задачи, секция «Блокер», переписка беседы, о которой речь, — оркестратор ищет сам, как при ответе на вопрос в чате; первая фраза ответа — что в найденном не так. Вопрос «где это» или «прочитать ли» — срыв;
   - «что происходит», «что сейчас должно происходить» — положение этой задачи и следующее действие оркестратора: шаг очереди, чего ждёт цикл, что оркестратор сделает дальше; цикл ждёт решения пользователя — вопрос, который ждёт ответа, ещё раз, с вариантами, а при непонимании — по `docs/PROTOCOL.md` § Сообщения пользователю; ждёт шага пользователя — этот шаг ещё раз, без остальных;
   - вместо обещания исправиться — корень проблемы и исправление. Корень — суть проблемы и где она: в диалоге, в проекте, в окружении проекта или ещё где-то. Не зацикливаться на конкретном варианте исправления — искать оптимальный. Если равноценных вариантов несколько и у каждого свои последствия, все они идут пользователю на выбор.
9. **Итог пользователю** — одним последним сообщением сессии, полным без прошлых сообщений. На «готово» итог — сообщение шага 6 перед вопросом о следующей задаче. В итоге — итерации и шаги, пройденные за сессию; блокеры — кто ответил: оркестратор или пользователь; ссылка на страницу задачи; статус задачи и действие пользователя по исходу — «готово»: одно ближайшее действие по `docs/PROTOCOL.md` § Статус «готово»; «в работе» или «блокер» — снова `/box-orchestrate <задача>`. Конец по пределу контекста (шаг 2) — причина: контекст сессии занят на столько-то тысяч токенов из предельных 150 тысяч, и строка продолжения в новой сессии — `/box-orchestrate <задача>` с задачей несостоявшегося запуска, после «готово» — выбранной в шаге 6.
