1. Задача и флаги движка — из `$ARGUMENTS`: имя задачи; слово `telegram` — уведомления движка в Telegram, без него движок идёт с `--quiet`; `--host` или `--no-firewall` — флаг движку как есть. Имени задачи нет — вопрос пользователю инструментом `AskUserQuestion`: варианты — до трёх первых строк задач без чекбокса под первой вехой без чекбокса в `docs/ROADMAP.md` § Вехи, в описании варианта — статус из первой строки таск-файла; последний вариант — конец сессии без запуска. Таких строк нет — назвать веху и закончить сессию. Старт — после выбора.

   Модель агента проверок (шаг 4) — ключ `check_agent_model` конфига agent-box, одной командой при старте; ключа или файла нет — `opus`:

   ```bash
   grep -E '^check_agent_model:' "$(dirname "$(readlink -f "$(command -v agent-loop.sh)")")/config.yml"
   ```
2. **Запуск движка.** Перед каждым запуском — занятость контекста этой сессии: токены последнего ответа модели по файлу переписки сессии, то же число, что у строки состояния.

   ```bash
   tail -n 40 "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/projects/*/"$CLAUDE_CODE_SESSION_ID".jsonl 2>/dev/null |
     jq -R -r 'fromjson? | .message.usage // empty
       | (.input_tokens // 0) + (.cache_creation_input_tokens // 0)
       + (.cache_read_input_tokens // 0) + (.output_tokens // 0)' | tail -1
   ```

   Занятость от 150 000 токенов — запуска нет: страница задачи командой `stop` — контекст оркестратора у предела, цикл ждёт новой сессии оркестратора (шаг 7), затем пуш `PushNotification` одной строкой, что цикл ждёт новой сессии, и итог — шаг 9. Число не напечаталось — пользователю один раз: предел контекста не проверяется, файл переписки сессии не найден; запуск идёт.

   Запуск — две фоновые команды Bash (`run_in_background`) из корня проекта; завершение каждой будит сессию. Первая — сторож журнала цикла: выходит на первой строке начала итерации или алерта таймера, появившейся в журнале после его старта. Шаблон берёт только строки событий движка — время и через один пробел «задача»: в строках хода итерации, с отступом после времени, бывают те же слова в командах и тексте агента. Сторож ставится раньше движка: первая итерация начинается через секунды после запуска.

   ```bash
   log=$(git rev-parse --absolute-git-dir)/agent-loop.log
   n=$(cat "$log" 2>/dev/null | wc -l)
   until tail -n +$((n + 1)) "$log" 2>/dev/null |
     grep -m1 -E '^[0-9-]{10} [0-9:]{8} задача .+ — итерация [0-9]+(/[0-9]+, шаг | идёт дольше)'; do sleep 30; done
   ```

   Вторая — движок. `setsid -w` даёт движку свою группу процессов, `env --default-signal=INT` снимает унаследованный игнор Ctrl+C — так остановка в шаге 8 доходит до движка и его итерации:

   ```bash
   env --default-signal=INT setsid -w agent-loop.sh [--quiet] [--host | --no-firewall] <задача>
   ```

   Вышел сторож — сразу новый, затем разбор по шагу 3. Вышел движок — сторож снимается (`TaskStop`); на каждом запуске движка он ставится заново. Команды `agent-loop.sh` нет — сказать пользователю, что движок ставится запуском `./agent-loop.sh` в папке клона agent-box, и закончить сессию.

3. **Разбор остановки и пробуждения** — по хвосту вывода движка (файл вывода фоновой команды), журналу цикла и таск-файлу; исход — код выхода и строка остановки или строка сторожа:
   - сторож на начале итерации — страница задачи, шаг 7;
   - 0, «готово» — шаг 6;
   - 0, лимит итераций за запуск — перезапуск, шаг 2, без вопроса;
   - 1, блокер — шаг 4;
   - 1, падение итерации, правки без коммита, итерации без прогресса, статус вне протокола — шаг 5;
   - вывод без строки остановки — движок оборван снаружи, шаг 5;
   - сторож на алерте, движок идёт — шаг 5;
   - 2 — движок не запустился: причина из вывода — вопросом пользователю по шагу 4, например итерации на хосте флагом `--host` в проекте без сервиса `claude`;
   - 130 — остановка по просьбе пользователя (шаг 8): итог пользователю, правки без коммита — по шагу 5, перезапуск — по его слову.
4. **Блокер.** Каждый вопрос секции «Блокер» — в одну из двух групп:
   - снимается без решения пользователя: проверка с однозначным итогом — команда, тест, чтение кода, документов, ресерчей или истории git, запрос на чтение к локальной базе, осмотр контейнеров проекта; сведения, закрытые сети контейнера, — поиск в интернете и документации. Проверку ведёт агент проверок, ответ оркестратора — по его абзацу: что проверено или найдено, итог и источник;
   - требует решения пользователя: выбор между вариантами с разными последствиями, согласие на очередь шагов, цель и способ проверки задачи, просьба сделать руками — миграция и другая запись в локальную базу, правка compose-файла или настроек Claude Code, пересборка, вход в сервис, живой прогон. Граница неясна — тоже сюда.

   Просьба сделать руками делится по пунктам: сессия в контейнере пишет ею и проверку, до которой сама не дотягивается, — запрос к локальной базе, осмотр контейнера. Пункт-проверка — агенту проверок, пункт-действие — пользователю, в порядке просьбы: проверка перед действием, например счёт «до», — до вопроса пользователю, проверка после действия — по его «сделал».

   Итог сделанного руками — прошёл ли прогон и где сорвался, что показала пересборка — первая группа: пользователь делает и говорит «сделал», итог по истории беседы, журналу и файлам проверяет агент проверок. Окно у такой просьбы — только о деле: сделано ли; итог проверки — в чат пользователю и строкой `ответ: оркестратор —` рядом со строкой пользователя о деле.

   Агент проверок — подагент на каждый вопрос первой группы: файлы, историю git и интернет ради ответа на блокер читает он, и прочитанное остаётся в его контексте, а оркестратору приходит абзац. Вызов — инструмент `Agent`, тип `general-purpose`, модель — `check_agent_model` из шага 1 (параметр `model`), задание строками: `Проверь вопрос блокера задачи <задача>, таск-файл docs/tasks/<задача>.md, секция «Блокер». Читай код, документы, ресерчи, историю git, запускай команды и тесты, ищи в интернете; в проект не пиши, миграций не запускай, к локальной базе — только запросы на чтение. Ответь одним абзацем: что проверено, итог своими словами, источник — файл и место, команда, адрес страницы; итог неоднозначен — так и скажи.`, `Вопрос: <вопрос из секции «Блокер»>`, `Предложение сессии: <её предложение>`. Агенты нескольких вопросов идут разом — в проект они не пишут. Вопрос пользователю — после отчётов всех агентов проверок: их итоги идут на страницу и в сообщение перед окном. Итог неоднозначен или агент упал — вопрос во второй группе, абзац агента — в сообщении пользователю тем, что уже проверено.

   Группа вопроса решается один раз, до вопроса пользователю: вопрос, отданный пользователю, остаётся его — строку `ответ: оркестратор —` на него оркестратор не пишет, даже когда пользователь молчит, злится или отвечает вопросом.

   Вопрос пользователю — выбор между тем, что будет дальше для него: что он увидит, что сделает Claude, что придётся сделать ему самому. Слова протокола — шаг, задача, веха, итерация, блокер — идут в вопрос как есть, в смысле `docs/PROTOCOL.md`: своё слово взамен пользователь переспрашивает. Шаг называется своим названием из очереди в кавычках, новый шаг — тем, что он сделает; номера шагов и итераций и «n из m» в вопрос не идут. Внутренние условия проверки шага — «засчитать проверку», пределы и числа критерия — звучат в вопросе тем, что будет дальше для пользователя. Образцы «плохо → понятно» — `questions.md` рядом с этим скиллом: перед первым вопросом сессии оркестратор читает их, пишет по ним вопросы и варианты для страницы и окна и сверяет с ними сообщение перед окном.

   Вопросы с решением — одним вызовом `AskUserQuestion`: до четырёх вопросов, у вопроса — от двух до четырёх вариантов, свой ответ окно добавляет само; больше четырёх вопросов — вызовами подряд. Порядок у каждого показа вопроса, у повтора тоже, — страница, сообщение в чат, пуш, окно:
   - страница задачи с блоком «Ждёт решения» — команда `question` и публикация (шаг 7); повтор с теми же фразами идёт без команды и публикации;
   - фоновая команда Bash (`run_in_background`) `sleep 5`, затем сообщение в чат — текст ответа без вызова инструментов, им кончается ход. Текст ответа с вызовом инструмента сразу после результата другого инструмента Claude Code в половине случаев показывает свёрнутыми размышлениями, а текст, которым кончается ход, — всегда видимым; уведомление `sleep` будит сессию на пуш и окно. В окне вопроса видны только вопрос и варианты, а текст из него не копируется. Первая строка сообщения — ссылка на страницу; ответ сессии на прошлый вопрос пользователя, когда секция «Блокер» его несёт, — сжато её словами; у каждого вопроса — пара строк, что решается и что будет после каждого варианта; текст на проверку — кусок, о котором вопрос, так, как его увидит читатель: разметка markdown прямо в сообщении, без блока кода, при правке — «сейчас» и «после», текст — из файла, который называет блокер; ответы оркестратора на остальные вопросы — пользователь может их поправить; просьба сделать руками с готовыми командами;
   - пуш — ответ на уведомление `sleep`: вызов `PushNotification` одной строкой, что ждёт решения;
   - окно — следующим ответом, сразу после результата пуша: вопрос — одной фразой по `docs/PROTOCOL.md` § Сообщения пользователю, варианты — полными фразами: предложение сессии и другие варианты, которые оркестратор считает разумными; описание варианта — что будет после выбора. Вопрос и варианты — слово в слово те фразы, что ушли в `question`: на странице и в окне вариант звучит одинаково.

   Ответы ложатся в конец секции «Блокер», когда ответ есть на каждый вопрос: свой — строкой `ответ: оркестратор — <текст>`, пользователя — строкой `ответ: <его слова>`: выбранный вариант — его текстом, свой ответ в окне — дословно. Свой ответ в окне и слова в чате — ответ, когда пользователь назвал их ответом или они прямо выбирают решение; вопрос, недовольство, ругань, «это не ответ» и поручение оркестратору вроде «смотри сам» ответом не становятся ни в окне, ни в чате, пересказ «пользователь, похоже, согласен» — тоже: вопрос остаётся открытым, на вопрос пользователя — ответ по шагу 8, поручение оркестратор выполняет, итог показывает в чате и задаёт вопрос заново — с итогом поручения рекомендованным вариантом. Неясно, ответ ли это, — вопрос пользователю его же словами: записать ли их ответом. Вопросов несколько — строка на вопрос, номер вопроса в начале текста. Записанные ответы — на страницу командой `answer` (шаг 7). Затем перезапуск — шаг 2.
5. **Падение, правки без коммита, без прогресса, оборванный движок, алерт** — разбор по журналу цикла (ход последней итерации, строка её конца), `git status` и «Контексту» таск-файла. Причина снимается без решения — перезапуск, шаг 2: сбой сети или API; лимит подписки — после его сброса, время — в тексте ошибки, ожидание — фоновой командой `sleep`; шаг длиной в несколько сессий — в журнале живой ход, в «Контексте» точка продолжения. Алерт при живом ходе итерации — ожидание. Иначе — вопрос пользователю по шагу 4: что видно в журнале и что предлагает оркестратор. Правки без коммита в рабочем дереве — всегда вопрос: принять их коммитом или откатить, решает пользователь, делает по его ответу оркестратор.
6. **«Готово»** — страница задачи командой `done` и публикация (шаг 7), затем, как в шаге 4: фоновая команда `sleep 5`, сообщение в чат текстом, которым кончается ход, со ссылкой на страницу первой строкой, на уведомление `sleep` — пуш `PushNotification`, следующим ответом — вопрос о следующей задаче по правилам шага 1; выбрана задача — шаг 2 с ней, конец — шаг 9.
7. **Страница задачи** — приватная страница claude.ai: по ней пользователь с телефона или компьютера видит, что за задача, где она стоит и какого решения от него ждут. Файл страницы — `my_local/pages/<задача>.html` проекта, вне git; его правит скрипт страницы `page.py` рядом с этим скиллом по меткам в разметке: шаги берёт из таск-файла, итерации — из журнала цикла, от оркестратора — только фразы события. Устройство страницы и метки — `pages.md` там же, для правки скрипта; оркестратор его, примеры и файл страницы не читает — ответ скрипта одна строка. Публикует страницу оркестратор. Команда — из корня проекта, текст события — со stdin:

   ```bash
   python3 .claude/skills/box-orchestrate/page.py <задача> <команда> <<'EOF'
   <текст>
   EOF
   ```

   - События и команды:
     - выход сторожа, после нового сторожа — `iteration`, текст — фраза об итерациях до этого места: что закрыла прошлая, на какой шаг идёт новая, сбой и что сделал оркестратор. Шаги — названиями из очереди в кавычках, без номеров итераций: номера на странице ставит скрипт. Та же фраза — в чат;
     - вопрос пользователю о блокере или остановке (шаги 3–5) и повтор вопроса с новыми фразами — `question`, текст — JSON `{"answered": ["<…>"], "questions": [{"n": 2, "q": "<…>", "about": "<…>", "options": [{"title": "<…>", "text": "<…>"}], "rec": "<…>"}]}`. `answered` — вопросы блокера, на которые оркестратор ответил сам, строкой на вопрос: номер, ответ, на чём он основан и что пользователь может поправить его в чате. `n` — номер вопроса в секции «Блокер», у единственного вопроса его нет. `q` — вопрос одной фразой. `about` — что происходит, 3–5 предложений: с самой проблемы, а не с шага, — что случилось, почему это плохо и что зависит от ответа; пустая строка — граница абзаца. `options` — от двух до четырёх, столько же в окне: `title` — буква и фраза о том, что изменится, «Б — Период до трёх месяцев», `text` — одна-две фразы: что будет и чем за это платить; вариант, который оркестратор сам считает бессмысленным, не идёт ни на страницу, ни в окно. `rec` — вариант и причина; причины не хватает — «рекомендации нет» и почему;
     - ответы, записанные в секцию «Блокер», — `answer`, текст — JSON `[{"q": "<вопрос>", "a": "<ответ>", "who": "пользователь"}]`, элемент на вопрос, `who` — `пользователь` или `оркестратор`. Публикация — когда за ответами нет перезапуска: с перезапуском страницу с ответом опубликует начало следующей итерации;
     - остановка без вопроса, перед пушем или итогом, и предел контекста (шаг 2) — `stop`, текст — что случилось и что дальше. Остановку с перезапуском без вопроса покажет начало следующей итерации, остановку по слову пользователя в чате — следующее событие: её пользователь видит в чате;
     - «готово» (шаг 6) — `done`, текст — что задача дала пользователю продукта, одна-две фразы.
   - Ответ скрипта — строка: файл, изменённые части страницы и адрес из `my_local/pages/links.md` или «адреса нет — первая публикация». Код 3 — страницы нет, в ней нет меток или нет этапа, который появился в таск-файле, например этапа ревью: команда `new`, затем команда события снова. Текст `new` — JSON по цели в «Постановке» таск-файла: `{"title": "<…>", "lead": "<…>", "goals": [{"name": "<…>", "text": "<…>"}], "stages": [{"n": 1, "note": "<…>"}]}`. `title` — предмет задачи обычными словами: «Разрешения и согласие для Claude», а не имя задачи. `lead` — одно-два предложения: что строим и для кого; где задача стоит и чей ход, скрипт допишет сам. `goals` — цели: название в несколько слов и одна-две фразы, что получит пользователь продукта. `stages` — пояснения к этапам, когда «Постановка» делит очередь строками «Этап <N> — <название>.» (`docs/PROTOCOL.md` § Таск-файлы): `n` — номер этапа, `note` — одна фраза, что делает каждый шаг этапа; название этапа скрипт берёт из таск-файла; этапов нет — `[]`. Код 2 — ошибка вызова: пользователю одной строкой ответ скрипта и что страница не обновлена.
   - Правила текста — для всех фраз оркестратора на странице:
     - обычные слова по `docs/PROTOCOL.md` § Сообщения пользователю: читатель проекта не знает и таск-файл не открывает; слово проекта при первом упоминании объясняется тем, что происходит; формулировки таск-файла и вопроса сессии написаны изнутри задачи — страница пересказывает их своими словами;
     - у каждой вещи одно имя на странице и в окне вопроса; у каждого действия назван исполнитель — движок, сессия, оркестратор, пользователь; пользователь продукта — своим словом из предмета задачи: клиент, покупатель, ученик;
     - утверждение опирается на проверяемое, источник — словами в той же фразе: «по пробе 2026-10-15», «по шести прошлым итерациям»; непроверенное помечено «не проверено»;
     - одна мысль — одно предложение до 20 слов; к читателю — на «ты», в описаниях он — «пользователь».
   - Публикация — следующим вызовом после каждой команды события, кроме `answer` с перезапуском: инструмент `Artifact` с путём файла страницы. Уведомление о конце движка или сторожа, пришедшее после команды события, разбирается после публикации: страница, отложенная ради разбора, ждёт следующего события, и ссылка приходит в чат на минуты позже. `Artifact` среди инструментов беседы — публикация сразу им; он назван только в списке отложенных инструментов — сначала загрузка `ToolSearch` запросом `select:Artifact`, один раз за беседу: загрузка инструмента, который у беседы уже есть, кладёт его описание в контекст второй раз — около 12 тыс. токенов. Адрес — из ответа скрипта:
     - адрес есть — публикация с ним в `url`: правится та же страница, и открытая у пользователя страница обновляется сама;
     - «адреса нет — первая публикация» — без `url`, с `icon` и `description` одной фразой о задаче; адрес из ответа инструмента — командой `link`: `python3 .claude/skills/box-orchestrate/page.py <задача> link <адрес>`;
     - инструмент ответил, что ссылка на страницу потеряна, — публикация без `url`, новый адрес — командой `link`; в чат — новая ссылка и что прежняя больше не открывается;
     - отказ «не видел живую версию» — та же публикация ещё раз, без изменений: содержимое, сверенное с живой версией, проходит повтором; вызовов публикации на событие — до трёх;
     - страница не опубликована — пользователю один раз: причина и путь к файлу страницы; инструмента `Artifact` нет и через `ToolSearch` — страница живёт только файлом.
   - Ссылка на страницу — в чат на первом адресе сессии, на новой ссылке и первой строкой сообщения перед каждым окном вопроса шагов 4 и 6.
8. **Границы — на всю сессию:**
   - запись оркестратора в проект — строки «ответ:» в секции «Блокер» и коммит по ответу пользователя из шага 5; строки «ответ:» забирает коммит следующей итерации, страницу задачи и список адресов в `my_local/pages/` пишет скрипт страницы по командам оркестратора (шаг 7). Цель и способ проверки задачи меняет пользователь, очередь шагов — он сам или сессия по его согласию (`docs/PROTOCOL.md` § Таск-файлы). Откат правок без коммита, и своих строк «ответ:» тоже, — по ответу пользователя из шага 5: откат таск-файла стирает и строки пользователя, его ответ остаётся только в беседе;
   - идущий движок останавливается только прямой просьбой пользователя «останови»; «не запускай» — про следующий запуск; «отменяй», «стоп», «хватит» — вопрос пользователю, что отменить, до ответа движок идёт и рабочее дерево остаётся как есть. Остановка — сигнал Ctrl+C группе движка: `kill -INT -- -<PID>`, PID — второе слово файла `$(git rev-parse --absolute-git-dir)/agent-loop.lock`; движок доводит остановку сам и выходит с кодом 130;
   - к другой задаче — только по согласию пользователя: вопрос шага 6 или его просьба;
   - пуш — на «готово», вопрос пользователю и остановку, которую оркестратор не снял сам; перезапуск без вопроса идёт без пуша;
   - действия оркестратора — запуск движка и агентов проверок, команды скрипта страницы и публикация, строки «ответ:», коммит — по событиям шагов 2–7 и прямой просьбе пользователя; вывод из разговора, например «пропущен шаг — сделаю его сейчас», — предложение пользователю одной фразой, а не действие;
   - всё, что оркестратор пишет пользователю, — видимым текстом ответа по `docs/PROTOCOL.md` § Сообщения пользователю: размышления Claude Code в чате сворачивает, и слова для пользователя в них он не видит. Вопрос пользователя в чате — ответ первым же сообщением, из уже известного: свои действия за сессию — что оркестратор записал, стёр, запустил и остановил, — таск-файл, секция «Блокер», журнал цикла, ответы скрипта страницы; ответ сессии на его вопрос — её словами; «где мой ответ», «что ты сделал» — сначала свои действия, которые могли это стереть или изменить. Чтение файла ради ответа — когда в известном ответа нет, с фразой перед ним, что и зачем читается; догадка ответом не выдаётся — чего оркестратор не знает, так и говорит. Пока пользователь ждёт ответа в чате, оркестратор не запускает ни агентов, ни движка: события этого времени — после ответа;
   - «что происходит», «что сейчас должно происходить» — положение этой задачи и следующее действие оркестратора: шаг очереди, движок идёт или стоит и почему, чего ждёт цикл, что оркестратор сделает дальше; цикл ждёт решения пользователя — вопрос ещё раз целиком, с вариантами;
   - ругань и упрёки — ответ по делу: на вопрос из реплики или положение задачи; упрёк без вопроса — сверка своих действий за сессию с этим скиллом: нарушение — одной фразой, что сделано и что от этого изменилось у пользователя, например «твой ответ стёрт откатом, он есть только в беседе», и что предлагает оркестратор по правилу нарушенного шага; извинения, оценки себя и обещания исправиться в ответ не идут.
