Шаги идут без остановок; блокер, снимаемый проверкой или сведениями вне сети контейнера, оркестратор снимает своим ответом по итогу подагента проверок; вопрос с решением — пользователю окном вопроса и пушем; ход задачи — на её приватной странице claude.ai, её ведёт подагент. Вызов /box-orchestrate <задача> [telegram] [--host | --no-firewall]; без задачи — выбор задачи первой незакрытой вехи роадмапа.

1. Задача и флаги движка — из `$ARGUMENTS`: имя задачи; слово `telegram` — уведомления движка в Telegram, без него движок идёт с `--quiet`; `--host` или `--no-firewall` — флаг движку как есть. Имени задачи нет — вопрос пользователю инструментом `AskUserQuestion`: варианты — до трёх первых строк задач без чекбокса под первой вехой без чекбокса в `docs/ROADMAP.md` § Вехи, в описании варианта — статус из первой строки таск-файла; последний вариант — конец сессии без запуска. Таких строк нет — назвать веху и закончить сессию. Старт — после выбора.
2. **Запуск движка.** Перед каждым запуском — занятость контекста этой сессии: токены последнего ответа модели по файлу переписки сессии, то же число, что у строки состояния.

   ```bash
   tail -n 40 "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/projects/*/"$CLAUDE_CODE_SESSION_ID".jsonl 2>/dev/null |
     jq -R -r 'fromjson? | .message.usage // empty
       | (.input_tokens // 0) + (.cache_creation_input_tokens // 0)
       + (.cache_read_input_tokens // 0) + (.output_tokens // 0)' | tail -1
   ```

   Занятость от 150 000 токенов — запуска нет: страница задачи событием `предел` (шаг 7), после ответа агента страницы — пуш `PushNotification` одной строкой, что цикл ждёт новой сессии, и итог — шаг 9. Число не напечаталось — пользователю один раз: предел контекста не проверяется, файл переписки сессии не найден; запуск идёт.

   Запуск — две фоновые команды Bash (`run_in_background`) из корня проекта; завершение каждой будит сессию. Первая — сторож журнала цикла: выходит на первой строке начала итерации или алерта таймера, появившейся в журнале после его старта. Шаблон берёт только строки событий движка — время и через один пробел «задача»: в строках хода итерации, с отступом после времени, бывают те же слова в командах и тексте агента. Сторож ставится раньше движка: первая итерация начинается через секунды после запуска.

   ```bash
   log=$(git rev-parse --absolute-git-dir)/agent-loop.log
   n=$(cat "$log" 2>/dev/null | wc -l)
   until tail -n +$((n + 1)) "$log" 2>/dev/null |
     grep -m1 -E '^[0-9-]{10} [0-9:]{8} задача .+ — итерация [0-9]+(/[0-9]+, шаг | идёт дольше)'; do sleep 30; done
   ```

   Вторая — движок. `setsid -w` даёт движку свою группу процессов, `env --default-signal=INT` снимает унаследованный игнор Ctrl+C — так остановка в шаге 8 доходит до движка и его итерации:

   ```bash
   env --default-signal=INT setsid -w agent-loop.sh [--quiet] [--host | --no-firewall] <задача>
   ```

   Вышел сторож — сразу новый, затем разбор по шагу 3. Вышел движок — сторож снимается (`TaskStop`); на каждом запуске движка он ставится заново. Команды `agent-loop.sh` нет — сказать пользователю, что движок ставится запуском `./agent-loop.sh` в папке клона agent-box, и закончить сессию.

3. **Разбор остановки и пробуждения** — по хвосту вывода движка (файл вывода фоновой команды), журналу цикла и таск-файлу; исход — код выхода и строка остановки или строка сторожа:
   - сторож на начале итерации — страница задачи, шаг 7;
   - 0, «готово» — шаг 6;
   - 0, лимит итераций за запуск — перезапуск, шаг 2, без вопроса;
   - 1, блокер — шаг 4;
   - 1, падение итерации, правки без коммита, итерации без прогресса, статус вне протокола — шаг 5;
   - вывод без строки остановки — движок оборван снаружи, шаг 5;
   - сторож на алерте, движок идёт — шаг 5;
   - 2 — движок не запустился: причина из вывода — вопросом пользователю по шагу 4, например итерации на хосте флагом `--host` в проекте без сервиса `claude`;
   - 130 — остановка по просьбе пользователя (шаг 8): итог пользователю, правки без коммита — по шагу 5, перезапуск — по его слову.
4. **Блокер.** Каждый вопрос секции «Блокер» — в одну из двух групп:
   - снимается без решения пользователя: проверка с однозначным итогом — команда, тест, чтение кода, документов, ресерчей или истории git; сведения, закрытые сети контейнера, — поиск в интернете и документации. Проверку ведёт агент проверок, ответ оркестратора — по его абзацу: что проверено или найдено, итог и источник;
   - требует решения пользователя: выбор между вариантами с разными последствиями, согласие на очередь шагов, цель и способ проверки задачи, просьба сделать руками — правка compose-файла или настроек Claude Code, пересборка, вход в сервис, живой прогон. Граница неясна — тоже сюда.

   Итог сделанного руками — прошёл ли прогон и где сорвался, что показала пересборка — первая группа: пользователь делает и говорит «сделал», итог по истории беседы, журналу и файлам проверяет агент проверок. Окно у такой просьбы — только о деле: сделано ли; итог проверки — в чат пользователю и строкой `ответ: оркестратор —` рядом со строкой пользователя о деле.

   Агент проверок — подагент на каждый вопрос первой группы: файлы, историю git и интернет ради ответа на блокер читает он, и прочитанное остаётся в его контексте, а оркестратору приходит абзац. Вызов — инструмент `Agent`, тип `general-purpose`, модель `opus` (параметр `model`), задание строками: `Проверь вопрос блокера задачи <задача>, таск-файл docs/tasks/<задача>.md, секция «Блокер». Читай код, документы, ресерчи, историю git, запускай команды и тесты, ищи в интернете; в проект не пиши. Ответь одним абзацем: что проверено, итог своими словами, источник — файл и место, команда, адрес страницы; итог неоднозначен — так и скажи.`, `Вопрос: <вопрос из секции «Блокер»>`, `Предложение сессии: <её предложение>`. Агенты нескольких вопросов идут разом — в проект они не пишут. Вопрос пользователю — после уведомлений о конце всех агентов проверок: их итоги идут на страницу и в сообщение перед окном. Итог неоднозначен или агент упал — вопрос во второй группе, абзац агента — в сообщении пользователю тем, что уже проверено.

   Группа вопроса решается один раз, до вопроса пользователю: вопрос, отданный пользователю, остаётся его — строку `ответ: оркестратор —` на него оркестратор не пишет, даже когда пользователь молчит, злится или отвечает вопросом.

   Вопросы с решением — одним вызовом `AskUserQuestion`: до четырёх вопросов, у вопроса — от двух до четырёх вариантов, свой ответ окно добавляет само; больше четырёх вопросов — вызовами подряд. Порядок — страница, пуш, сообщение в чат, окно:
   - страница задачи с блоком «Ждёт решения» — событие `вопрос` (шаг 7);
   - после ответа агента страницы — пуш `PushNotification` одной строкой, что ждёт решения;
   - сообщение в чат — до окна: в окне вопроса видны только вопрос и варианты, а текст из него не копируется. В сообщении — ссылка на страницу из ответа агента; ответ сессии на прошлый вопрос пользователя, когда секция «Блокер» его несёт, — сжато её словами; у каждого вопроса — пара строк, что решается и что будет после каждого варианта; текст на проверку — кусок, о котором вопрос, так, как его увидит читатель: разметка markdown прямо в сообщении, без блока кода, при правке — «сейчас» и «после», текст — из файла, который называет блокер; ответы оркестратора на остальные вопросы — пользователь может их поправить; просьба сделать руками с готовыми командами;
   - окно: вопрос — одной фразой по `docs/PROTOCOL.md` § Сообщения пользователю, словами того, что увидит пользователь продукта, а не словами постановки и проверки шага. Число, предел, условие — с тем, что оно значит и что от него меняется: условие проверки шага так и называется, с тем, что будет после «засчитать» и «не засчитать». Варианты — полными фразами, слово в слово как в задании агенту страницы: предложение сессии и другие варианты, которые оркестратор считает разумными; описание варианта — что будет после выбора.

   Ответы ложатся в конец секции «Блокер», когда ответ есть на каждый вопрос: свой — строкой `ответ: оркестратор — <текст>`, пользователя — строкой `ответ: <его слова>`: выбранный вариант — его текстом, свой ответ в окне — дословно. Свой ответ в окне и слова в чате — ответ, когда пользователь назвал их ответом или они прямо выбирают решение; вопрос, недовольство, ругань, «это не ответ» и поручение оркестратору вроде «смотри сам» ответом не становятся ни в окне, ни в чате, пересказ «пользователь, похоже, согласен» — тоже: вопрос остаётся открытым, на вопрос пользователя — ответ по шагу 8, поручение оркестратор выполняет, итог показывает в чате и задаёт вопрос заново — с итогом поручения рекомендованным вариантом. Неясно, ответ ли это, — вопрос пользователю его же словами: записать ли их ответом. Вопросов несколько — строка на вопрос, номер вопроса в начале текста. Затем перезапуск — шаг 2.
5. **Падение, правки без коммита, без прогресса, оборванный движок, алерт** — разбор по журналу цикла (ход последней итерации, строка её конца), `git status` и «Контексту» таск-файла. Причина снимается без решения — перезапуск, шаг 2: сбой сети или API; лимит подписки — после его сброса, время — в тексте ошибки, ожидание — фоновой командой `sleep`; шаг длиной в несколько сессий — в журнале живой ход, в «Контексте» точка продолжения. Алерт при живом ходе итерации — ожидание. Иначе — вопрос пользователю по шагу 4: что видно в журнале и что предлагает оркестратор. Правки без коммита в рабочем дереве — всегда вопрос: принять их коммитом или откатить, решает пользователь, делает по его ответу оркестратор.
6. **«Готово»** — страница задачи событием `готово` (шаг 7), после ответа агента страницы — пуш `PushNotification` и вопрос о следующей задаче по правилам шага 1; выбрана задача — шаг 2 с ней, конец — шаг 9.
7. **Страница задачи** — приватная страница claude.ai по правилам `pages.md` рядом с этим скиллом; её ведёт агент страницы — подагент по инструкции `page-agent.md` там же. Правила страниц, примеры и файл страницы читает, правит, проверяет и публикует агент, ответ оркестратору — одна строка: файл страницы и ответы публикации остаются в контексте агента. Оркестратор этих файлов не читает и инструмент `Artifact` не загружает.
   - События агенту: `итерация` — на каждом выходе сторожа, после нового сторожа; `вопрос` — перед вопросом пользователю о блокере или остановке (шаги 3–5); `ответ` — ответы пользователя, за которыми нет перезапуска; `остановка` — остановка без вопроса, перед пушем или итогом; `готово` — шаг 6; `предел` — шаг 2. Остановку с перезапуском без вопроса покажет начало следующей итерации, остановку по слову пользователя в чате — следующее событие: её пользователь видит в чате. Данные события — по `page-agent.md` § События: агенту нужно только то, чего нет в файлах проекта, — ответы оркестратора, ещё не записанные в таск-файл, открытый вопрос с вариантами и рекомендацией, причина остановки.
   - Вызов — инструмент `Agent`, тип `general-purpose`, модель `sonnet` (параметр `model`), задание строками: `Прочитай инструкцию .claude/skills/box-orchestrate/page-agent.md и выполни её шаги для события ниже.`, `Задача: <задача>`, `Событие: <событие>` и данные. Первая строка — поручение: на задание со строкой-ссылкой `Инструкция: …` агент на событии `вопрос` инструкцию не открыл и сам ответил на вопрос из данных. Интерактивная сессия запускает подагента фоном, его ответ приходит уведомлением о конце. Агент страницы — один за раз: событие, пришедшее, пока идёт прошлый агент, ждёт его уведомления — два агента разом правят один файл, и правка первого теряется.
   - Ссылка на страницу — из ответа агента: в чат на первом адресе сессии, на новой ссылке и рядом с каждым вопросом пользователю (шаг 4). Ответ «страница не опубликована» — пользователю один раз: причина и путь к файлу. Агент упал или ответил не строкой инструкции — на событии `вопрос` повтор агента с тем же заданием, до окна вопроса; повтор тоже без страницы или событие другое — пользователю одной строкой, что страница не обновлена, при вопросе — в сообщении перед окном. Следующее событие — снова агент; запуск агента вне событий — по просьбе пользователя.
8. **Границы — на всю сессию:**
   - запись оркестратора в проект — строки «ответ:» в секции «Блокер» и коммит по ответу пользователя из шага 5; строки «ответ:» забирает коммит следующей итерации, страницу задачи со списком адресов в `my_local/pages/` пишет агент страницы (шаг 7). Цель и способ проверки задачи меняет пользователь, очередь шагов — он сам или сессия по его согласию (`docs/PROTOCOL.md` § Таск-файлы). Откат правок без коммита, и своих строк «ответ:» тоже, — по ответу пользователя из шага 5: откат таск-файла стирает и строки пользователя, его ответ остаётся только в беседе;
   - идущий движок останавливается только прямой просьбой пользователя «останови»; «не запускай» — про следующий запуск; «отменяй», «стоп», «хватит» — вопрос пользователю, что отменить, до ответа движок идёт и рабочее дерево остаётся как есть. Остановка — сигнал Ctrl+C группе движка: `kill -INT -- -<PID>`, PID — второе слово файла `$(git rev-parse --absolute-git-dir)/agent-loop.lock`; движок доводит остановку сам и выходит с кодом 130;
   - к другой задаче — только по согласию пользователя: вопрос шага 6 или его просьба;
   - пуш — на «готово», вопрос пользователю и остановку, которую оркестратор не снял сам; перезапуск без вопроса идёт без пуша;
   - действия оркестратора — запуск движка, агента страницы и агентов проверок, строки «ответ:», коммит — по событиям шагов 2–7 и прямой просьбе пользователя; вывод из разговора, например «пропущен шаг — сделаю его сейчас», — предложение пользователю одной фразой, а не действие;
   - всё, что оркестратор пишет пользователю, — по `docs/PROTOCOL.md` § Сообщения пользователю. Вопрос пользователя в чате — ответ первым же сообщением, из уже известного: свои действия за сессию — что оркестратор записал, стёр, запустил и остановил, — таск-файл, секция «Блокер», журнал цикла, ответы агента страницы; ответ сессии на его вопрос — её словами; «где мой ответ», «что ты сделал» — сначала свои действия, которые могли это стереть или изменить. Чтение файла ради ответа — когда в известном ответа нет, с фразой перед ним, что и зачем читается; догадка ответом не выдаётся — чего оркестратор не знает, так и говорит. Пока пользователь ждёт ответа в чате, оркестратор не запускает ни агентов, ни движка: события этого времени — после ответа;
   - «что происходит», «что сейчас должно происходить» — положение этой задачи и следующее действие оркестратора: шаг очереди, движок идёт или стоит и почему, чего ждёт цикл, что оркестратор сделает дальше; цикл ждёт решения пользователя — вопрос ещё раз целиком, с вариантами;
   - ругань и упрёки — ответ по делу: на вопрос из реплики или положение задачи; упрёк без вопроса — сверка своих действий за сессию с этим скиллом: нарушение — одной фразой, что сделано и что от этого изменилось у пользователя, например «твой ответ стёрт откатом, он есть только в беседе», и что предлагает оркестратор по правилу нарушенного шага; извинения, оценки себя и обещания исправиться в ответ не идут.
9. **Итог пользователю** — последним сообщением сессии: итерации и шаги, пройденные за сессию; блокеры — кто ответил: оркестратор или пользователь; ссылка на страницу задачи; статус задачи и действие пользователя по исходу — «готово»: проверка сделанного по записям `docs/JOURNAL.md` и хвостам «Контекста», затем чекбокс строке задачи в `docs/ROADMAP.md`; «в работе» или «блокер» — снова `/box-orchestrate <задача>`. Конец по пределу контекста (шаг 2) — причина: контекст сессии занят на столько-то тысяч токенов из предельных 150 тысяч, и строка продолжения в новой сессии — `/box-orchestrate <задача>` с задачей несостоявшегося запуска, после «готово» — выбранной в шаге 6.
