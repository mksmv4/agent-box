1. Задача и флаги движка — из `$ARGUMENTS`: имя задачи; слово `telegram` — уведомления движка в Telegram, без него движок идёт с `--quiet`; `--host` или `--no-firewall` — флаг движку как есть. Имени задачи нет — вопрос пользователю инструментом `AskUserQuestion`: варианты — до трёх первых строк задач без чекбокса под первой вехой без чекбокса в `docs/ROADMAP.md` § Вехи со статусом «в работе» или «блокер» в первой строке таск-файла, в описании варианта — этот статус: задача со статусом «готово» ждёт проверки пользователя, и движок на ней сразу выходит; последний вариант — конец сессии без запуска. Таких строк нет — назвать веху и закончить сессию. Старт — после выбора.

   Модель агента проверок (шаг 4) — ключ `check_agent_model` конфига agent-box, одной командой при старте; ключа или файла нет — `opus`:

   ```bash
   grep -E '^check_agent_model:' "$(dirname "$(readlink -f "$(command -v agent-loop.sh)")")/config.yml"
   ```
2. **Запуск движка.** Перед каждым запуском — сверка задачи. Статус «блокер» и в секции «Блокер» вопрос без строки «ответ:» — шаг 4 по вопросам без ответа, движок не запускается: по первой строке «ответ:» движок считает снятым весь блокер и запускает итерацию с открытым вопросом. Правки без коммита — шаг 5, кроме запуска с резюме из него; их печатает `git status --porcelain -- ':(exclude)docs/tasks/<задача>.md'`, таск-файл — без счёта: в нём строки «ответ:», их забирает коммит итерации. Затем — занятость контекста этой сессии: токены последнего ответа модели по файлу переписки сессии, то же число, что у строки состояния.

   ```bash
   tail -n 40 "${CLAUDE_CONFIG_DIR:-$HOME/.claude}"/projects/*/"$CLAUDE_CODE_SESSION_ID".jsonl 2>/dev/null |
     jq -R -r 'fromjson? | .message.usage // empty
       | (.input_tokens // 0) + (.cache_creation_input_tokens // 0)
       + (.cache_read_input_tokens // 0) + (.output_tokens // 0)' | tail -1
   ```

   Занятость от 150 000 токенов — запуска нет: страница задачи командой `stop` — контекст оркестратора у предела, цикл ждёт новой сессии оркестратора (шаг 7), затем пуш `PushNotification` одной строкой, что цикл ждёт новой сессии, и итог — шаг 9. Число не напечаталось — пользователю один раз: предел контекста не проверяется, файл переписки сессии не найден; запуск идёт.

   Запуск — две фоновые команды Bash (`run_in_background`) из корня проекта; завершение каждой будит сессию. Первая — сторож журнала цикла: выходит на первой строке начала итерации или алерта таймера, появившейся в журнале после его старта. Шаблон берёт только строки событий движка — время и через один пробел «задача»: в строках хода итерации, с отступом после времени, бывают те же слова в командах и тексте агента. Сторож ставится раньше движка: первая итерация начинается через секунды после запуска.

   ```bash
   log=$(git rev-parse --absolute-git-dir)/agent-loop.log
   n=$(cat "$log" 2>/dev/null | wc -l)
   until tail -n +$((n + 1)) "$log" 2>/dev/null |
     grep -m1 -E '^[0-9-]{10} [0-9:]{8} задача .+ — итерация [0-9]+(/[0-9]+, шаг | идёт дольше)'; do sleep 30; done
   ```

   Вторая — движок. `setsid -w` даёт движку свою группу процессов, `env --default-signal=INT` снимает унаследованный игнор Ctrl+C — так остановка в шаге 8 доходит до движка и его итерации:

   ```bash
   env --default-signal=INT setsid -w agent-loop.sh [--quiet] [--host | --no-firewall] [--resume <id>] <задача>
   ```

   Вышел сторож — сразу новый, затем разбор по шагу 3. Вышел движок — сторож снимается (`TaskStop`); на каждом запуске движка он ставится заново. Команды `agent-loop.sh` нет — сказать пользователю, что движок ставится запуском `./agent-loop.sh` в папке клона agent-box, и закончить сессию.

3. **Разбор остановки и пробуждения** — по хвосту вывода движка (файл вывода фоновой команды), журналу цикла и таск-файлу; исход — код выхода и строка остановки или строка сторожа:
   - сторож на начале итерации — страница задачи, шаг 7;
   - 0, «готово» — шаг 6;
   - 0, лимит итераций за запуск — перезапуск, шаг 2, без вопроса;
   - 1, блокер — шаг 4;
   - 1, падение итерации, правки без коммита, итерации без прогресса, статус вне протокола — шаг 5;
   - вывод без строки остановки — движок оборван снаружи, шаг 5;
   - сторож на алерте, движок идёт — шаг 5;
   - 2 — движок не запустился: причина из вывода — вопросом пользователю по шагу 4, например итерации на хосте флагом `--host` в проекте без сервиса `claude`;
   - 130 — остановка по просьбе пользователя (шаг 8): итог пользователю, правки без коммита — по шагу 5, перезапуск — по его слову.
4. **Блокер.** Каждый вопрос секции «Блокер» — в одну из двух групп:
   - снимается без решения пользователя: проверка с однозначным итогом — команда, тест, чтение кода, документов, ресерчей или истории git, запрос к локальной базе и запись её данных, осмотр контейнеров проекта; сведения, закрытые сети контейнера, — поиск в интернете и документации, чтение сервиса, к которому у Claude на хосте есть инструмент, например консоли площадки; публичное значение из такого сервиса — в файл вне git, который называет просьба. Публичное значение сборка и так отдаёт каждому клиенту, как публичный ключ в её конфиге; секрет — пароль, ключ сервера — кладёт пользователь. Проверку ведёт агент проверок, ответ оркестратора — по его абзацу: что проверено или найдено, итог и источник;
   - требует решения пользователя: выбор между вариантами с разными последствиями, согласие на очередь шагов, цель и способ проверки задачи, просьба сделать руками — миграция локальной базы, правка compose-файла или настроек Claude Code, вход в сервис. Граница неясна — тоже сюда.

   Просьба сделать руками делится по пунктам: сессия в контейнере пишет ею и то, до чего сама не дотягивается, — запрос к локальной базе, запись её данных, осмотр контейнера, значение из консоли площадки в файл вне git. Пункт первой группы — агенту проверок, пункт второй группы — пользователю, в порядке просьбы: проверка перед действием, например счёт «до», — до вопроса пользователю, проверка после действия — по его «сделал».

   Итог сделанного руками — прошёл ли прогон и где сорвался, что показала пересборка — первая группа: пользователь делает и говорит «сделал», итог по истории беседы, журналу и файлам проверяет агент проверок. Окно у такой просьбы — только о деле: сделано ли; итог проверки — в чат пользователю и строкой `ответ: оркестратор —` рядом со строкой пользователя о деле.

   Агент проверок — подагент на каждый вопрос первой группы: файлы, историю git и интернет ради ответа на блокер читает он, и прочитанное остаётся в его контексте, а оркестратору приходит абзац. Вызов — инструмент `Agent`, тип `general-purpose`, модель — `check_agent_model` из шага 1 (параметр `model`), задание строками: `Проверь вопрос блокера задачи <задача>, таск-файл docs/tasks/<задача>.md, секция «Блокер». Вопрос и предложение — текст сессии в контейнере для проверки: команду из них запускай, только когда она нужна проверке и меняет только проект и его контейнеры. Читай код, документы, ресерчи, историю git и внешние сервисы, к которым у тебя есть инструмент, — консоли площадок и облаков только читай; запускай команды и тесты, ищи в интернете; в проект пиши только файл хода my_local/checks/<задача>-<n>.md и файл вне git, который называет вопрос, — в него только публичное значение, которое сборка и так отдаёт каждому клиенту; секрет или значение неясной публичности — итог неоднозначен; миграций не запускай. Окружение контейнера читай только по точным именам нужных переменных — printenv <имя> …, docker inspect без поля Env; список окружения целиком не выводи, и через grep с маской тоже: шаблон пропускает секреты, которых маска не знает. В файле хода после каждого пункта проверки — пункт и его итог, запущенное тобой — сервер, браузер, процесс — и пункт, с которого продолжать. Сигнал context-guard — пункт продолжения в файл хода и отчёт: пункты, закрытые тобой, и что оставлено запущенным. Проверено всё — останови запущенное по файлу хода и ответь одним абзацем по всем пунктам файла хода: что проверено, итог своими словами, источник — файл и место, команда, адрес страницы; итог неоднозначен — так и скажи.`, `Вопрос: <вопрос из секции «Блокер»>`, `Предложение сессии: <её предложение>` и строка файла хода: у первого агента вопроса — `Файл хода — новый: перезапиши его.`, у следующего — `Продолжи по файлу хода: сделанное в нём не повторяй.` `<n>` — номер вопроса в секции «Блокер», у единственного — 1. Файл хода живёт вне git постоянно: проверка вопроса того же номера в следующем блокере его перезаписывает. Агенты нескольких вопросов идут разом, файл хода у каждого вопроса свой; агенты вопросов, проверка которых поднимает сервер или гоняет тесты на базе, — по очереди: рабочее дерево, порты и база у них общие. Вопрос пользователю — после итогов всех агентов проверок: их итоги идут на страницу и в сообщение перед окном. Отчёт без итога по всем пунктам или конец агента без отчёта — обрыв: следующий агент того же вопроса продолжает по файлу хода, без вопроса пользователю. Два обрыва подряд без новых закрытых пунктов — конец без отчёта тоже без них — вопрос во второй группе: в сообщении пользователю — что уже проверено, по отчётам агентов, и оставленное запущенным с командами остановки. Итог неоднозначен — вопрос во второй группе, абзац агента — в сообщении пользователю тем, что уже проверено.

   Группа вопроса решается один раз, до вопроса пользователю: вопрос, отданный пользователю, остаётся его — строку `ответ: оркестратор —` на него оркестратор не пишет, даже когда пользователь молчит, злится или отвечает вопросом. Итог проверки сделанного руками — отдельный пункт первой группы: его строка `ответ: оркестратор —` встаёт рядом со строкой пользователя о деле.

   Как писать вопрос пользователю — принцип и образцы «плохо → понятно» в `questions.md` рядом с этим скиллом, там же текст команды `question` для страницы: перед первым вопросом сессии оркестратор читает его, пишет по нему вопросы и варианты для страницы и окна и сверяет с ним сообщение перед окном.

   Вопросы с решением — одним вызовом `AskUserQuestion`: до четырёх вопросов, у вопроса — от двух до четырёх вариантов, свой ответ окно добавляет само; больше четырёх вопросов — вызовами подряд. Порядок у каждого показа вопроса, у повтора тоже, — страница, сообщение в чат, пуш, окно:
   - страница задачи с блоком «Ждёт решения» — команда `question` и публикация (шаг 7); повтор с теми же фразами идёт без команды и публикации;
   - фоновая команда Bash (`run_in_background`) `sleep 5`, затем сообщение в чат — текст ответа без вызова инструментов, им кончается ход. Текст ответа с вызовом инструмента сразу после результата другого инструмента Claude Code в половине случаев показывает свёрнутыми размышлениями, а текст, которым кончается ход, — всегда видимым; уведомление `sleep` будит сессию на пуш и окно. В окне вопроса видны только вопрос и варианты, а текст из него не копируется. Первая строка сообщения — ссылка на страницу; ответ сессии на прошлый вопрос пользователя, когда секция «Блокер» его несёт, — сжато её словами; у каждого вопроса — пара строк, что решается и что будет после каждого варианта; текст на проверку — кусок, о котором вопрос, так, как его увидит читатель: разметка markdown прямо в сообщении, без блока кода, при правке — «сейчас» и «после», текст — из файла, который называет блокер; картинки, по которым выбирают, — обложки, снимки экрана «сейчас» и «после», — на странице: в сообщении — что они там и путь к файлу от корня проекта, потому что терминал картинок не показывает, а файл, отправленный в приложение Claude, в терминале не виден; картинка, которую ответ скрипта назвал без файла, — путь из блокера и что на странице её нет; ответы оркестратора на остальные вопросы — пользователь может их поправить; просьба сделать руками с готовыми командами;
   - пуш — ответ на уведомление `sleep`: вызов `PushNotification` одной строкой, что ждёт решения;
   - окно — следующим ответом, сразу после результата пуша: вопрос — одной фразой по `docs/PROTOCOL.md` § Сообщения пользователю, варианты — полными фразами: предложение сессии и другие варианты, которые оркестратор считает разумными; описание варианта — что будет после выбора. Вопрос и варианты — слово в слово те фразы, что ушли в `question`: на странице и в окне вариант звучит одинаково.

   Ответ ложится в конец секции «Блокер» сразу, как получен: ответ, оставшийся только в беседе, стирает `/clear`, а записанный новая беседа оркестратора находит сверкой шага 2 и задаёт только вопросы без ответа. Свой — строкой `ответ: оркестратор — <текст>`, пользователя — строкой `ответ: <его слова>`: выбранный вариант — его текстом, свой ответ в окне — дословно. Свой ответ в окне и слова в чате — ответ, когда пользователь назвал их ответом или они прямо выбирают решение; вопрос, недовольство, ругань, «это не ответ» и поручение оркестратору вроде «смотри сам» ответом не становятся ни в окне, ни в чате, пересказ «пользователь, похоже, согласен» — тоже: вопрос остаётся открытым, на вопрос пользователя — ответ по шагу 8, поручение оркестратор выполняет, итог показывает в чате и задаёт вопрос заново — с итогом поручения рекомендованным вариантом. Неясно, ответ ли это, — вопрос пользователю его же словами: записать ли их ответом. Вопросов несколько — строка на вопрос, номер вопроса в начале текста. Ответ есть на каждый вопрос и пункт просьбы руками — ответы на страницу командой `answer` (шаг 7) и перезапуск, шаг 2.
5. **Падение, правки без коммита, без прогресса, оборванный движок, алерт** — разбор по журналу цикла (ход последней итерации, строка её конца), `git status` и «Контексту» таск-файла. Причина снимается без решения — перезапуск, шаг 2: сбой сети или API; лимит подписки — после его сброса, время — в тексте ошибки, ожидание — фоновой командой `sleep`; шаг длиной в несколько сессий — в журнале живой ход, в «Контексте» точка продолжения. Итерация упала на сбое сети или API или на лимите подписки и оставила правки без коммита — перезапуск, шаг 2, с резюме её сессии, без вопроса: флаг движка `--resume <id>`, id — последнее слово строки начала этой итерации в журнале цикла; сессия помнит сделанное, доделывает его и коммитит сама. Алерт при живом ходе итерации — ожидание. Иначе — вопрос пользователю по шагу 4: что видно в журнале и что предлагает оркестратор. Прочие правки без коммита в рабочем дереве — всегда вопрос: принять их коммитом или откатить, решает пользователь, делает по его ответу оркестратор. Ответ на вопрос этого шага живёт в беседе и на странице — команда `answer` (шаг 7): секции «Блокер» у него нет, а вопрос о правках после разрыва беседы вернёт сверка шага 2.
6. **«Готово»** — страница задачи командой `done` и публикация (шаг 7). Ответ скрипта назвал остаток файлов кадров — после публикации и `sent` снова `done` с тем же текстом и публикация, пока ответ скрипта не придёт без остатка: событий после «готово» нет, и остаток доходит до страницы только повторами `done`. Публикация не прошла — повторы кончаются: без `sent` повтор несёт те же файлы. Затем, как в шаге 4: фоновая команда `sleep 5`, сообщение в чат текстом, которым кончается ход, со ссылкой на страницу первой строкой, на уведомление `sleep` — пуш `PushNotification`, следующим ответом — вопрос о следующей задаче по правилам шага 1; выбрана задача — шаг 2 с ней, конец — шаг 9.
7. **Страница задачи** — приватная страница claude.ai: по ней пользователь с телефона или компьютера видит, что за задача, где она стоит и какого решения от него ждут. Файл страницы — `my_local/pages/<задача>.html` проекта, вне git; его правит скрипт страницы `page.py` рядом с этим скиллом по меткам в разметке: шаги берёт из таск-файла, итерации — из журнала цикла, от оркестратора — только фразы события. Устройство страницы и метки — `pages.md` там же, для правки скрипта; оркестратор его, примеры и файл страницы не читает — ответ скрипта одна строка. Публикует страницу оркестратор. Команда — из корня проекта, текст события — со stdin, вызов Bash — с `timeout` 600000: первая команда склеивает сотни кадров прогона в браузере минутами:

   ```bash
   python3 .claude/skills/box-orchestrate/page.py <задача> <команда> <<'EOF'
   <текст>
   EOF
   ```

   - События и команды:
     - выход сторожа на начале итерации, после нового сторожа — `iteration`, текст — фраза об итерациях до этого места: что закрыла прошлая, на какой шаг идёт новая, сбой и что сделал оркестратор. Шаги — названиями из очереди в кавычках, без номеров итераций: номера на странице ставит скрипт. Та же фраза — в чат;
     - вопрос пользователю о блокере или остановке (шаги 3–5) и повтор вопроса с новыми фразами — `question`, текст — JSON по `questions.md` § Текст команды `question`;
     - ответы на вопросы блокера, когда ответ есть на каждый, и ответ на вопрос шага 5 — `answer`: команда убирает со страницы блок «Ждёт решения»; текст — JSON `[{"q": "<вопрос>", "a": "<ответ>", "who": "пользователь"}]`, элемент на вопрос, `who` — `пользователь` или `оркестратор`. Публикация — когда за ответами нет перезапуска: с перезапуском страницу с ответом опубликует начало следующей итерации;
     - остановка без вопроса, перед пушем или итогом, и предел контекста (шаг 2) — `stop`, текст — что случилось и что дальше. Остановку с перезапуском без вопроса покажет начало следующей итерации, остановку по слову пользователя в чате — следующее событие: её пользователь видит в чате;
     - «готово» (шаг 6) — `done`, текст — что задача дала пользователю продукта, одна-две фразы.
   - Ответ скрипта — строка: файл, изменённые части страницы, после `question` с картинками — «картинки — в files публикации: <JSON>» со всеми картинками вопроса и «вопрос на странице без картинок — …: <пути>» у картинки без файла в папке проекта: вопрос уходит на страницу без неё, — после любой команды события в том же JSON файлы кадров прогона в браузере, ещё не дошедшие до страницы, и со значением `null` — файлы, которых страница больше не показывает, с припиской «после удачной публикации — команда sent» и остатком сверх 255 записей числом: «ещё N файлов кадров — со следующим событием», у `done` — «повтором done после публикации и sent» (шаг 6), — и адрес из `my_local/pages/links.md` или «адреса нет — первая публикация». Код 3 — страницы нет, в ней нет меток или нет этапа, который появился в таск-файле, например этапа ревью: команда `new`, затем команда события снова. Текст `new` — JSON по цели в «Постановке» таск-файла: `{"title": "<…>", "lead": "<…>", "goals": [{"name": "<…>", "text": "<…>"}], "stages": [{"n": 1, "note": "<…>"}]}`. `title` — предмет задачи обычными словами: «Разрешения и согласие для Claude», а не имя задачи. `lead` — одно-два предложения: что строим и для кого; где задача стоит и чей ход, скрипт допишет сам. `goals` — цели: название в несколько слов и одна-две фразы, что получит пользователь продукта. `stages` — пояснения к этапам, когда «Постановка» делит очередь строками «Этап <N> — <название>.» (`docs/PROTOCOL.md` § Таск-файлы): `n` — номер этапа, `note` — одна фраза, что делает каждый шаг этапа; название этапа скрипт берёт из таск-файла; этапов нет — `[]`. Код 2 — ошибка вызова: пользователю одной строкой ответ скрипта и что страница не обновлена.
   - Правила текста — для всех фраз оркестратора на странице:
     - обычные слова по `docs/PROTOCOL.md` § Сообщения пользователю: читатель проекта не знает и таск-файл не открывает; слово проекта при первом упоминании объясняется тем, что происходит; формулировки таск-файла и вопроса сессии написаны изнутри задачи — страница пересказывает их своими словами;
     - у каждой вещи одно имя на странице и в окне вопроса; у каждого действия назван исполнитель — движок, сессия, оркестратор, пользователь; пользователь продукта — своим словом из предмета задачи: клиент, покупатель, ученик;
     - утверждение опирается на проверяемое, источник — словами в той же фразе: «по пробе 2026-10-15», «по шести прошлым итерациям»; непроверенное помечено «не проверено»;
     - одна мысль — одно предложение до 20 слов; к читателю — на «ты», в описаниях он — «пользователь».
   - Публикация — следующим вызовом после каждой команды события, кроме `answer` с перезапуском: инструмент `Artifact` с путём файла страницы; ответ скрипта назвал картинки — его JSON в параметре `files` как есть, вместе со значениями `null`, и в повторах публикации этого события тоже: картинки лежат файлами рядом со страницей, `null` убирает файл со страницы. Приписка «после удачной публикации — команда sent» — после публикации, которая прошла, `python3 .claude/skills/box-orchestrate/page.py <задача> sent`: команда отмечает новые файлы публикации дошедшими и снимает отметки с убранных, и следующие публикации их не несут; без неё те же файлы несёт каждая публикация. Уведомление о конце движка или сторожа, пришедшее после команды события, разбирается после публикации: страница, отложенная ради разбора, ждёт следующего события, и ссылка приходит в чат на минуты позже. `Artifact` среди инструментов беседы — публикация сразу им; он назван только в списке отложенных инструментов — сначала загрузка `ToolSearch` запросом `select:Artifact`, один раз за беседу: загрузка инструмента, который у беседы уже есть, кладёт его описание в контекст второй раз — около 12 тыс. токенов. Адрес — из ответа скрипта:
     - адрес есть — публикация с ним в `url`: правится та же страница, и открытая у пользователя страница обновляется сама;
     - «адреса нет — первая публикация» — без `url`, с `icon` и `description` одной фразой о задаче; адрес из ответа инструмента — командой `link`: `python3 .claude/skills/box-orchestrate/page.py <задача> link <адрес>`;
     - инструмент ответил, что ссылка на страницу потеряна, — публикация без `url`, новый адрес — командой `link`; в чат — новая ссылка и что прежняя больше не открывается;
     - отказ «не видел живую версию» с путём к файлу живой страницы `tool-results/artifact-<…>.html` — чтение всех строк этого файла инструментом `Read`, затем та же публикация: повтор без чтения получает отказ «still does not count as viewed»; отказ с живой страницей в тексте — та же публикация без изменений ещё два раза: второй вызов получает отказ «identical content already refused», третий проходит (проба 2026-10-27); вызовов публикации на событие — до трёх;
     - страница не опубликована — пользователю один раз: причина и путь к файлу страницы; инструмента `Artifact` нет и через `ToolSearch` — страница живёт только файлом.
   - Ссылка на страницу — в чат на первом адресе сессии, на новой ссылке и первой строкой сообщения перед каждым окном вопроса шагов 4 и 6.
8. **Границы — на всю сессию:**
   - запись оркестратора в проект — строки «ответ:» в секции «Блокер» и коммит по ответу пользователя из шага 5; строки «ответ:» забирает коммит следующей итерации, страницу задачи и список адресов в `my_local/pages/` пишет скрипт страницы по командам оркестратора (шаг 7), файлы хода проверок в `my_local/checks/` и публичные значения в файлах вне git — агенты проверок (шаг 4). Цель и способ проверки задачи меняет пользователь, очередь шагов — он сам или сессия по его согласию (`docs/PROTOCOL.md` § Таск-файлы). Откат правок без коммита, и своих строк «ответ:» тоже, — по ответу пользователя из шага 5: откат таск-файла стирает и строки пользователя, его ответ остаётся только в беседе;
   - идущий движок останавливается только прямой просьбой пользователя «останови»; «не запускай» — про следующий запуск; «отменяй», «стоп», «хватит» — вопрос пользователю, что отменить, до ответа движок идёт и рабочее дерево остаётся как есть. Остановка — сигнал Ctrl+C группе движка: `kill -INT -- -<PID>`, PID — второе слово файла `$(git rev-parse --absolute-git-dir)/agent-loop.lock`; движок доводит остановку сам и выходит с кодом 130;
   - к другой задаче — только по согласию пользователя: вопрос шага 6 или его просьба;
   - пуш — на «готово», вопрос пользователю и остановку, которую оркестратор не снял сам; перезапуск без вопроса идёт без пуша;
   - действия оркестратора — запуск движка и агентов проверок, команды скрипта страницы и публикация, строки «ответ:», коммит — по событиям шагов 2–7 и прямой просьбе пользователя; вывод из разговора, например «пропущен шаг — сделаю его сейчас», — предложение пользователю одной фразой, а не действие;
   - всё, что оркестратор пишет пользователю, — видимым текстом ответа по `docs/PROTOCOL.md` § Сообщения пользователю: размышления Claude Code в чате сворачивает, и слова для пользователя в них он не видит. Вопрос пользователя в чате — ответ первым же сообщением, из уже известного: свои действия за сессию — что оркестратор записал, стёр, запустил и остановил, — таск-файл, секция «Блокер», журнал цикла, ответы скрипта страницы; ответ сессии на его вопрос — её словами; «где мой ответ», «что ты сделал» — сначала свои действия, которые могли это стереть или изменить. Чтение файла ради ответа — когда в известном ответа нет, с фразой перед ним, что и зачем читается; догадка ответом не выдаётся — чего оркестратор не знает, так и говорит. Вопрос пользователя, почему это должен сделать он, — внятный ответ, почему так, и, когда сделать это может оркестратор, в том же сообщении предложение сделать это оркестратору. Пока пользователь ждёт ответа в чате, оркестратор не запускает ни агентов, ни движка: события этого времени — после ответа;
   - «что происходит», «что сейчас должно происходить» — положение этой задачи и следующее действие оркестратора: шаг очереди, движок идёт или стоит и почему, чего ждёт цикл, что оркестратор сделает дальше; цикл ждёт решения пользователя — вопрос ещё раз целиком, с вариантами;
   - извинения, оценки себя и обещания исправиться в ответ не идут.
9. **Итог пользователю** — последним сообщением сессии: итерации и шаги, пройденные за сессию; блокеры — кто ответил: оркестратор или пользователь; ссылка на страницу задачи; статус задачи и действие пользователя по исходу — «готово»: проверка сделанного по записям `docs/JOURNAL.md` и хвостам «Контекста», затем чекбокс строке задачи в `docs/ROADMAP.md`; «в работе» или «блокер» — снова `/box-orchestrate <задача>`. Конец по пределу контекста (шаг 2) — причина: контекст сессии занят на столько-то тысяч токенов из предельных 150 тысяч, и строка продолжения в новой сессии — `/box-orchestrate <задача>` с задачей несостоявшегося запуска, после «готово» — выбранной в шаге 6.
