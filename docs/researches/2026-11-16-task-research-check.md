## Ресерч: практики и что к месту

1. Разведка ограничена по времени и кончается решением: тикетами, документом или списком вопросов; вариант «ничего не менять» стоит в сравнении всегда (spike, «Option Zero»). К месту: вывод «по ресерчу нынешний план оптимален» — исход наравне с правками; предел разведки — шаг очереди и порог контекста. Оценка часами не берётся: у итерации предел — контекст.
2. Неиспользованный итог разведки — потерянная работа; разбор итога назначается заранее (spike). К месту: правки ресерча не остаются в файле — их берёт проверка или блокер.
3. Проверяющий, которого просят искать недочёты, находит их всегда; правка каждого добавляет лишние слои и тесты невозможных случаев — поэтому «skip style» (Claude Code, § Review against your spec). К месту — правилом обоих этапов: правка — только когда без неё задача хуже дойдёт до цели. Это слова пользователя «не пытаться воткнуть что-то ради задачи».
4. Интервью до спецификации, сборка — новой сессией по записанной спецификации (Claude Code, § Brainstorm with Claude first). В обвязке это уже заведение задачи; ресерч и проверка идут отдельными итерациями с чистым контекстом.

## Проверка: практики и что к месту

5. Проверка до реализации только читает и отчитывается; правки — после явного согласия; проходы: покрытие в обе стороны — требование без задачи и задача без требования, спор с «конституцией» проекта — всегда критично, порядок задач, неизмеримые критерии, разнобой терминов; без находок — короткий отчёт об успехе (Spec Kit, `analyze.md`). К месту: цель ↔ шаги в обе стороны, спор с `RULES.md` и `ARCHITECTURE.md`, порядок шагов, проверка шага с однозначным итогом; согласие на правки протокол уже требует; без находок — чекбокс, как у ревью без находок. Таблица серьёзности и предел в 50 находок не берутся: фильтр пункта 3 оставляет только находки, мешающие цели. Номера требований `FR-###` не берутся: шаги и так видны чекбоксами.
6. Валидация — «делаем то, что нужно», верификация — «требования записаны верно»; обе держатся на трассировке: каждое требование связано с потребностью, которой служит (блоги поставщиков). К месту: «цель — из слов пользователя» и «решение ведёт к цели» — валидация; «шаги закрывают цель, каждый ей нужен» — трассировка; «проверка шага однозначна» — верифицируемость.
7. Перед запуском без присмотра — пять вопросов: знает ли агент, как выглядит «готово»; может ли проверить свою работу; что ему можно трогать; что его остановит; кто принимает итог (Claude Code, Best practices). К месту первые два — цель и проверка шага. Остальные три обвязка закрывает контейнером, пределами движка и блокером — задаче их сверять не нужно.
8. Проверки этого репозитория 2026-11-13 и 2026-11-14 нашли расхождения на стыках правил и предложение против решения пользователя; проверка после правок нашла новые расхождения в самих правках. К месту: сверка с `DECISIONS.md` — пункт проверки; правки ресерча проверяются до показа пользователю — довод за решение 2026-11-16 «один раз после проверки»; находка — где, что сломается, правка «сейчас → после», как в тех проверках.

## Показ правок — не одной портянкой

9. Уточнения — по одному вопросу, не больше пяти, рекомендация первой с причиной, только вопросы, ответ на которые меняет работу (Spec Kit, `clarify.md`). К месту: правка — отдельный пункт с номером и своим ответом; оркестратор показывает вопросы блокера окнами по одному, до четырёх за вызов (скилл оркестратора, шаг 4) — правки берут это без правки скилла; предложение сессии — рекомендация. Предел в пять не берётся: мелочь режет фильтр пункта 3, а правка сверх предела потерялась бы.
10. Решения пользователя: макет README в конце ресерча на 509 строк он читать не стал (2026-10-15); просьбу сделать руками одним сообщением назвал портянкой, шаги по одному действию — второй крайностью; шаг — одно или несколько действий ради одного результата (2026-11-15). К месту: текст ресерча и проверки в блокер не идёт — блокер называет файлы; правка — один результат для задачи, правки одного места — одним пунктом.

## Как ресерч в контейнере читает страницы

- Поиск WebSearch идёт через бэкенд Anthropic, адрес `api.anthropic.com` ограничение сети держит открытым — поиск в контейнере работает. По документации он возвращает заголовки и адреса и страниц не читает. На хосте 2026-11-16 ответ поиска нёс и пересказ найденного с выдержками со страниц; в контейнере — не проверено, проверит живой прогон.
- Чтение страницы WebFetch — запрос с самой машины (`2026-10-04-firewall.md`). В контейнере открыты документация Claude Code `code.claude.com` — исходник `.md` берёт `curl`, — GitHub по его диапазонам: сайт, API и git, — npm и PyPI (`container/firewall.sh`). Файл публичного репозитория — `curl` к API GitHub с заголовком `Accept: application/vnd.github.raw`; в образе нет `gh`; в контейнере не проверено. Прочие сайты закрыты.
- Закрытая страница, от которой зависит вывод, — уже правило протокола § Таск-файлы: блокер с адресом, зачем он шагу, и строкой `CLAUDE_BOX_ALLOW`. С оркестратором такой вопрос снимает его агент проверок на хосте: скилл оркестратора, шаг 4 — «сведения, закрытые сети контейнера, — поиск в интернете и документации». Весь прогон движка с открытой сетью — `--no-firewall` или `--host`; у задач самого agent-box движок идёт с `--host`.
- Итог: нового механизма не нужно. Шаг ресерча помечает вывод по выдаче поиска без чтения страницы и приносит закрытую страницу, от которой зависит вывод, блокером по старому правилу.

## Решения макета

- Место правил — новый раздел протокола после § Таск-файлы: задачи заводят и `/box-task`, и сессия в беседе (решение 2026-11-13), а протокол читают обе; `/box-task` ссылается. Скилл оркестратора и `/box-next` без правок: оркестратор уже показывает вопросы блокера по одному и снимает закрытые страницы агентом проверок, `/box-next` делает шаг любого этапа.
- Этапы встают по выбору: отдельный вопрос с четырьмя вариантами, без ответа на него этапов нет. Иначе ответ на первый вопрос сообщения — согласие на всё в нём — ставил бы оба этапа каждой задаче.
- Правок нет — без остановки, как ревью без находок (`/box-review`): вывод лежит в файле ресерча.
- Итог проверки — свой файл `<дата>-<задача>-check.md`, как `2026-11-13-orchestrator-helper-check.md`: блокер несёт правки коротко, находки целиком лежат в файле.
- Объём: раздел — около 4 тыс. знаков к протоколу в 20 тыс., его читает на старте каждая сессия. Шаблон этапов файлом рядом с `/box-task` сократил бы протокол, но сессии в беседе пришлось бы читать его отдельно — шаблон оставлен в протоколе.
- Правку цели и способа проверки по согласию пользователя вписывает сессия: протокол даёт это только очереди, а правки ресерча и проверки задевают и цель.
