# Ресерч 2026-11-09 — сеть контейнера Claude отдельным проектом Compose

Вопрос беседы: что в agent-box привело к падению контейнера Claude в пилотном проекте и к тому, что агенты сбой обходили, а не чинили. Повод — беседа оркестратора пилотного проекта 2026-11-09. Решения — `DECISIONS.md` 2026-11-09; задача — `tasks/compose-net.md`.

## Случай пилотного проекта

- Основной compose-файл пилотного проекта с первого коммита задаёт сети по умолчанию своё имя: `networks: default: name: <проект>_net`. `claude-box.yml` лёг 2026-11-06 по схеме `researches/2026-10-14-compose-local.md`: то же имя проекта Compose — у обоих файлов по папке, — сеть без своего имени, Compose называет её `<проект>_default`. У одного проекта Compose две сети с меткой сети по умолчанию.
- 2026-11-06, Compose 5.6.1. Итерации задачи сборки документации в контейнере прошли: запуск Claude создал `<проект>_default`. Вечером итерация другой задачи на хосте поднимала базу основного стека: Compose печатал `network "<проект>_default" carries the compose label "default" but does not match the compose file … it is left untouched`, база не стартовала — `container … is not connected to the network <проект>_default`. Итерация удалила `<проект>_default` руками, строки Compose о ней вырезала из вывода (`grep -v '<проект>_default'`), в «Контексте» записала только, что на машине осталась старая сеть. Итерация следующего шага так же вырезала эти строки из вывода `docker compose config`.
- 2026-11-08 Compose обновился до 5.7.0 (журнал пакетов).
- 2026-11-09, Compose 5.7.0. Первая итерация в контейнере упала за секунду: `Error response from daemon: error while removing network: network <проект>_net has active endpoints`. Compose приводит сети проекта к `claude-box.yml`: создаёт `<проект>_default` и убирает `<проект>_net`, а к ней подключена работающая база.
- Оркестратор назвал причину без проверки — «задача переименовала сеть»; по истории git имя стоит с первого коммита. Вариантом по умолчанию он рекомендовал запуск итераций на хосте, без ограничения сети, — так шли прошлые запуски задачи. Настоящую причину нашёл только по требованию пользователя.

## Причина в agent-box

- Общее имя проекта Compose. Для Compose `claude-box.yml` — описание всего проекта, а в нём только сервис Claude. Всё остальное, что у проекта есть, Compose при каждом запуске Claude считает расхождением с файлом: контейнеры проекта — лишними (`Found orphan containers`, движок глушит строку переменной `COMPOSE_IGNORE_ORPHANS=true`; запуск Claude с `--remove-orphans` удаляет базу проекта — `researches/2026-10-14-compose-local.md` § Проба образца и движка), сеть проекта со своим именем — чужой сетью по умолчанию: 5.6 её оставлял с предупреждением, 5.7 убирает.
- Проба 2026-10-14 проверила только сеть по умолчанию без своего имени и строку `name:` основного файла; случай «у проекта свои сети» в «Контексте» `tasks/compose-local.md` записан непроверенным предложением.
- Сбой среды — Docker, сеть, инструменты, — не связанный с шагом, протокол и скиллы не разбирают: сессия видит в нём помеху шагу и обходит самым коротким путём — удаляет ресурс, прячет предупреждение, меняет способ запуска.

## Проба — Compose 5.7.0, образ `alpine`, 2026-11-09

Временная папка: основной compose-файл — проект `cbp-proj`, сервис `db` (`sleep 600`), сеть по умолчанию с именем `cbp_net`; файл Claude — проект `cbp-claude`, сервис `claude` с `profiles: [claude]`, сеть по умолчанию с тем же именем `cbp_net`, без `external`. Запуски — `docker compose -f … up -d` проекта и `docker compose -f … run` Claude: `run -d` держит контейнер Claude живым, `run --rm claude getent hosts db` — адрес базы по имени.

- Проект первым, затем Claude: Claude входит в сеть проекта, `db` по имени отвечает. Каждый запуск Claude печатает `a network with name cbp_net exists but was not created for project "cbp-claude". Set external: true to use an existing network`, код 0. Повторный `up` проекта при живом Claude — `Running`, код 0; повторный запуск Claude — код 0; сеть не пересоздаётся.
- `down` проекта при живом Claude: база убрана, сеть остаётся — `Resource is still in use`, код 0.
- Claude первым, затем проект: запуск Claude создаёт `cbp_net` с меткой проекта `cbp-claude`; `up` проекта печатает то же предупреждение для `cbp-proj`, входит в сеть, код 0; `db` по имени отвечает; повторные запуски обоих — код 0.
- Сеть основного файла с настройками — метка и подсеть `10.99.77.0/24`, — в файле Claude только имя. Проект первым: Claude входит в сеть, подсеть — `10.99.77.0/24`, база по имени отвечает, повторный `up` проекта сеть не трогает. Claude первым: сеть создаётся по файлу Claude — подсеть `192.168.176.0/20`, без метки; `up` проекта входит в неё с одним предупреждением, код 0: проект молча живёт в сети с чужими настройками.
- Хэш настроек сети в метке `com.docker.compose.config-hash` у одинаковых описаний совпадает, у описаний с разными настройками — разный; пересоздания сети из-за разницы хэшей в пробе не было.

## Выводы

- Своё имя проекта Compose у `claude-box.yml` и сеть проекта в нём тем же именем без `external`: нет сети — Compose создаёт её сам, есть — входит; ресурсы основного проекта запуск Claude больше не сверяет со своим файлом. `external: true` требует сети до запуска: по документации Compose внешнюю сеть не создаёт и при её отсутствии возвращает ошибку.
- Описание сети в файле Claude — целиком, как в основном файле: сеть, созданную запуском Claude, проект получает с настройками файла Claude. Проект, сменивший настройки сети, отстаёт от файла Claude до повторного `/box-init`.
- Предупреждение «сеть создана не этим проектом» печатается на каждом запуске и советует `external: true` — совет здесь ломает старт Claude без поднятого проекта; файлу Claude нужен комментарий об этом.
- Путь папки проекта в контейнере сейчас — `/workspace/${COMPOSE_PROJECT_NAME}`; со своим именем проекта он сменится, а к пути привязаны сессии, автопамять и доверие Claude Code (`architecture/container.md`). Путь — явной строкой с нынешним значением.
- Не проверено: сервисы проекта только в своих сетях, без сети по умолчанию; сеть, описанная в дополнении основного compose-файла. `--remove-orphans` в запуске Claude со своим именем проекта — § Проба образца.

## Проба образца — шаг «Образец», Compose 5.7.0, образ `maksim44/claude-box` от 2026-11-08

Временная папка, в ней два проекта с git. Файл Claude — `template/claude-box.yml`, `<проект>` заменён именем проекта основного файла. Команды Claude — `run` с `--entrypoint getent claude hosts db` — адрес базы по имени — и `run -d` с `--entrypoint sleep` — живой контейнер Claude.

- Проект A: основной файл `name: cbn-proj`, сервис `db`, сеть по умолчанию `cbn_net` с меткой и подсетью `10.99.78.0/24`; в файле Claude — `name: cbn-proj-claude` и тот же блок сети целиком.
  - Проект первым: Claude получает адрес базы `10.99.78.2`. Повторный `up` проекта при живом Claude — `Running`, повторный запуск Claude — код 0; id сети, подсеть и метка проекта `cbn-proj` не меняются.
  - Claude первым: запуск создаёт `cbn_net` с подсетью `10.99.78.0/24` и меткой из блока, метка проекта — `cbn-proj-claude`. `up` проекта входит в неё, база по имени отвечает; повторные запуски обоих — код 0, id сети тот же.
  - `run --rm --remove-orphans` Claude при поднятой базе — код 0, база работает. `up -d --remove-orphans` проекта — живой контейнер Claude работает.
  - `docker compose -f claude-box.yml down` при живой базе и живом Claude — `No resource found to remove for project "cbn-proj-claude"`, код 0: база, контейнер Claude и сеть на месте, и когда сеть создал запуск Claude. `down --remove-orphans` проекта Claude контейнеры `run` тоже оставляет; уборка пробы — `docker rm -f` и `docker network rm`.

- Проект B: основной файл `name: cbm-proj` без блока сети; в файле Claude — `name: cbm-proj-claude` и блок образца `name: cbm-proj_default`. Проект первым — сеть с меткой проекта `cbm-proj`, Claude входит в неё; Claude первым — сеть создаёт запуск Claude с меткой `cbm-proj-claude`, `up` проекта входит в неё. В обоих порядках база по имени отвечает, повторные запуски сеть не пересоздают, сеть проекта одна.
- Предупреждение `a network with name … exists but was not created for project …` печатает каждый запуск Claude в сеть проекта и каждый `up` проекта в сеть, созданную запуском Claude; код 0. `--progress quiet`, с которым движок запускает итерации, строку оставляет в stderr.

## Выводы шага «Образец»

- Образец — своё имя проекта Compose, блок сети основного файла, путь папки проекта явной строкой — держит все случаи пробы: Claude видит базу по имени в обоих порядках запуска, сеть одна и не пересоздаётся, настройки у неё — основного файла, кто бы её ни создал; `--remove-orphans` из любого из двух файлов контейнеры другого не трогает.
- Предупреждение о сети человек видит и в выводе `up` проекта, когда сеть создал Claude, и в журнале движка: пункт `README.md` о нём — в шаге «Движок и документы».
- Сервисы проекта только в своих сетях и сеть из дополнения основного файла по-прежнему не проверены — критерии блокера задачи.

## Проба дополнения основного файла — шаг `/box-init`, Compose 5.7.0

Временная папка: основной файл `compose.yml` — `name: cbo-main`, сервис `db`, сеть по умолчанию `cbo_net` с `driver_opts` `a: "1"`; дополнение — своя строка `name:` и тот же блок сети с `driver_opts` `b: "2"`. Только `docker compose config`, без контейнеров и сетей.

## Итог шага `/box-init`

## Правило о сбоях среды — шаг этапа 2, 2026-11-09

- Правило — абзац `PROTOCOL.md` § Таск-файлы после абзаца о закрытом адресе интернета: сбой среды, не связанный с шагом, — блокер; сессия не обходит его — не удаляет ресурсы, не вырезает предупреждения, не меняет способ запуска, — а ищет причину проверкой и пишет, что сломалось, почему и что предлагает починить. Слов про `--host` нет — ответ пользователя, `DECISIONS.md` 2026-11-09.
- Случай пилотного проекта 2026-11-09 — итерация упала до начала сессии: контейнер Claude не стартовал, и блокер писать было некому, сбой видел только оркестратор. Поэтому правило называет и его: такой сбой оркестратор разбирает тем же порядком в вопросе пользователю о падении итерации — ветка «иначе» шага 5 скилла оркестратора, где он пишет, «что видно в журнале и что предлагает».
- Скилл оркестратора не правился: протокол он получает хабом на старте (`template/AGENTS.md`, «Чтение на старте»), а шаг 5 оставляет предложение на его усмотрение — правило ложится в это место. Перезапуск без вопроса из шага 5 — сбой сети или API, лимит подписки — остаётся: повтор запуска не входит в перечень обходов.
- `/box-next` не правился: сессия шага получает протокол тем же хабом, как и правило о закрытом адресе.
