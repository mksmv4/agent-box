# orchestrator-context

## Постановка

Цель: к первой публикации страницы задачи оркестратор занимает не больше 60 тыс. токенов контекста — замер по истории сессии оркестратора в этом репозитории; до задачи — 105–115 тыс. (сессии areas-config, readme, compose-local 2026-10-14 и 2026-10-15). Обновление страницы и проверка вопроса блокера добавляют в контекст оркестратора короткий ответ подагента, а не прочитанные файлы. Страница задачи и её правила `template/.claude/skills/box-orchestrate/pages.md` остаются как есть. Повод — беседа 2026-10-15: на старте оркестратор читает правила страниц, таск-файл, файл страницы или пример, загружает инструмент `Artifact`, а первая публикация существующей страницы в новой сессии получает отказ «не видел живую версию» с живой страницей целиком в ответе; на работу остаётся меньше 50 тыс. до предела 150 тыс.

## Контекст

Шаг «Проверка агента проверок вживую» ждёт прогона пользователя — секция «Блокер». Тестовый проект собран и проверен: скрипт `my_local/orchestrator-check-probe.sh`, вне git, кладёт копию образца в `/tmp/orch-check` с задачей report из двух шагов. Шаг «Порт сервиса» ждёт значение `port` из `ops/service.yml` — 8437: папка вне git строкой `/ops/` в `.gitignore`, в контейнере на её месте пустая папка в памяти — ключ `tmpfs` в `claude-box.yml` копии; пустую папку в контейнере и файл на хосте показал `ls` в контейнере сервиса. Шаг «Подпись отчёта» — выбор пользователя из двух вариантов. Ожидаемый ход: итерация 1 — блокер о порте, его снимает агент проверок, строка «ответ: оркестратор —» с источником, перезапуск; итерация 2 закрывает шаг, итерация 3 — блокер о подписи и вопрос пользователю; итерация 4 — «готово», вопрос о следующей задаче.

Замер — следующая сессия, по ответу пользователя:

- история оркестратора — свежий `.jsonl` в `~/.claude/projects/-tmp-orch-check/`, истории агентов — в `<id>/subagents/`, версия CLI — поле `version`; счёт — команда «Проверки шага» и отрезки, как в ресерче § Рост контекста оркестратора на обновлении;
- рост контекста оркестратора на блокере о порте — задание агенту проверок, ответ запуска, отчёт агента, уведомление о конце, запись строки ответа; предел 3 тыс.;
- строка ответа и источник — `git -C /tmp/orch-check log -p` по таск-файлу и `DECISIONS.md` тестового проекта; расход агента проверок на Opus — по его истории;
- страница — вызов агента страницы и его ответ «опубликована» на каждом событии: `итерация` ×4, `вопрос`, `готово`; ссылка в чате — рядом с вопросом о подписи и вопросом о следующей задаче;
- правки шага «Оркестратор на вопросе пользователю» — сообщение со ссылкой перед окном, вопрос словами пользователя продукта, ответ в таск-файле — словами пользователя;
- числа — новым разделом в `docs/researches/2026-10-15-page-agent.md`; оркестратор спросил пользователя о порте — критерий не выполнен, сессия замера ищет причину в истории; команды уборки — в итог сессии замера, они же в «Блокере».

Состояние среды: `/tmp/orch-check` и сеть Docker `orch-check_default` — от проверки `ls`, движок прогона возьмёт ту же сеть; остатки прошлой пробы оркестратора — папка `/tmp/orch-limit` и сеть `orch-limit_default`.

## Блокер

Нужен живой прогон оркестратора на тестовом проекте. Проверяется: вопрос, ответ на который лежит в файле проекта, оркестратор снимает сам через помощника, и его память почти не растёт; вопрос с выбором он задаёт вам, а рядом в чате — ссылка на страницу задачи.

Тестовый проект уже собран в папке `/tmp/orch-check`: задача report из двух шагов. На первом шаге сессия спросит порт сервиса — внутри контейнера его не видно, ответить должен оркестратор сам, без вас. На втором шаге спросит, какой подписью закончить отчёт, — это вопрос вам, подойдёт любой вариант.

Сделать руками:

1. Папки `/tmp/orch-check` нет — например, после перезагрузки, — собрать заново:
   ```
   bash ~/tools/agent-box/my_local/orchestrator-check-probe.sh
   ```
2. В новом окне терминала запустить Claude в папке проекта, на вопрос о доверии папке — да:
   ```
   cd /tmp/orch-check
   claude
   ```
   В Claude — `/box-orchestrate report`.
3. Дальше оркестратор ведёт задачу сам: четыре итерации движка. От вас — ответ на вопрос о подписи и в конце, на вопрос о следующей задаче, — конец сессии. Если оркестратор спросит вас о порте — это срыв проверки: ответьте «8437», чтобы прогон дошёл до конца, и упомяните это в ответе здесь.

Номер беседы называть не нужно: следующая сессия найдёт её историю в папке тестового проекта.

Уборка — после сессии замера: до неё история беседы нужна для подсчёта. Страница пробы на claude.ai после уборки остаётся.
```
docker network rm orch-check_default
rm -rf /tmp/orch-check
rm -rf ~/.claude/projects/-tmp-orch-check
rm -rf ~/.claude-box/.claude/projects/-workspace-orch-check
```

Как ответить: допиши в конец файла docs/tasks/orchestrator-context.md строку, которая начинается с «ответ:», и после двоеточия — сам ответ: прогон прошёл до конца или где сорвался. Потом запусти в Claude /box-next orchestrator-context или в терминале agent-loop.sh orchestrator-context.
