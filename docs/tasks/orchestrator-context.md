# orchestrator-context

## Постановка

Цель: к первой публикации страницы задачи оркестратор занимает не больше 60 тыс. токенов контекста — замер по истории сессии оркестратора в этом репозитории; до задачи — 105–115 тыс. (сессии areas-config, readme, compose-local 2026-10-14 и 2026-10-15). Обновление страницы и проверка вопроса блокера добавляют в контекст оркестратора короткий ответ подагента, а не прочитанные файлы. Страница задачи и её правила `template/.claude/skills/box-orchestrate/pages.md` остаются как есть. Повод — беседа 2026-10-15: на старте оркестратор читает правила страниц, таск-файл, файл страницы или пример, загружает инструмент `Artifact`, а первая публикация существующей страницы в новой сессии получает отказ «не видел живую версию» с живой страницей целиком в ответе; на работу остаётся меньше 50 тыс. до предела 150 тыс.

## Контекст

Шаг «Агент проверок при блокере» закрыт сверкой ниже. Правки — шаги «Блокер» и «Границы» скилла оркестратора `template/.claude/skills/box-orchestrate/SKILL.md`, строка `description` в его шапке, `docs/ARCHITECTURE.md` § Оркестратор — абзац об агенте проверок после абзаца об агенте страницы и пункт о блокере в списке разбора остановки.

Сверка — чтение для ответа на блокер → место в скилле:

- чтение кода, документов, ресерчей, истории git, команды и тесты, поиск в интернете и документации — шаг «Блокер», первая группа: «Проверку ведёт агент проверок, ответ оркестратора — по его абзацу»; абзац «Агент проверок — подагент на каждый вопрос первой группы…» — вызов `Agent`, тип `general-purpose`, модель `opus` по решению пользователя (`DECISIONS.md` 2026-10-15 — модель помощников оркестратора), задание из трёх строк: поручение с перечнем того, что агент читает и запускает, «в проект не пиши» и форма ответа — один абзац «что проверено, итог своими словами, источник»; вопрос из секции «Блокер»; предложение сессии. Строку «ответ: оркестратор —» оркестратор пишет по абзацу; итог неоднозначен или агент упал — вопрос во второй группе, абзац агента — в сообщении пользователю;
- вопросы второй группы — как раньше: страница, пуш, сообщение, окно; итоги агентов проверок идут на страницу событием `вопрос` и в сообщение перед окном — вопрос пользователю ждёт уведомлений о конце всех агентов проверок;
- остальное чтение в скилле ответом на блокер не служит: шаг 3 — хвост вывода движка, журнал цикла и таск-файл для разбора остановки и группы вопроса; шаг 4, сообщение в чат — текст на проверку из файла, который называет блокер, для вопроса второй группы; шаг 5 — журнал, `git status` и «Контекст» для разбора падения; шаг 8 — чтение файла ради ответа на вопрос пользователя в чате;
- шаг «Границы» — запуск агентов проверок в списке действий оркестратора по событиям.

Скилл по `RULES.md` § Конвенции кода: имя, `disable-model-invocation`, `argument-hint` и нумерованные шаги не менялись; `description` — «оркестратор снимает своим ответом по итогу подагента проверок»; дополнены шаги 4 и 8. Скилл вырос с 13,3 до 14,4 тыс. знаков — около 0,6 тыс. токенов к старту оркестратора. Задание агента проверок — строками прямо в скилле: на задание со строкой-ссылкой на инструкцию агент страницы инструкцию однажды не открыл (шаг «Страница задачи» скилла).

Правки скилла и протокола в этом репозитории действуют сразу через ссылки, в проектах — после пересборки образа и `/box-update`. Живой прогон следующего шага проверяет и правки шага «Оркестратор на вопросе пользователю» — сообщение со ссылкой перед окном, вопрос словами пользователя продукта, ответы только по словам пользователя.

Следующий шаг — «Проверка агента проверок вживую»: начать с `my_local/orchestrator-limit-probe.sh` и `docs/researches/2026-10-15-page-agent.md`. - `docs/ARCHITECTURE.md` — 67 тыс. знаков, выше порога раздела 50 тыс.; предложение раздела уже в хвостах `docs/tasks/areas-config.md`.
