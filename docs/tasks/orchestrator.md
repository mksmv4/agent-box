# orchestrator

## Постановка

Цель: в проекте под обвязкой пользователь одной командой делает интерактивную сессию Claude Code на хосте оркестратором задачи. Оркестратор ведёт задачу движком: шаги идут без остановок; блокер, который снимается проверкой без решения или сведениями, недоступными контейнеру, снимает сам и помечает ответ как свой; вопрос, требующий решения пользователя, задаёт инструментом вопроса — при Remote Control он приходит пушем в приложение Claude; ответ пользователя записывает для цикла его словами; к другой задаче переходит только с согласия пользователя. Под оркестратором движок по умолчанию не шлёт уведомлений в Telegram. Ход цикла виден: движок пишет журнал в постоянное место на хосте, оркестратор ведёт на claude.ai приватную страницу задачи со схемами по описанным правилам страниц, копия страницы — в `my_local/pages/` проекта. `README.md` описывает подключение Remote Control и запуск оркестратора.

Документ описывает структуру страницы задачи — разделы и их порядок: цель и схема очереди шагов — сделано, идёт, впереди; таблица итераций — время, шаг, длительность, исход, коммиты; текущее состояние; блок «Ждёт решения», пока вопрос пользователю открыт; история блокеров и кто ответил. Главное — сразу, подробности — в раскрывающихся блоках; вопрос, риски и неизвестное всегда на виду. Правила текста: обычные слова по `PROTOCOL.md` § Сообщения пользователю; у каждой вещи одно имя на всей странице, на схемах и в окне вопроса; у каждого действия назван исполнитель — движок, оркестратор, сессия, пользователь; шаги — по отдельности; короткие предложения, в абзаце одна тема — то, что автор поста берёт из ASD-STE100. Основания выводов — четырёх видов: факт с источником; оценка с диапазоном и базой; допущение и что изменится, если оно неверно; неизвестное, которое может поменять выбор. Без источника — «не проверено»; пустая категория — «не выявлено». Блок «Ждёт решения»: что строим и на чём остановились; откуда вопрос и почему решать сейчас; ограничения; риски и неизвестное; какой именно ответ нужен от пользователя; варианты — не меньше двух живых, у каждого цена и условие, при котором он лучше; рекомендация с основаниями рядом, при нехватке оснований — «рекомендации нет» и почему; варианты, отброшенные оркестратором, — причина и допущение, на котором держится отказ; вариант без условия, при котором он разумен, отбрасывается так же. Варианты в окне вопроса — полными фразами, теми же словами, что на странице. Формат под вопрос: меняется экран — картинка «как сейчас / после» с подписью, куда смотреть; меняется порядок действий — схема последовательности; меняются права и границы — схема границ и что будет при сбое; несколько критериев — таблица; простой выбор — пара строк текста. Правила схем: схема — SVG, нарисованный прямо в HTML страницы, без внешних библиотек; очередь шагов задачи — схемой всегда; схема строится из блоков, стрелок и подписей обычными словами; рядом со схемой — текст: порядок, направление, границы, что будет при сбое; предел числа блоков на схеме; цвета со смыслом, одинаковые на всех схемах; схема читается на экране телефона, в светлой и тёмной теме. Примеры — две страницы вымышленной задачи: в работе и с открытым вопросом. Проверка — пользователь: примеры, опубликованные страницами, открываются на телефоне и компьютере, задача и вопрос понятны по странице без таск-файла. Читает: `template/docs/PROTOCOL.md` § Сообщения пользователю, скилл оркестратора, скиллы страниц Claude Code `artifact-design` и `artifact-diagramming`, навык decision-mockups https://github.com/djd1m/dz-harness/tree/main/packages/skills-decision-mockups/decision-mockups — `SKILL.md`, `references/language-guide.md`, `references/mockup-kit.md`, `examples/context-cases.md`.

Ожидание: первый блокер оркестратор снимает сам, ответ помечен; второй вопрос приходит пушем, ответ из приложения доходит до цикла; задача доходит до «готово», оркестратор спрашивает о следующей; страница задачи открывается с телефона, обновляется после каждой итерации, при вопросе показывает блок «Ждёт решения» со схемой вариантов, копия лежит в `my_local/pages/`; журнал показывает ход итераций; в Telegram за прогон ничего не приходит.

Проверка шага: правка движка — проба в тестовом git-репозитории с заглушками `claude` и `curl`, как у задачи agent-loop (`tasks/agent-loop.md` § Постановка); правка скилла, протокола и образца — живая проверка пользователем по `RULES.md` § Конвенции работы.

Блокер: граница «проверка без решения» на конкретном случае; место журнала и что в него попадает из хода итерации; поведение Remote Control, пушей или страниц, разошедшееся с докой и описаниями инструментов; отказ классификатора режима auto на хосте при запуске движка из оркестратора — смежная задача sandbox-rule.

## Блокер

Оркестратор теперь доезжает до проектов: заведение проекта и обновление обвязки кладут его в проект вместе с правилами страниц и примерами, а в README agent-box появился раздел «Оркестратор» — как один раз настроить телефон и как запустить оркестратора с компьютера или с телефона. Шаг закрывается, когда вживую видно, что обновление обвязки кладёт оркестратора в проект, заведённый раньше.

1. Просьба сделать руками — обновление обвязки в тестовом проекте без оркестратора:

   1. Пересобери образ и подготовь тестовый проект — копию образца без оркестратора с первым коммитом:

      ```bash
      cd ~/tools/agent-box && docker compose build claude
      d=/tmp/box-update-probe && mkdir -p "$d" && tar -C template --exclude=box-orchestrate -cf - . | tar -C "$d" -xf - && git -C "$d" init -q && git -C "$d" add -A && git -C "$d" commit -qm init
      ```

   2. Открой в нём новый контейнер:

      ```bash
      cd /tmp/box-update-probe && docker run --rm -it -v "$PWD":/workspace/box-update-probe -w /workspace/box-update-probe -v "$HOME"/.claude-box:/home/node -v "$HOME":/root/host-home:ro maksim44/claude-box
      ```

   3. В сессии — `/box-update`. Ожидание: в итоге сказано, что в проекте появился оркестратор, как его запускать и где настройка; в проекте лежит папка оркестратора с описанием скилла, правилами страниц и двумя примерами; в истории git — коммит обновления и запись журнала. Проверка на хосте: `ls -R /tmp/box-update-probe/.claude/skills/box-orchestrate; git -C /tmp/box-update-probe log --oneline`.
   4. `/box-update` ещё раз, новой сессией в той же папке: ответ — обвязка свежая, правок нет.

   Уборка после проверки: `rm -rf /tmp/box-update-probe ~/.claude-box/.claude/projects/-workspace-box-update-probe`.

2. Вопрос: дописать ли оркестратора в схему каркаса в карточках документов — дерево того, что лежит в проекте под обвязкой? Сейчас там из скиллов только `/box-next`; карточки правятся только с твоего разрешения. Предложение — строка между `/box-next` и настройкой сигнала context-guard, комментарии соседних строк сдвигаются под неё:

   ```text
       ├── skills/box-next/         # скилл /box-next <задача>: один шаг задачи и завершение по протоколу
       ├── skills/box-orchestrate/  # скилл /box-orchestrate <задача>: сессия на хосте ведёт задачу движком; правила страниц и примеры
       └── context-guard.conf       # CONTEXT_GUARD_MODE=rules: сигнал context-guard предлагает варианты по правилам проекта
   ```

Как ответить: допиши в конец файла docs/tasks/orchestrator.md строку, которая начинается с «ответ:», и после двоеточия — ответ на оба пункта с номерами: по п. 1 — «работает» или что пошло не так, по п. 2 — «ок» или свой вариант; например «ответ: 1 — работает; 2 — ок». Потом запусти в Claude /box-next orchestrator или в терминале agent-loop.sh --host orchestrator.
