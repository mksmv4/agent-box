# areas-config

## Постановка

Цель: проект с несколькими разработчиками и с разросшейся документацией ведётся обвязкой без лишнего контекста и без конфликтов при слиянии веток. Архитектура и правила делятся по областям кода — частям проекта со своими папками, например фронт и бэк, — когда в документации проекта раздел уже есть или документ перерос порог; правила области подгружаются сессии, которая трогает код области, и не подгружаются остальным. Журнал и реестр решений сливаются между ветками без конфликта. Пределы движка и порог раздела живут в файле настроек в корне проекта под git. Одиночный проект без раздела и без файла настроек работает как раньше.

Повод — беседа 2026-10-14 о пилотном проекте с двумя разработчиками, фронт и бэк: в документации проекта раздел по областям уже есть, архитектура фронта — около 75 тыс. знаков.

Раскладка раздела — по ответу пользователя: у разделённого документа своя папка, основной файл — в ней же под прежним именем. Архитектура — `docs/architecture/ARCHITECTURE.md`: общая часть — сервисы, связи между областями, деплой — и список областей со ссылками; область — `docs/architecture/<область>.md`. Правила — `docs/rules/RULES.md`, общие, хаб подключает их на старте; область — `docs/rules/<область>.md`. Ссылки протокола и скиллов по голому имени `ARCHITECTURE.md` и `RULES.md` верны при обеих раскладках. Тексты правил области лежат в `docs/rules/`, а Claude Code их подгружает через указатель: папка `.claude/` — защищённый путь Claude Code, запись в неё в режиме auto идёт классификатору, в интерактивном режиме — вопросом (code.claude.com/docs/en/permission-modes § Protected paths, 2026-10-14), а сессии пишут в правила грабли.

Файл настроек — `agent-box.yml` в корне проекта под git, плоский YAML «ключ: целое число»: пределы движка — итераций за запуск, пауза между итерациями, итераций подряд без прогресса, потолок ходов итерации, минут до алерта таймера — и порог раздела в знаках. Нынешние значения — по умолчанию: 10, 10 секунд, 3, 200, 60 минут; порог — 50 000 знаков. Пределы общие для всех разработчиков проекта. Алерт таймера остаётся уведомлением, итерацию не останавливает. Режим запуска движка — контейнер, хост, открытая сеть — в файл не идёт: правка агентом вывела бы следующий запуск из песочницы.

## Контекст

Шаг «Слияние кнопкой»: команды пробы на GitHub и GitLab и уборки — в секции «Блокер», пробу ведёт пользователь. Следующее — по ответу: факт в `docs/ARCHITECTURE.md` § Образец проекта на месте фразы «Слияние кнопкой запроса на слияние на GitHub и GitLab ждёт пробы» — площадка, способ слияния, итог, дата; чекбокс шага. Площадка показала конфликт — предложение другого способа блокером.

Подготовка тестового репозитория из блокера прогнана на хосте 2026-10-15, git 2.43.0, в `/tmp/ac-button-dry`: с `.gitattributes` образца слияние веток `ac-a`, затем `ac-b` в `main` проходит чисто, обе записи в обоих файлах; без `.gitattributes` — конфликт в обоих файлах: проба различает исходы. Там же голый клон, `git merge-tree --write-tree main ac-b` при `main` на `ac-a` — чисто: голый репозиторий git 2.43 берёт атрибуты из `HEAD:.gitattributes` (`man git-config` § `attr.tree`). Как сливают площадки — неизвестно до пробы. Старые сообщения о `merge=union` при слиянии кнопкой: GitHub — github.com/rubocop-hq/rubocop/pull/3594 (2016), веб-слияние файла с конфликтом не прошло; GitLab — gitlab.com/gitlab-org/gitlab-foss/-/issues/17325; Bitbucket — jira.atlassian.com BCLOUD-21337, BSERV-19161.

Команды блокера сверены 2026-10-15: GitLab создаёт частный проект при первой отправке в несуществующий адрес (`doc/topics/git/project.md`), запрос на слияние — опциями отправки `merge_request.create` и `merge_request.target` (`doc/topics/git/commit.md` § Push options), удаление проекта — «Actions» → «Delete», затем «Delete permanently», иначе удаление через 30 дней (`doc/user/project/working_with_projects.md`); `gh repo delete` с именем репозитория без `--yes` спрашивает подтверждение, нужна область `delete_repo` (`gh repo delete --help`, gh 2.102.0). На хосте `gh` вошёл в github.com по ssh, `glab` нет.

Уборка блокера покрывает и пункт 9 прошлого: `/tmp/ac-*`, истории сессий `-workspace-ac-live-*` и `-workspace-ac-rules-*`, сети Docker `ac-live-*_default` и `ac-rules-*_default`, черновик `my_local/areas-config/`.

Движок по этой задаче — с `--host` (`AGENTS.md` § Грабли).

## Блокер

Последний шаг задачи — проверить, сливаются ли журнал и реестр решений без конфликта, когда ветку вливают кнопкой на сайте GitHub и GitLab. Командой git это уже проверено, а кнопкой сайт сливает своими средствами. Создать репозиторий на твоей учётной записи и нажать кнопку сессия не может, поэтому пробу ведёшь ты. На компьютере та же подготовка без правила слияния дала конфликт, с правилом — нет: проба покажет, какой из двух случаев на сайте.

**Вопрос.** Что показали GitHub и GitLab на втором запросе на слияние после слияния первого — кнопку слияния или конфликт, — и лежат ли потом обе тестовые записи в обоих файлах? Каким способом сливал: обычное слияние, одним коммитом (squash) или rebase?

**Сделать руками** — терминал на компьютере, по порядку. Кнопкой сливать тем способом, каким сливает пилотный проект; не знаешь — обычным слиянием, оно по умолчанию.

1. Тестовый репозиторий: две ветки, каждая дописывает свою запись в начало журнала и реестра:

   ```
   mkdir /tmp/ac-button && cd /tmp/ac-button
   git init -q -b main
   printf '%s\n' 'docs/JOURNAL.md merge=union' \
     'docs/DECISIONS.md merge=union' >.gitattributes
   mkdir docs
   printf '# Журнал\n\n- старая запись\n' >docs/JOURNAL.md
   printf '# Реестр\n\n- старая запись\n' >docs/DECISIONS.md
   git add -A && git commit -qm init
   for b in ac-a ac-b; do
     git switch -qc $b main
     sed -i "2a - $b" docs/JOURNAL.md docs/DECISIONS.md
     git commit -qam $b
   done
   git switch -q main
   ```

2. GitHub — частный репозиторий `ac-button-probe` и два запроса на слияние; последние две команды печатают их адреса:

   ```
   gh repo create ac-button-probe --private \
     --source . --push
   git push -q origin ac-a ac-b
   gh pr create -B main -H ac-a -t ac-a -b ''
   gh pr create -B main -H ac-b -t ac-b -b ''
   ```

   На сайте: слить первый запрос, `ac-a`; открыть второй, `ac-b`, и записать, что написано у кнопки, — что конфликтов нет или «This branch has conflicts that must be resolved». Конфликта нет — слить и его. Проверка:

   ```
   git fetch -q origin
   git grep -n 'ac-[ab]$' origin/main -- docs
   ```

   Ждём: второй запрос без конфликта; четыре строки — `ac-a` и `ac-b` в каждом из двух файлов.

3. GitLab — нужна учётная запись с SSH-ключом; проект `ac-button-probe` создаётся частным при первой отправке. В первой строке — свой логин GitLab:

   ```
   u=<логин на GitLab>
   git remote add gitlab \
     git@gitlab.com:$u/ac-button-probe.git
   git push gitlab main
   for b in ac-a ac-b; do
     git push gitlab $b -o merge_request.create \
       -o merge_request.target=main
   done
   ```

   Отправка веток печатает адреса двух запросов. На сайте — так же: слить первый, у второго записать, что показано у кнопки — кнопка «Merge» или сообщение о конфликте; конфликта нет — слить. Проверка:

   ```
   git fetch -q gitlab
   git grep -n 'ac-[ab]$' gitlab/main -- docs
   ```

   Ждём то же: второй запрос без конфликта, четыре строки.

4. Уборка — после пробы. Репозиторий GitHub — команда попросит ввести его имя для подтверждения:

   ```
   gh auth refresh -s delete_repo
   r=$(gh api user -q .login)/ac-button-probe
   gh repo delete "$r"
   ```

   Или на сайте: настройки репозитория, внизу «Delete this repository» — тогда эти команды не нужны. Проект GitLab — на сайте: страница проекта, справа вверху «⋮» (Actions) → «Delete», ввести имя проекта; затем там же «Delete permanently» — без этого GitLab удалит проект через 30 дней.

   Тестовые папки этой задачи, истории их сессий и сети Docker:

   ```
   cd ~
   rm -rf /tmp/ac-*
   rm -rf ~/.claude-box/.claude/projects/-workspace-ac-*
   docker network ls -q --filter name=ac-live \
     --filter name=ac-rules | xargs -r docker network rm
   ```

   Черновик прошлых шагов — в папке клона agent-box:

   ```
   rm -rf my_local/areas-config
   ```

Как ответить: допиши в конец файла docs/tasks/areas-config.md строку, которая начинается с «ответ:», и после двоеточия — сам ответ: что показал каждый сайт на втором запросе, что нашла проверка и каким способом сливал. Потом запусти в Claude /box-next areas-config или в терминале agent-loop.sh --host areas-config.
