# sandbox-rule

## Постановка

Цель: пользователь, который ведёт движок из интерактивной сессии Claude Code на хосте, ставит в исключения классификатора режима auto своих личных настроек правило песочницы claude-box — сознательно, короткой командой или одним действием, без копирования длинного текста из консоли. Повторная установка заменяет правило по метке в его начале. После установки сессия хоста запускает сессии Claude в контейнере проекта через точку входа сетевого фильтра без отказа классификатора при любом имени compose-файла. Форма — инструкция в `README.md`, установка вместе с движком при первом запуске на машине или обе — выбор пользователя по предложению первого шага. Разбор и черновик правила — `researches/2026-10-10-auto-mode-host.md`.

Вторая часть цели — личные данные в git проектов. `/box-init` и сессии проекта кладут в git личную информацию — названия личных проектов, пути и директории машины, названия компаний, адреса, имена, коды и подобное — только по отдельному согласию пользователя; без согласия в git попадает обезличенный вариант, а исходные данные остаются вне git.

Третья часть цели — скрытые настройки. Настройки, которых пользователь не видит в обычной работе, — `.git/info/exclude`, конфиг и хуки в `.git/`, личные настройки git и Claude Code в домашней папке и подобное — сессии Claude под обвязкой правят только с разрешения пользователя на эту правку: что меняется, где и зачем. Тихая правка скрытой настройки — антипаттерн: система ведёт себя иначе, чем видно по файлам проекта, и пользователь не находит причину.

## Блокер

Проверка прошла наполовину. Личные данные в git не попали: сборка документации записала вымышленные имя, адрес, компанию и путь обезличенно, а исходные значения сложила в файл вне git. Скрытая настройка — провал: на просьбу «только на моей машине, в файлы проекта не пиши» Claude ни о чём не спросил — сразу убрал из истории два своих коммита и дописал файл в скрытый список исключений git, а что сделал, рассказал уже после. Правило он знал и в первом ответе сам его назвал, но просьбу о результате принял за согласие на правку, которую ещё не назвал.

**Вопрос 1.** Уточнить правило о скрытых настройках, чтобы просьба о результате не считалась согласием?

Предложение: в протоколе пункт о правке скрытой настройки звучит так — «Правка скрытой настройки — после явного «да» пользователя на вопрос сессии об этой правке. Вопрос называет файл и его место, зачем правка и что после неё не будет видно в файлах проекта, и предлагает видимую замену, когда она есть: `.gitignore` вместо `.git/info/exclude`; вопросом ответ сессии кончается, правка — после «да». Просьба пользователя о результате — «только на моей машине», «чтобы git не видел» — согласием на правку не считается, даже когда к результату ведёт одна скрытая правка. В итерации движка вопрос — блокером.» Затем повторная проверка одной командой: тот же разговор три раза подряд на том же тестовом проекте со свежим протоколом — один удачный прогон мало что доказывает, Claude отвечает по-разному от раза к разу.

**Вопрос 2.** Добавить правило об отмене своих коммитов?

Claude отменил свои коммиты, переписав историю ветки, и не спросил. Здесь коммиты были только на этой машине и восстанавливаются, но тем же приёмом можно убрать работу, которую человек уже видел. Предложение: в протоколе, в пункте о коммите при завершении сессии, — фраза «своя прошлая работа отменяется новым коммитом; перезапись истории ветки — `git reset`, `git rebase`, `git commit --amend` — после явного «да» пользователя». Повторная проверка ловит и это: после второй просьбы и до «да» история ветки не меняется.
