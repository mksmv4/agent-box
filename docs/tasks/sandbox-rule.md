# sandbox-rule

## Постановка

Цель: пользователь, который ведёт движок из интерактивной сессии Claude Code на хосте, ставит в исключения классификатора режима auto своих личных настроек правило песочницы claude-box — сознательно, короткой командой или одним действием, без копирования длинного текста из консоли. Повторная установка заменяет правило по метке в его начале. После установки сессия хоста запускает сессии Claude в контейнере проекта через точку входа сетевого фильтра без отказа классификатора при любом имени compose-файла. Форма — инструкция в `README.md`, установка вместе с движком при первом запуске на машине или обе — выбор пользователя по предложению первого шага. Разбор и черновик правила — `researches/2026-10-10-auto-mode-host.md`.

Вторая часть цели — личные данные в git проектов. `/box-init` и сессии проекта кладут в git личную информацию — названия личных проектов, пути и директории машины, названия компаний, адреса, имена, коды и подобное — только по отдельному согласию пользователя; без согласия в git попадает обезличенный вариант, а исходные данные остаются вне git.

Третья часть цели — скрытые настройки. Настройки, которых пользователь не видит в обычной работе, — `.git/info/exclude`, конфиг и хуки в `.git/`, личные настройки git и Claude Code в домашней папке и подобное — сессии Claude под обвязкой правят только с разрешения пользователя на эту правку: что меняется, где и зачем. Тихая правка скрытой настройки — антипаттерн: система ведёт себя иначе, чем видно по файлам проекта, и пользователь не находит причину.

- [ ] Разбивка на шаги по `researches/2026-10-10-auto-mode-host.md`, `README.md` § Движок автоцикла, установке команды в начале `agent-loop.sh`, `ARCHITECTURE.md` § Ступени изоляции — режимы разрешений; для личных данных — `skills/box-init/SKILL.md`, `skills/box-init/documents.md`, `template/docs/PROTOCOL.md`, `template/docs/RULES.md`; для скрытых настроек — `template/docs/RULES.md`, `template/docs/ARCHITECTURE.md`: предложение формы доставки правила, места и формы правила о личных данных, места правила и антипаттерна о скрытых настройках и очереди — у каждого шага что делается, чем проверяется и какие файлы читает, размер шага по `PROTOCOL.md` § Таск-файлы — в секцию «Блокер» со статусом «блокер»; по согласию пользователя очередь слово в слово вписывает в «Постановку» сессия, свой вариант — пользователь; чекбокс этого шага ставит сессия, увидевшая очередь там.

Проверка шага: правка скрипта записи правила — проба в контейнере на копии настроек во временной папке (`AGENTS.md` § Грабли): первый запуск добавляет правило после `"$defaults"`, повторный заменяет его, запись с меткой одна, прочие ключи файла на месте. Установка на хосте и живая проверка — пользователь по `RULES.md` § Конвенции работы: `claude auto-mode config` показывает правило; сессия хоста в режиме auto запускает сессию в контейнере проекта строкой итерации движка без отказа классификатора. Правка образца и скиллов о личных данных — живая проверка пользователем: пересборка, новый контейнер, `/box-init` в тестовой папке, где в коде и старых документах есть путь домашней папки, имя, адрес и название компании, — без согласия пользователя в коммитах их нет. Такой шаг кончается блокером с командой и ожидаемым итогом.

Блокер: форма доставки правила; текст правила — что песочница покрывает и что нет; правило, не снявшее отказ на живой проверке; что считается личными данными, как и когда пользователь даёт согласие, куда ложатся исходные данные; что считается скрытой настройкой.

## Контекст

Шаг «разбивка» сделан и ждёт ответа на блокер. По согласию сессия вписывает очередь из секции «Блокер» в «Постановку» слово в слово под шагом разбивки, ставит его чекбокс и переносит блокер в `DECISIONS.md`; ответ с поправками — поправленная очередь снова блокером, свой вариант очереди пользователь вписывает сам.

Размеры шагов предложенной очереди (`LC_ALL=C.UTF-8 wc -m` по списку «Читает»): команда правила — 87 тыс. символов, живая проверка правила — 41 тыс., раздел протокола — 85 тыс., живая проверка личных данных — 40 тыс.

Опоры шагов:

- Основа режима движка — скрипт, которым пользователь поставил правило на своей машине, `my_local/claude-box-sandbox-rule.sh`, вне git: замена записи по метке через `jq`, копия настроек за день, вывод `claude auto-mode config`. Файла `~/.claude/settings.json` у нового пользователя может не быть — скрипт его не создаёт.
- Проба записи правила — в контейнере (`AGENTS.md` § Грабли): шаг ведёт сессия контейнера (`docker compose run --rm claude` в корне клона, затем `/box-next sandbox-rule`) или сессия хоста запускает в контейнере одну пробу без Claude. Образ несёт `jq` (`container/Dockerfile`).
- Черновик правила (`researches/2026-10-10-auto-mode-host.md` § Текст правила) говорит «с хоста подключены только папка проекта и ~/.claude-box», а домашняя папка хоста подключена только на чтение и закрыта процессу агента (`README.md` § Запуск) — поправка вынесена вопросом 2 блокера.
- Команда доследования итерации, которую печатает движок (`docker compose -f <файл> run --rm claude --resume <id>`), идёт без точки входа сетевого фильтра — правило её не покрывает.
- Сборка документации `/box-init` велит переносить старые журналы, карточки и решения «без правок» и ответы — «как записаны в источнике» (шаблон задачи сборки, шаги «история» и `docs/DECISIONS.md`) — главный путь личных данных из заметок под `.gitignore` в git.
- Правила и архитектура образца (`template/docs/RULES.md`, `template/docs/ARCHITECTURE.md`) — пустые заготовки: `/box-init` кладёт их только при первом заходе, сборка документации переписывает их под проект; протокол проекту обновляют `/box-update` и повторный `/box-init`.
- Опоры части о личных данных: образец несёт `my_local/` вне git — `/box-init` дописывает его в `.gitignore` проекта; у agent-box такое правило — `RULES.md` § Конвенции работы, первый пункт. Повод части о скрытых настройках — беседа 2026-10-10: сессия хоста без спроса дописала `.claude/settings.local.json` в `.git/info/exclude` agent-box, и git перестал показывать файл. Разрешение через `/box-init` и `/box-update` не поставить — скиллы работают в контейнере, `~/.claude` хоста им закрыта (`DECISIONS.md` 2026-10-10 — правило песочницы claude-box в продукте).

## Блокер

Задача разбита на четыре шага. Нужны ответы на шесть вопросов и согласие на очередь.

1. **Как ставить разрешение для Claude на компьютере, который ведёт движок?** Claude на компьютере в режиме auto может отказаться запускать сессию Claude в контейнере проекта: со стороны команда выглядит как запуск агента без присмотра, а что контейнер — песочница с закрытой сетью, из неё не видно. Разрешение — одна запись в личных настройках Claude Code на компьютере.
   Предложение: короткая команда `agent-loop.sh --sandbox-rule` — человек запускает её в терминале один раз на машину; повторный запуск заменяет запись, прежние настройки сохраняются копией с датой рядом. В README — новым пунктом разовой настройки оркестратора: разрешение нужно тем, кто ведёт движок из Claude. При первом запуске движка вопроса о разрешении нет: движок ставят и те, кому оно не нужно, а оркестратор запускает движок там, где ответить некому.

2. **Что разрешение покрывает?** Предложение: текст, который уже стоит на этой машине, с одной поправкой. Разрешено: запуск Claude в контейнере проекта через сетевой фильтр, в том числе продолжение сессии и работа без вопросов о разрешениях; контейнер описан как песочница — сеть только на список адресов, обычный пользователь, с компьютера подключены папка проекта и отдельная домашняя папка контейнера. Не покрыто: запуск без сетевого фильтра, подключение других папок, смена пользователя, расширенные права, файл настройки контейнера вне корня проекта. Поправка: прежний текст говорит, что домашняя папка компьютера в контейнер не подключена, а она подключена — только на чтение и закрыта от агента; текст скажет так.

3. **Что считать личными данными?** Предложение: сведения о человеке и его окружении, которые проекту для работы не нужны, — имена людей, названия личных проектов и компаний, адреса, телефоны, почта, пути и папки компьютера (путь в домашней папке пишется через `~`), имена компьютеров и адреса домашней сети, номера договоров и счетов, коды клиентов. Правило действует и тогда, когда значение уже есть в коде проекта.

4. **Как пользователь даёт согласие и где лежат исходные данные?** Предложение: по умолчанию сессия пишет в git обезличенный вариант — «пилотный проект», «<компания>», `~/…` — и не спрашивает, движок не останавливается. Исходные значения — в файле `my_local/personal.md` проекта, вне git: строка на замену — что написано в git, что было на самом деле, в каком файле. Сессия спрашивает согласие, когда без исходного значения документ теряет смысл; в движке — вопросом блокера. Согласие на вид данных навсегда («название компании можно») — строкой в правилах работы проекта (`docs/RULES.md`), следующие сессии не спрашивают.

5. **Что считать скрытой настройкой?** Предложение: файл, который меняет поведение git, Claude Code или оболочки и не виден среди файлов проекта: всё в папке `.git/` — настройки, хуки, список исключений; настройки под `.gitignore`, например `.claude/settings.local.json`; личные настройки в домашней папке компьютера и контейнера — `~/.gitconfig`, `~/.config/`, `~/.claude/`, файлы запуска оболочки (`~/.zshrc`, `~/.bashrc`), планировщики задач. Перед правкой сессия называет, что меняет, где и зачем, предлагает видимую замену, когда она есть (`.gitignore` вместо списка исключений в `.git/`), и правит только после явного «да» на эту правку; в движке — вопросом блокера.

6. **Где записать правила о личных данных и скрытых настройках?** Задача называла правила и архитектуру образца, но их получают только новые проекты, и сборка документации переписывает их под проект. Предложение: новый раздел протокола — его копию получают все проекты при обновлении обвязки, и его читает каждая сессия на старте; тихая правка скрытой настройки описана там же как антипаттерн, с причиной. Сборке документации, которая сейчас переносит старые журналы и решения «без правок», добавится оговорка об обезличивании.

**Очередь.** Предложение — четыре шага: команда разрешения с README и пробой на копии настроек; живая проверка разрешения — ведёте вы, сессия готовит тестовую папку и команды; раздел протокола о личных данных и скрытых настройках с оговоркой для сборки документации; живая проверка — ведёте вы: тестовый проект с подложенными личными данными, сборка документации, в git их нет.
