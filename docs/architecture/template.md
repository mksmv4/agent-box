# Образец проекта и скиллы контейнера

## Образец проекта — `template/`

То, что `/box-init` кладёт в новый проект: хаб `AGENTS.md` со строкой «Чтение на старте» и `CLAUDE.md` строкой `@AGENTS.md`; заготовки документов `docs/` с заголовками обязательных разделов, пустые `docs/tasks/` и `docs/researches/`; `docs/PROTOCOL.md` — рабочий оригинал протокола; скиллы `.claude/skills/box-next/`, `.claude/skills/box-orchestrate/` — оркестратор с правилами страниц и примерами, — `.claude/skills/box-task/`, `.claude/skills/box-review/` и `.claude/skills/box-qa/`; `.claude/context-guard.conf` строкой `CONTEXT_GUARD_MODE=rules`; `.claude/settings.json` с правилами запрета (`container.md` § Ступени изоляции); `claude-box.yml` с сервисом `claude`; `.gitignore` строками `my_local/` и `/claude-box.yml`; `.gitattributes` строками `docs/JOURNAL.md merge=union` и `docs/DECISIONS.md merge=union`. Образ несёт папку в `/etc/claude-box/template/` вместе со скрытыми файлами.

`/box-task`, `/box-review` и `/box-qa` лежат в проекте и работают в любой его сессии — в контейнере и на хосте; вызываются только командой и начинают с чистого рабочего дерева, как скиллы контейнера (§ Скиллы контейнера).

- `/box-task` — заведение задачи: сначала имя, веха, цель, проверка шага и блокер, затем очередь шагов; вопросы пользователю по одному на сообщение, черновик целиком — только по просьбе, запись — после ответа на последний; таск-файл и строка задачи под вехой — одним коммитом с именем задачи в сообщении, его хэш войдёт в запись журнала о задаче на её «готово». Очередь, не согласованная за сессию, — один шаг «разбивка»: `/box-next` ведёт его сколько нужно сессий и кладёт предложенную очередь в секцию «Блокер», в «Постановку» её вписывает сессия по согласию пользователя или сам пользователь, чекбокс разбивки ставит сессия, увидевшая очередь там. Отдельным вопросом при заведении — ресерч и проверка постановки: выбранные встают первыми этапами очереди по шаблону `template/docs/PROTOCOL.md` § Ресерч и проверка постановки, а правки задачи от них приходят пользователю один раз — блокером последнего из этих этапов. Правила этапов живут в протоколе, скилл на них ссылается: задачу заводит и сессия в беседе без скилла, а протокол читают обе (решение пользователя 2026-11-13 в `DECISIONS.md`, `researches/2026-11-16-task-research-check.md` § Решения макета). Шаги — `template/.claude/skills/box-task/SKILL.md`.
- `/box-review` — ревью задачи со статусом «готово»: в конец очереди ложится этап ревью по всем коммитам задачи, статус — «в работе», коммит с именем задачи. Этап — строка «Этап <N> — ревью <K>.», абзац ревью один на этап и шаги-части строкой с коммитами: так таск-файл задачи пилотного проекта с 16 частями носил бы около 3 тыс. знаков ревью, а не 20 тыс. — по шагу на часть с повтором абзаца (2026-10-20). Задача без этапов получает перед первым шагом строку «Этап 1 — основная работа.». Само ревью делает цикл задачи: сессия обычного шага сверяет изменения с целью, критериями шагов, ответами пользователя по задаче, правилами и архитектурой — при разделе по областям и с файлами областей своего кода: правила области подгружаются, когда сессия читает файл в папке области (code.claude.com/docs/en/memory, 2026-10-21), а изменения шаг ревью смотрит через git, — и рядом с изменениями шага ей открыта вся задача. Находку по коммиту шага сессия до записи сверяет с нынешним видом файла: исправленное позже другим коммитом задачи — не находка (2026-11-20). Простоту ревью меряет по результату: находка — и случай из задачи, который код не обрабатывает, и сложность, которую можно убрать; случаи вне задачи не находки; когда простой результат требует переделки базового кода, предложений два — переделка и запасная правка на месте. Шагов несколько, когда изменения задачи вместе с «Постановкой» таск-файла и файлами областей больше размера шага. У каждой части в счёт идут файлы областей её коммитов; `ARCHITECTURE.md` шаг читает нужными разделами, вне счёта; ресерчи задачи в `docs/researches/` в ревью не идут; таск-файл, журнал и реестр шаг читает в нынешнем виде, и их изменения в счёт не идут. Прежний счёт — весь таск-файл, `ARCHITECTURE.md` и файлы областей всей задачи в каждой части, ресерчи в изменениях — делил задачу пилотного проекта на 39 частей: на код в части оставалось около 20 тыс. знаков из 147 тыс.; нынешний — на 15 (2026-11-20). Находки шаг ревью приносит блокером с предложенными шагами правок; дальше — тот же путь, что у разбивки: по согласию шаги правок вписывает сессия, сразу после шага ревью, и ставит ему чекбокс. Шаблон шага и деление — `template/.claude/skills/box-review/SKILL.md`.
- `/box-qa` — QA задачи со статусом «готово», после ревью: прогон в браузере глазами пользователя. Сценарии — файл `docs/qa/<задача>.md`: шапка с адресом приложения, командой запуска и источником учётных данных без значений, сценарий разделом — из задачи или вне её, действия, ожидание, итог. Сценарии составляет сама сессия `/box-qa` и согласует с пользователем в беседе: так он читает их до прогона, а цикл не тратит на согласие остановку (2026-10-21). По согласию в конец очереди ложится этап «Этап <N> — QA <K>.» с абзацем QA и шагами — группами до 5 сценариев: каждое действие в браузере приносит в контекст разметку страницы. После каждого действия шаг прогона снимает экран в файл `my_local/qa/<задача>/<K>-<сценарий>-<кадр>.png`, вне git — на снимках бывают данные клиентов: с именем файла снимок ложится на диск, а в контекст приходит строка с путём (проба 2026-10-30, `orchestrator.md`, предпросмотр через Playwright MCP); страница задачи оркестратора показывает кадры у сценария и листает их по порядку (`DECISIONS.md` 2026-10-30 — снимки экрана в QA); статус — «в работе», коммит с именем задачи; карта документации получает строку `qa/`, `.gitignore` — строки `.playwright-mcp/` и `my_local/`. Прогон делает цикл задачи на хосте, `agent-loop.sh --host`: браузер — MCP-сервер хоста, а MCP хоста в контейнер не едут (`container.md` § Образ и скрипт запуска). Провал сценария из задачи — находка с шагом правки; провал вне задачи — вопрос, чинить ли: случай вне задачи для ревью не находка, и решает пользователь; ответ «не чинить» в реестре убирает сценарий из следующего `/box-qa`. Дальше — путь находок ревью: шаги правок по согласию вписывает сессия, сразу после шага прогона. Повторный `/box-qa` очищает итоги и дописывает сценарии шагов правок. Открыто: пропускает ли режим auto итерации хоста действия браузера и запуск приложения — вживую не проверено. Шаблоны — `template/.claude/skills/box-qa/SKILL.md`.

Журнал и реестр решений сливаются между ветками без конфликта: при `merge=union` git на месте конфликта оставляет строки обеих веток — сначала текущей, затем вливаемой, — и записи, которые две ветки дописали в начало файла, после слияния лежат обе. Способ держится на записи в одну строку: строки, одинаковые в добавках обеих веток, git оставляет один раз, и у записи в несколько строк общие с записью другой ветки строки — ответ «ок», «Постановка» не правилась — уходят под заголовок чужой записи (проба 2026-10-15 с записями реестра под заголовком `##`). Поэтому запись реестра, как и журнала, — одна строка (`docs/PROTOCOL.md` § Протокол сессии, шаг 2 завершения); записи реестра прежнего вида в проекте остаются как есть, новые ложатся над ними. На стыке записей двух веток пропадает пустая строка между ними, список в разметке выглядит так же. Старая запись, правленная в обеих ветках, после слияния лежит в двух версиях. Проба 2026-10-15, git 2.43.0: тестовый репозиторий с `.gitattributes` образца и записью реестра прежнего вида, два круга слияния двух веток с записями одной строкой в начале журнала и реестра — все записи целиком, прежняя запись цела. Живая проверка 2026-10-15 на пересобранном образе: `/box-init` кладёт строки образца в `.gitattributes` — у проекта со своим файлом после его строк, — и две ветки с записями журнала и реестра сливаются командой git без конфликта. Кнопка запроса на слияние на GitHub правило не применяет: после слияния первой из двух веток с записями в начале журнала и реестра запрос второй GitHub показывает с конфликтом (`mergeable_state: dirty`) и не сливает. Основная ветка, влитая в ветку второй командой `git merge origin/main` на компьютере, ложится без конфликта — правило срабатывает у git, — и после отправки ветки запрос сливается, все записи на месте. Проба 2026-10-15: частный репозиторий GitHub, обычное слияние через API GitHub (`gh pr merge --merge`), git 2.43.0. GitLab не проверялся — решение пользователя 2026-10-15 (`DECISIONS.md`); старое сообщение пользователей о `merge=union` при слиянии кнопкой на GitLab — gitlab.com/gitlab-org/gitlab-foss/-/issues/17325. Порядок слияния кнопкой — абзац протокола образца после списка «Завершение» (`template/docs/PROTOCOL.md` § Протокол сессии): перед кнопкой основная ветка вливается в свою командой git на компьютере, ветка отправляется, те же команды снимают конфликт, показанный сайтом; протокол читает каждая сессия проекта на старте, и порядок она выполнит по просьбе или подскажет. Журнал и реестр остаются одним файлом каждый — решение пользователя 2026-10-15 (`DECISIONS.md`).

Правила области кода — текст в `docs/rules/<область>.md`, подгрузка — через `CLAUDE.md` в папке области со строкой `@`-импорта этого файла; путь импорта — от папки указателя, у `front/` — `@../docs/rules/front.md`. Вложенный `CLAUDE.md` вместе с его импортом Claude Code подгружает, когда сессия читает файл его папки, в том числе в подпапках; сессия по файлам вне папки их не видит. По документации так же действуют правка файла и `cat` одного файла (code.claude.com/docs/en/memory § How CLAUDE.md files load). Указатель `.claude/rules/<область>.md` с полем `paths:` по пути подгружает только свой текст, а файл своего импорта отдаёт на старте каждой сессии — правила фронта получает и сессия по бэку. Проба 2026-10-15, CLI 2.1.300: сессии `claude -p` в контейнере в режиме итерации движка, две тестовые папки с кодовыми словами в указателе и в файле импорта; у `.claude/rules/` чтение файла фронта дало оба слова, чтение файла бэка — слово импорта; у вложенного `CLAUDE.md` чтение `front/app.js` и `front/src/components/Button.js` дало оба слова, чтение файла бэка — ни одного. В истории сессии загрузка на старте — вложение `instructions`, подгрузка по пути — вложение `nested_memory` с путём файла. Живая проверка 2026-10-15 на копии пилотного проекта: сессия по файлу фронта назвала слово правил фронта, сессия по файлу бэка — нет.

Раздел по областям — архитектура и правила проекта папками `docs/architecture/` и `docs/rules/` (`skills/box-init/documents.md` § Раздел по областям). Его решает `/box-init` в описи источников, каждому документу по своему условию: документ уже разделён — прошлой сборкой или в источниках проекта — или текст его файла и отданных ему источников больше порога `split_chars` конфига agent-box (`engine.md`), в контейнере — из его копии `/etc/claude-box/config.yml` (`container.md` § Образ и скрипт запуска); области — из прошлой сборки, разделённых источников или папок кода верхнего уровня, при одной области документ остаётся одним файлом. Задача сборки получает на месте шага документа шаги раздела: общую часть, куда прежний файл переезжает `git mv`, и шаг на область; общая часть правил меняет и строку хаба, шаг области правил кладёт указатели в её папки. Области из описи `/box-init` называет в итоге: пользователь правит их в «Постановке» до их шагов. Папки `docs/architecture/` и `docs/rules/`, занятые проектом до первой сборки, уходят в `.old/`, как `docs/tasks/`. Дальше раздел держит протокол (`template/docs/PROTOCOL.md` § Порядок на месте): факт и конвенция одной области — в её файл, а документ одним файлом, переросший порог после записи сессии, получает предложение раздела в хвостах «Контекста» — раздел делает повторный `/box-init` новой задачей сборки. Живая проверка 2026-10-15: повторный `/box-init` на копии пилотного проекта завёл задачу сборки с шагами раздела архитектуры — общая часть и шаги фронта и бэка. Протокол, `/box-task` и карта образца называют правила и архитектуру голым именем `RULES.md`, `ARCHITECTURE.md`: при обеих раскладках оно ведёт на основной файл.

Правила о личных данных и скрытых настройках — раздел протокола (`template/docs/PROTOCOL.md` § Личные данные и скрытые настройки): свежую копию протокола получает каждый проект при `/box-update` и повторном `/box-init`, каждая сессия читает её на старте, а правила и архитектуру проекта сборка документации пишет под проект. Сборка документации переносит старые журналы и решения из заметок под `.gitignore` в git — главный путь личных данных в историю проекта, — поэтому шаблон её задачи обезличивает записи по тому же разделу.

Сервис `claude` живёт в `claude-box.yml` в корне проекта, под `.gitignore`: файл несёт пути и адреса машины, в git и деплой проекта он не попадает. Запуск — `docker compose -f claude-box.yml run --rm claude`. Образ `maksim44/claude-box`, `stdin_open` и `tty` для интерактива, права `NET_ADMIN` и `NET_RAW` для ограничения сети. `profiles: [claude]`: `docker compose -f claude-box.yml up` сервис пропускает, прямой `run` профиль активирует. `.env` проекта читает скрипт запуска (`container.md` § Образ и скрипт запуска), строки `env_file` у сервиса нет. Подключения — `container.md` § Образ и скрипт запуска. У `claude-box.yml` своё имя проекта Compose — строка `name: <проект>-claude`, где `<проект>` — имя проекта основного compose-файла: строка `name:` его дополнения или его самого, без неё и без файла — имя папки. Запуск Claude сверяет со своим файлом только ресурсы проекта Claude, и `--remove-orphans` из любого из двух файлов контейнеры другого оставляет; почему не общее имя — `ARCHITECTURE.md` § Анти-паттерны. Строка `COMPOSE_PROJECT_NAME` в `.env` проекта сильнее строки `name:` обоих файлов и возвращает Claude в проект основного файла. Claude — в сети сервисов основного compose-файла: сеть по умолчанию в `claude-box.yml` — блок `networks: default:` основного файла и его дополнения целиком, с именем и настройками, у сети без своего имени — `name: <проект>_default`, как её называет Compose; у проекта без своего compose-файла блока нет. Нет сети — запуск Claude создаёт её по блоку, есть — входит в неё; проект, поднятый после Claude, встаёт в ту же сеть с настройками блока; повторные запуски обоих сеть не пересоздают, `down` проекта при работающем Claude сеть оставляет (проба 2026-11-09, Compose 5.7.0, `researches/2026-11-09-compose-net.md`). Проект, сменивший имя или настройки сети в основном файле, отстаёт от `claude-box.yml` до повторного `/box-init`. Каждый запуск Claude в сеть проекта — и запуск проекта в сеть, созданную Claude, — печатает предупреждение Compose «a network with name … exists but was not created for project …» с советом `external: true`: предупреждение безвредно, а внешнюю сеть Compose не создаёт, и Claude без поднятого проекта с ней не стартует. Путь папки проекта в контейнере — явной строкой `/workspace/<проект>` в рабочем каталоге и подключениях (`container.md` § Образ и скрипт запуска).

## Скиллы контейнера — `skills/`

Скиллы едут в образе, `/etc/claude-box/skills/`, и доступны в любом проекте без установки: скрипт запуска при каждом старте контейнера кладёт их свежую копию в `~/.claude/skills`, скиллы пользователя под другими именами остаются рядом. Папки `box-*` прошлого запуска он перед этим убирает целиком: имена `box-*` принадлежат обвязке, а личный скилл Claude Code берёт верх над одноимённым скиллом проекта (code.claude.com/docs/en/skills, 2026-10-13) — копия `/box-task` или `/box-review` из образа до их переезда в проект заслонила бы проектную. Все вызываются только командой (`disable-model-invocation: true`) и начинают с чистого рабочего дерева: коммит в конце забирает дерево целиком, поэтому при незакоммиченных правках скилл перечисляет их и заканчивает без изменений. Исключение у `/box-update` и повторного `/box-init` — правки пользователя в таск-файлах, ответ на блокер и правка «Постановки»: они остаются в рабочем дереве вне коммитов скилла, их забирает коммит сессии задачи. `/box-init` исключения не делает для таск-файла незаконченной сборки документации — его дорабатывает сам.

- `/box-init` — заведение проекта в обвязку, его роль — `DESCRIPTION.md` § Ключевые решения. Занятые имена образца освобождаются переименованием в `.old` (`.old2`, `.old3`…); переименованное, что было под `.gitignore` проекта, остаётся вне git строкой в корневом `.gitignore` под комментарием сборки. Папки скиллов `box-next`, `box-orchestrate`, `box-task`, `box-review` и `box-qa` при любом заходе ложатся свежей копией поверх: имена принадлежат обвязке. Папки `docs/`, `.claude/`, `.claude/skills/`, а также `.gitignore`, `.gitattributes` и compose-файл проекта остаются на местах: образец ложится рядом, недостающие файлы — `cp -rn`, в `.gitignore` — недостающие строки образца `my_local/` и `/claude-box.yml`, в `.gitattributes` — недостающие строки образца (§ Образец проекта), в `.claude/settings.json` проекта — недостающие правила запрета образца, а правила прежнего образца на правку compose-файлов оттуда убираются. Сервис `claude` — в `claude-box.yml` при любом заходе: файла нет — копия образца, а сервис `claude` основного compose-файла проекта, заведённого раньше, переезжает в него без строки `env_file`: переменные `.env` передаёт скрипт запуска (`container.md` § Образ и скрипт запуска); имя проекта, путь папки проекта и блок сети — по § Образец проекта: имя проекта и блок сети `/box-init` берёт из текста основного файла и его дополнения, строки дополнения ложатся поверх, как у Compose, список `COMPOSE_FILE` в `.env` не разбирается — итог называет, откуда блок; путь — и на месте `${COMPOSE_PROJECT_NAME}` у сервиса прежней схемы: к пути привязаны сессии, автопамять и доверие Claude Code; строка `COMPOSE_PROJECT_NAME` в окружении сессии при основном compose-файле — конец без правок с просьбой перенести имя в строку `name:` основного файла; сервису дописываются недостающие подключения только на чтение, права ограничения сети, строка модели `ANTHROPIC_MODEL` образца и свои адреса проекта строкой `CLAUDE_BOX_ALLOW` по списку, согласованному с пользователем; в дополнительной рабочей копии git на месте подключений `./.git/…` — `.git` основного репозитория по пути из строки `gitdir:` (`container.md` § Образ и скрипт запуска). Основной compose-файл `/box-init` не правит: в контейнере прежней схемы он подключён только на чтение, строки сервиса `claude` на удаление уходят в итог. `claude-box.yml` в контейнере, запущенном из него, тоже только на чтение: у заведённого проекта строки на замену — `name:`, путь, блок сети — и на дописку уходят в итог. Правила запрета ложатся после записи в `claude-box.yml`: Claude Code применяет их в идущей сессии сразу (живая проверка 2026-10-04 — правка compose-файла после копии настроек образца получила отказ). Новая задача сборки ложится строкой под незакрытую веху `Сборка документации`, прежнюю с датой тоже; незакрытой нет — заводится новая без даты: задачи документации копятся под одной вехой. Шаги, опись источников и шаблон задачи сборки с вариантами хранения архива — `skills/box-init/SKILL.md`; рядом — карточки документов проекта `documents.md`.
- `/box-update` — обновление обвязки в проекте: протокол и скиллы проекта `/box-next`, `/box-orchestrate`, `/box-task`, `/box-review` и `/box-qa`, разошедшиеся с образцом или недостающие, — свежей копией, коммит и запись журнала; документы, задачи и сборка документации остаются как есть. Шаги — `skills/box-update/SKILL.md`.
