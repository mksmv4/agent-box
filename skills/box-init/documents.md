# Документы проекта — структура и границы

Правится только по прямому разрешению пользователя.

Карточка на каждый документ из дерева (§ Дерево): что сюда идёт, обязательные разделы, необязательные разделы, кто и на каком шаге пишет. Что сессия читает и когда — § Слои чтения; дом каждой части решения — § Где живёт решение; архитектура и правила, разделённые по областям кода, — § Раздел по областям; шаги завершения сессии — `docs/PROTOCOL.md` § Протокол сессии.

## Дерево

```
проект/
├── CLAUDE.md            # одна строка: @AGENTS.md
├── AGENTS.md            # единая точка входа любого агента: чтение на старте
│                        # (@docs/RULES.md, @docs/README.md, @docs/PROTOCOL.md), суть проекта,
│                        # жёсткие ограничения, грабли, точки входа
├── README.md            # для человека: quick start, запуск, деплой
├── claude-box.yml       # сервис claude вне git проекта: Claude Code в контейнере, docker compose -f claude-box.yml run --rm claude
├── docs/
│   ├── README.md        # карта документации: source of truth каждого дока
│   ├── RULES.md         # конвенции кода и работы, включая поведение агента
│   ├── PROTOCOL.md      # протокол сессии, таск-файлы, статус «готово», закрытие вехи, порядок на месте: копия из образца
│   ├── DESCRIPTION.md   # спецификация: цели, стек, ключевые решения
│   ├── ARCHITECTURE.md  # устройство системы, правила зависимостей, анти-паттерны
│   ├── GLOSSARY.md      # канонические термины (по необходимости)
│   ├── ROADMAP.md       # вехи, строка на задачу, открытые вопросы
│   ├── tasks/           # таск-файл на задачу: статус, постановка с очередью шагов, перезаписываемый контекст
│   ├── JOURNAL.md       # журнал работ: новые сверху
│   ├── DECISIONS.md     # реестр решений пользователя: вопрос агента → ответ; новые сверху
│   ├── DONE.md          # архив закрытых вех
│   └── researches/      # логи разведки по датам: как пришли к решениям
├── my_local/            # локальные артефакты вне git
└── .claude/
    ├── skills/box-next/         # скилл /box-next <задача>: один шаг задачи и завершение по протоколу
    ├── skills/box-orchestrate/  # скилл /box-orchestrate <задача>: сессия на хосте ведёт задачу движком; правила страниц и примеры
    └── context-guard.conf       # CONTEXT_GUARD_MODE=rules: сигнал context-guard предлагает варианты по правилам проекта
```

Архитектура и правила, разделённые по областям кода (§ Раздел по областям), — папками на месте своего файла:

```
проект/
├── docs/
│   ├── architecture/
│   │   ├── ARCHITECTURE.md  # общая часть: сервисы, связи между областями, деплой; § Области
│   │   └── <область>.md     # устройство кода области
│   └── rules/
│       ├── RULES.md         # конвенции работы и общие конвенции кода; хаб подключает на старте
│       └── <область>.md     # конвенции кода области
└── <папка области>/
    └── CLAUDE.md            # указатель: строка @-импорта docs/rules/<область>.md
```

## Слои чтения

| Слой | Когда читается | Что |
|---|---|---|
| Автозагрузка | каждая сессия: `CLAUDE.md` → `AGENTS.md` → строка «Чтение на старте» | `AGENTS.md`, `docs/RULES.md` (при разделе правил — `docs/rules/RULES.md`), `docs/README.md`, `docs/PROTOCOL.md` |
| Подгрузка по пути | сессия читает или правит файл в папке области: указатель `CLAUDE.md` папки | правила области `docs/rules/<область>.md` — при разделе правил |
| Старт работы | начало сессии, по `docs/PROTOCOL.md` § Протокол сессии | «Вехи» `ROADMAP.md`, таск-файл задачи |
| По запросу | правка кода; задача упёрлась | `ARCHITECTURE.md` — перед правкой кода, при разделе — общая часть и файл области правимого кода; `DESCRIPTION.md`, `GLOSSARY.md`, хвост `JOURNAL.md`, `researches/` |
| Архив | только grep | `DONE.md`, `DECISIONS.md`, таск-файлы со статусом «готово» |

## Где живёт решение

У каждой части решения один дом, остальные ссылаются:

- факт решения («теперь X») — `DESCRIPTION.md`, если про продукт, стек, цели; `ARCHITECTURE.md`, если про устройство кода, при разделе архитектуры — файл области, если факт про код одной области, иначе общая часть;
- путь к решению (варианты, доводы, замеры) — `researches/<дата>-<тема>.md`, когда была отдельная разведка: источники, замеры, больше одной сессии; иначе — «Зачем» в записи `JOURNAL.md` о задаче, где решили, или о работе вне задачи;
- запись `JOURNAL.md` — что сделано и зачем, с хэшами коммитов;
- решение пользователя на вопрос или предложение агента — запись `DECISIONS.md`: вопрос, предложение агента, ответ; факт и правило, порождённые решением, — в своих домах, запись ссылается;
- карточка вехи в `DONE.md` — что закрыто и ссылки на журнал и ресерч;
- `ROADMAP.md` и таск-файл держат вопрос, пока он открыт; после решения — строка-ссылка на факт.

## Раздел по областям

Область кода — часть проекта со своими папками, например фронт и бэк. Архитектура и правила делятся по областям, каждый документ по своему условию: в источниках проекта он уже разделён по областям, или его текст — при сборке документации текст его источников — больше порога. Порог — ключ `split_chars` конфига agent-box — в контейнере `/etc/claude-box/config.yml`, на хосте `config.yml` в папке, куда ведёт команда `agent-loop.sh`; без файла или ключа — 50 000 знаков; счёт — `LC_ALL=C.UTF-8 wc -m <файл>`. Документ без раздела — один файл, как в § Дерево.

У разделённого документа своя папка, основной файл — в ней под прежним именем:

- архитектура — `docs/architecture/ARCHITECTURE.md`: общая часть — сервисы, связи между областями, деплой — и § Области; область — `docs/architecture/<область>.md`;
- правила — `docs/rules/RULES.md`: конвенции работы и общие конвенции кода, хаб подключает их на старте; область — `docs/rules/<область>.md`: конвенции кода области.

§ Области — строка на область: имя — оно же имя файлов области, — папки кода и ссылка на файл архитектуры области. Живёт в архитектуре: в общей части разделённой, при разделе одних правил — разделом `docs/ARCHITECTURE.md`.

Правила области подгружает указатель — `CLAUDE.md` в папке области строкой `@`-импорта файла правил; путь — от папки указателя, у `front/` — `@../docs/rules/front.md`. Claude Code подгружает указатель с импортом, когда сессия читает или правит файл папки, в том числе в подпапках; сессия по коду других областей этих правил не видит. У области несколько папок — указатель в каждой, все импортируют один файл правил. В папке уже лежит `CLAUDE.md` проекта — строка импорта дописывается в него.

Ссылка по имени `ARCHITECTURE.md` или `RULES.md` ведёт на основной файл документа при обеих раскладках.

## `CLAUDE.md`

- Содержание: одна строка — `@AGENTS.md`.
- Обязательно: эта строка.
- Необязательно: ничего.
- Пишется: при создании проекта.

## `AGENTS.md` — хаб, единая точка входа любого агента

- Содержание: чтение на старте, суть проекта, жёсткие ограничения, грабли, точки входа.
- Обязательно: строка «Чтение на старте» — `@docs/RULES.md`, при разделе правил — `@docs/rules/RULES.md`, `@docs/README.md`, `@docs/PROTOCOL.md` (Claude Code подгружает импортом, другой агент читает по строке); суть проекта; жёсткие ограничения; § Грабли; точки входа в продукт проекта — по одной строке на файл, содержание живёт в самих файлах.
- Необязательно: ничего.
- Границы: пересказ содержимого других документов сюда не идёт; правила поведения агента — в `RULES.md` § Конвенции работы.
- Пишется: при создании проекта; § Грабли — шаг 4 завершения сессии.

## `README.md` — для человека

- Содержание: запуск продукта проекта — quick start, запуск, деплой.
- Обязательно: ничего.
- Необязательно: quick start, запуск, деплой.
- Границы: агент этот файл на старте не читает; правила для агента живут в `AGENTS.md`.
- Пишется: когда у продукта появляется запуск; при изменении запуска или деплоя.

## `docs/README.md` — карта документации

- Содержание: source of truth каждого документа — строка на документ.
- Обязательно: строка на каждый документ `docs/`, у `ARCHITECTURE.md` — с пометкой «читать перед правкой кода»; у разделённого документа — строка на основной файл и строка на файлы областей: `architecture/ARCHITECTURE.md` и `architecture/<область>.md` — пометка «читать перед правкой кода общую часть и файл области», `rules/RULES.md` и `rules/<область>.md` — пометка «правила области подгружаются при работе с её кодом»; правило «каждый факт живёт ровно в одном документе»; правило «архивы не чинятся»; маршрутизация решения одной строкой (§ Где живёт решение).
- Необязательно: ничего.
- Границы: карта — строки, не абзацы; содержание документов сюда не идёт.
- Пишется: при создании проекта; строка добавляется вместе с новым документом.

## `docs/RULES.md`

- Содержание: конвенции кода и работы, включая поведение агента.
- Обязательно: конвенции кода; конвенции работы.
- Необязательно: ничего; группировка и примеры при росте уходят в `ARCHITECTURE.md`.
- Раздел по областям: `docs/rules/RULES.md` — конвенции работы и общие конвенции кода; `docs/rules/<область>.md` — конвенции кода области; указатели в папках областей (§ Раздел по областям).
- Пишется: при создании проекта; конвенция, выяснившаяся в сессии, — шаг 4 завершения сессии, конвенция кода одной области — в файл области.

## `docs/PROTOCOL.md`

- Содержание: правила работы любой сессии проекта — копия протокола из образца `/etc/claude-box/template/docs/PROTOCOL.md`.
- Обязательно: § Протокол сессии, § Таск-файлы, § Статус «готово», § Протокол закрытия вехи, § Порядок на месте.
- Необязательно: ничего.
- Границы: файл — копия образца; проектные дополнения идут в `AGENTS.md` или `RULES.md`.
- Пишется: при создании проекта копией из образца; обновляется копией при следующем касании проекта после правки образца.

## `docs/DESCRIPTION.md` — спецификация

- Содержание: цели, стек, ключевые решения.
- Обязательно: цели; стек; ключевые решения.
- Необязательно: ничего.
- Границы: здесь факт решения про продукт, стек, цели; путь к решению — в ресерче или журнале.
- Пишется: при создании проекта; факт решения — в момент решения.

## `docs/ARCHITECTURE.md`

- Содержание: устройство системы, правила зависимостей, анти-паттерны.
- Обязательно: устройство системы; правила зависимостей; § Области — при разделе правил без раздела архитектуры.
- Необязательно: анти-паттерны; группировка и примеры, вытесненные из `RULES.md`.
- Раздел по областям: `docs/architecture/ARCHITECTURE.md` — устройство системы: сервисы, связи между областями, деплой; правила зависимостей между областями; § Области. `docs/architecture/<область>.md` — устройство кода области, правила зависимостей внутри неё, анти-паттерны области (§ Раздел по областям).
- Границы: здесь факт решения про устройство кода; путь к решению — в ресерче или журнале.
- Пишется: факт решения — в момент решения, при разделе факт про код одной области — в файл области; читается перед правкой кода, при разделе — общая часть и файл области правимого кода.

## `docs/GLOSSARY.md`

- Содержание: канонические термины.
- Обязательно: термин и определение, по строке на термин.
- Необязательно: сам документ — по необходимости.
- Пишется: по мере появления терминов.

## `docs/ROADMAP.md`

- Содержание: «что делать дальше и что уже сделано» на горизонте недель.
- Обязательно: «Вехи» с чекбоксами; под вехой — строка на задачу с чекбоксом и ссылкой на таск-файл.
- Необязательно: открытые вопросы — до решения, после решения строка-ссылка на факт.
- Границы: очередь шагов — в таск-файле; содержание закрытого — карточка в `DONE.md`, здесь от закрытого строка со ссылкой; сиюминутное — в «Контексте» таск-файла.
- Пишется: строка задачи под вехой — при создании задачи; чекбокс вехи и её свёртка в строку со ссылкой — протокол закрытия вехи; чекбокс строки задачи — пользователь после проверки руками задачи со статусом «готово».

## `docs/tasks/<задача>.md` — таск-файл

- Содержание: одна задача — машиночитаемая шапка, постановка, перезаписываемый контекст. Шаблон — `docs/PROTOCOL.md` § Таск-файлы.
- Обязательно: шапка — `статус` первой строкой; «Постановка» — цель, очередь шагов чекбоксами, способ проверки шага, критерий блокера; «Контекст».
- Необязательно: «Блокер» — дописывается в конец файла вместе со статусом «блокер»: вопрос пользователю, что уже выяснено, предлагаемое решение, ответ пользователя строкой «ответ:»; при статусе «в работе» сессия на первом же завершении переносит блокер с ответом в `DECISIONS.md` и стирает секцию.
- Границы: цель, способ проверки и очередь шагов меняет только пользователь, предложение сессии о новом шаге — в хвосты «Контекста»; «Контекст» перезаписывается целиком с переносом неразобранных предложений, история — в журнале; после статуса «готово» файл остаётся здесь навсегда.
- Пишется: генератор или пользователь — при создании; шапка, чекбокс шага и «Контекст» — шаг 3 завершения сессии; «Блокер» — сессия при постановке статуса «блокер», строка «ответ:» — пользователь.

## `docs/JOURNAL.md`

- Содержание: фактически сделанное — запись на задачу со статусом «готово» или законченную работу вне задачи: что сделано и зачем; задача, дополненная шагами после «готово», на новом «готово» получает новую запись — о новых шагах; новые записи сверху.
- Обязательно: запись одной строкой — у задачи `` - **<ISO-дата>** задача `<задача>`, `<типы коммитов>` (`<хэш>`, …) — что сделано. Зачем: … ``, у работы вне задачи — `` - **<ISO-дата>** `<типы коммитов>` (`<хэш>`, …) — что сделано. Зачем: … ``; в скобках — хэши всех коммитов работы, у задачи — после её прошлой записи.
- Необязательно: ничего.
- Границы: текст после хэшей — до 1250 знаков языком, понятным менеджеру, без имён файлов, классов и технического жаргона; «Зачем» — только при явной причине: её назвал пользователь или она записана по ходу работы — ресерч, сообщение коммита; такой нет — запись кончается на «что сделано»; на старте сессии не читается, поиск grep-ом по дате, сути и имени задачи; разбор вариантов — в ресерче, решение пользователя — в `DECISIONS.md`.
- Пишется: шаг 6 завершения сессии, поставившей задаче «готово» или закончившей работу вне задачи, — отдельным коммитом после коммитов работы; протокол закрытия вехи.

## `docs/DECISIONS.md` — реестр решений

- Содержание: решения пользователя на вопросы и предложения агента — ответы на блокеры, выбор из вариантов агента, отказы от предложений агента; новые записи сверху. Накопленные записи — база прецедентов для авторешения блокеров, следующей ступени автоцикла: часть блокеров решит модель по прошлым решениям пользователя, пользователь проверит её решения позже.
- Обязательно: запись на решение одной строкой `- **<ISO-дата>** <вопрос> — задача: <задача или «беседа»>; предложение агента: <…>; ответ: «<слова пользователя>»`; у ответа на блокер в конце — `; «Постановка» правилась` или `; «Постановка» не правилась`.
- Необязательно: в конце строки — `; ссылка на факт: …` в спеке или архитектуре и на правило в `RULES.md` или `AGENTS.md`, когда решение их породило.
- Границы: здесь случай — вопрос, предложение агента, ответ пользователя; факт «теперь X» живёт в спеке или архитектуре, правило — в `RULES.md` или `AGENTS.md`, решения агента внутри шага — «Зачем» в записи журнала, разбор вариантов — ресерч; на старте сессии не читается, поиск grep-ом по дате и вопросу.
- Пишется: шаг 2 завершения сессии; ответ на блокер — до стирания секции «Блокер».

## `docs/DONE.md`

- Содержание: архив закрытых вех.
- Обязательно: карточка на закрытую веху — что закрыто, ссылки на журнал и ресерч.
- Необязательно: ничего.
- Границы: карточка ссылается, не пересказывает; детали — в спеке или архитектуре, путь — в журнале или ресерче; решения пользователя — в `DECISIONS.md`.
- Пишется: протокол закрытия вехи.

## `docs/researches/<дата>-<тема>.md`

- Содержание: лог разведки — как пришли к решению: источники, замеры, варианты.
- Обязательно: дата и тема в имени; источники.
- Необязательно: замеры; отвергнутые варианты.
- Границы: факт решения живёт в спеке или архитектуре, здесь путь к нему; заводится, когда была отдельная разведка — источники, замеры, больше одной сессии.
- Пишется: сессией разведки.
